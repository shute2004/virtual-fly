# Flyppy並列学習アーキテクチャ再設計案レビュー

Date: 2026-09-15 09:24 JST  
対象: `docs/20260915_flyppy学習アーキテクチャ再設計案.md`  
Status: **review / rewrite**

## 1. 結論

提案されている

```text
複数 Fly worker が episode を並列実行
→ 各 worker は episode-local な神経状態・可塑状態を持つ
→ episode 終了時に plasticity transaction を生成
→ 最新の shared global weight に順次 commit
→ 終了した worker は最新版から即座に次 episode を開始
```

という方式は、`virtual-fly` の Flyppy 学習を高速化するための基本アーキテクチャとして妥当である。

特に次の判断は維持してよい。

- weight averaging をしない
- worker の `W_local_end` で global weight を上書きしない
- topology / metadata は全 worker で共有する
- membrane / spike / trace / modulation / eligibility / body state は worker-local にする
- episode 終了時に可塑性操作だけを global weight へ commit する
- global curriculum は経験分布として共有する
- GPU 側は worker dimension を持つ batched dispatch にする
- MuJoCo / retina / peripheral state は worker ごとに独立させる
- 終了の早い worker を長い episode に待たせない

したがって、設計の方向自体を変える必要はない。

修正すべきなのは主に、実装順・メモリ構成・transaction 表現・checkpoint の扱いである。

また、この並列化は `virtual-fly` の研究対象そのものではなく、**同じ学習をより短い wall-clock time で進めるための計算基盤**として扱うべきである。

`population=1` と `population>1` の差を詳細に研究することを目的にしない。必要なのは、並列化実装が壊れていないことを確認する回帰テストと不変条件の検証だけである。

## 2. canonical training は async shared-weight でよい

この文書の revision で採用された

```text
asynchronous shared weight
+ episode-local worker
+ serialized transaction commit
```

を canonical training として進めてよい。

概念的には以下で十分である。

```text
GlobalWeightStore Wg(v)

worker 0: Wg(v0) -> episode -> T0
worker 1: Wg(v1) -> episode -> T1
worker 2: Wg(v2) -> episode -> T2

episode 完了順に

Wg <- Apply(Wg, Ti)
version += 1

完了した worker は newest Wg から次 episode を開始
```

ここで重要なのは、`Ti` が外部 optimizer の更新ではなく、worker 内で実際に起きた

```text
sensory stimulation
→ neural dynamics
→ DAN / neuromodulation
→ eligibility
→ local plasticity
```

から得られた更新であることだけである。

複数 episode の経験を同時生成すること自体を、別の研究テーマへ拡張する必要はない。

## 3. transaction 方式は現行 plasticity rule と相性がよい

現行則は概ね各 edge について

```text
eligibility <- eligibility_decay * eligibility + local
weight <- clamp(weight + d, 0, weight_max)

d = learning_rate * modulation * eligibility
```

である。

したがって、episode 内で起きた weight 操作を transaction として扱う方針は適切である。

### 3.1 additive + clamp の要約

文書にある

```text
shift = 0
lo = 0
hi = M

for each d:
    shift += d
    lo = clamp(lo + d, 0, M)
    hi = clamp(hi + d, 0, M)

commit:
    w = clamp(w + shift, lo, hi)
```

という要約は、現在の「加算して `[0, M]` に clamp」を繰り返す更新列に対して成立する。

そのため、現行 rule の transaction representation としては採用してよい。

### 3.2 将来の rule 変更時は transaction version を分ける

将来、

- weight-dependent learning rate
- multiplicative plasticity
- synapse creation / deletion
- metaplasticity

などを導入した場合、この `(shift, lo, hi)` 表現はそのまま使えない。

そのため checkpoint / commit log には

```text
plasticity_rule_version
transaction_semantics_version
```

を必ず保存する。

## 4. 最初から full transaction × 多worker にしない

MaleCNS は約 25.6M edge ある。

`f32` なら 1 edge-array は概算で

```text
25.6M * 4 byte ≈ 102 MB
```

である。

worker ごとに

```text
local_weight
eligibility
transaction_shift
transaction_lo
transaction_hi
```

を全 edge 分そのまま持つと約 500 MB / worker になる。

M1 16 GB では 8 worker 程度でも edge state だけで数 GB を消費し、MuJoCo、retina、WGPU buffer、Python/Rust process、OS unified memory と競合する。

したがって最初の実装は **2 worker に限定**する。

まず実測するもの:

```text
1 episode 内で d != 0 になる edge 数
1 episode 内で weight が実際に変わる edge 数
eligibility が非zeroになる edge 数
DAN modulation が到達する postsynaptic neuron / edge 数
```

これが十分疎いなら transaction は sparse representation にする。

例えば:

```text
changed_edge_ids[]
shift[]
lo[]
hi[]
```

だけを commit payload とする。

一方で local weight と eligibility は episode 中の dynamics に影響するため、単純に削除してはならない。

## 5. 最初の prototype は単純な構成を優先する

最短で動かすなら、最初から Rust orchestrator へ全面移行する必要はない。

最初は既存 Python trainer を拡張して

```text
2 MuJoCo/FlyBody instances
2 episode-local CNS states
1 shared GPU topology
1 shared GlobalWeightStore
1 commit coordinator
```

を作る方がよい。

まず意味と性能を確認し、その後 profile で Python scheduling / GIL / IPC が支配的と判明した場合だけ Rust scheduler へ移す。

推奨順序:

```text
Phase 1
Python orchestrator
2 workers
GPU batched CNS
MuJoCo は最初は単純実装

Phase 2
worker 数を増やす
CPU physics / retina / peripheral を並列化

Phase 3
Python が bottleneck の場合のみ Rust scheduler 化
```

目的は scheduler を作ることではなく、Flyppy の経験生成量を増やすことである。

## 6. GPU batching は優先度が高い

現在の 1 fly ごとの

```text
GPU submit
→ wait/readback
→ CPU physics
→ next submit
```

を複数回行うより、active worker をまとめて

```text
batched sensory current
→ batched propagation
→ batched neuron update
→ batched plasticity
→ batched trace update
→ all-worker MN gather
→ compact motor readback
```

とする構成は有望である。

GPU buffer は概念的に

```text
membrane[slot][neuron]
spikes[slot][neuron]
refractory[slot][neuron]
trace[slot][neuron]
modulation[slot][neuron]
eligibility[slot][edge]
local_weight[slot][edge]
```

を持つ。

一方、以下は 1 copy でよい。

```text
row_offsets
pre_indices
edge_posts
synapse_counts
neurotransmitter metadata
immutable topology
motor / sensory body-ID maps
```

worker が終了した場合は active mask を落とし、commit 完了後にその slot を再初期化する。

全 worker の episode 終了を待つ barrier は作らない。

## 7. CPU / MuJoCo 側は profiling してから並列方式を決める

MuJoCo body は worker ごとに独立 instance を持つ。

ただし、最初から

```text
Python multiprocessing
Rust threads
専用 process pool
```

のどれかへ固定しない。

2 worker prototype で以下を profile する。

```text
retina encoding time
peripheral update time
MuJoCo step time
collision/course update time
GPU submit/wait time
motor readback time
commit time
```

GPU が主ボトルネックなら CPU parallelism を複雑化しても効果が小さい。

逆に MuJoCo が主ボトルネックなら body step を並列化する。

## 8. curriculum の global distribution 化には賛成

worker ごとに独立 curriculum を持たせるより、現在の学習状態を表す共有 distribution を持つ方がよい。

例:

```text
CurriculumDistribution
  spawn_x range / distribution
  spawn_z range / distribution
  initial_vx range / distribution
  target gate stage mixture
  environment seed distribution
```

worker が episode を開始するたびに、最新版 distribution から条件を sample する。

終了 episode は rolling statistics へ追加する。

一定件数がたまったら curriculum を更新する。

重要なのは、curriculum は

```text
どの経験を与えるか
```

を決めるだけで、

```text
どう動くべきか
どの synapse をどう変えるべきか
```

を決めないことである。

## 9. curriculum 成功判定は継続飛行へ合わせて更新する

現在までの診断で、第1 gate pass だけでは飛行能力を表さないことが分かった。

過去の身体では高度回復能力が不足していても、初期高度・初速・姿勢変更で第1 gate を通過できた。

したがって今後の curriculum では単純な

```text
passed_gates > 0
```

だけではなく、stage に応じて

```text
post-gate survival
altitude maintenance / recovery
next gate reach
multi-gate continuation
```

を sampling difficulty 更新の材料にする。

これは reward そのものではない。

DAN stimulation rule と curriculum progression rule は分離する。

## 10. checkpoint は global state を中心にする

非同期 worker 全部を完全 checkpoint すると、保存量と実装複雑性が大きくなる。

最初の canonical checkpoint は以下で十分である。

```text
global weights
global weight version
commit sequence
curriculum state
sampler RNG state
code SHA
MaleCNS snapshot hash
plasticity rule version
transaction semantics version
```

checkpoint を取るとき、in-flight worker episode は checkpoint 対象にしなくてよい。

resume 時は global checkpoint から新しい worker episode を開始する。

つまり crash / restart で失うのは未commit episode だけとする。

これにより checkpoint 実装を大幅に単純化できる。

必要なら将来 exact in-flight resume を追加すればよいが、初期実装では不要である。

## 11. commit log は軽量にする

各 commit について最低限:

```text
commit_seq
worker_id
episode_id
source_weight_version
commit_weight_version
source seed / environment condition
transaction changed-edge count
transaction checksum
PAM event count
PPL1 event count
behavior summary
wall-clock episode duration
simulated biological duration
```

を記録する。

transaction payload 全体を毎回永続ログへ保存する必要はない。

checkpoint 間の完全 replay が必要になった場合のみ optional full transaction log を有効にする。

## 12. staleness は記録するが、最初から研究課題にしない

非同期 worker では

```text
source_weight_version != commit 時の global version
```

になることがある。

これは設計上当然なので、

```text
source_weight_version
commit_weight_version
version_staleness
```

を記録する。

ただし最初から

```text
population 1 / 2 / 4 / 8 の学習曲線比較
staleness 理論研究
serial learner との統計比較
```

を行う必要はない。

まず 2 worker で正常に学習が進むことを確認する。

もし worker 数を増やしたときに

- 学習が急に崩れる
- weight が極端に飽和する
- curriculum が不安定になる
- throughput が逆に落ちる

などの実害が出た場合にだけ、staleness cap や worker 数調整を入れる。

## 13. `population=1` は研究比較用ではなく回帰テスト用に残す

既存 serial trainer は捨てず、最小の回帰確認にだけ使う。

必要な確認は例えば:

```text
population=1 の新 trainer が旧 trainer と同じ update semantics を持つ
small fixture で CPU/GPU が一致する
transaction summary が step-by-step clamp 更新と一致する
stale worker の final weight が global を上書きしない
weight averaging が存在しない
checkpoint resume で global weight が壊れない
```

これらが通ればよい。

並列化あり／なしの差そのものを研究テーマにしない。

## 14. control experiments は並列基盤の実装条件にしない

元文書では P6 に control learners が置かれているが、並列基盤完成の条件としては不要である。

並列学習基盤の役割は

```text
大量の Flyppy experience を正しい神経・身体経路で高速に生成し、
その可塑性を shared learned state に反映する
```

ことに限定する。

control experiment が必要な研究を行う場合は、その時点で同じ trainer を別 condition で起動すればよい。

したがって P6 は immediate roadmap から外して構わない。

## 15. 推奨する実装順

### P0: transaction 単体テスト

実装前に小さい synthetic edge set で

```text
step-by-step additive + clamp
```

と

```text
shift / lo / hi transaction
```

が完全一致することをテストする。

### P1: 2-worker Python prototype

- 共有 topology
- worker-local CNS / body state
- worker-local weight / eligibility
- global weight store
- serialized commit coordinator
- episode 完了後の即時 restart

を実装する。

この段階では最適化しすぎない。

### P2: GPU batched CNS

2 worker の neural step を 1 batched dispatch へまとめる。

MN readback も worker ごとではなく 1 compact readback にする。

### P3: transaction memory 最適化

実際の changed-edge density を測り、

```text
dense transaction
sparse transaction
```

のどちらが速いか決める。

### P4: worker 数増加

M1 16 GB の unified memory と throughput を見ながら

```text
2 -> 4 -> 8
```

と増やす。

「比較研究」ではなく、単に最も速く安定して動く worker 数を選ぶ。

### P5: CPU body parallelism

profile 上 MuJoCo / retina / periphery が bottleneck なら並列化する。

### P6: scheduler 再実装は必要な場合のみ

Python が明確な bottleneck の場合だけ Rust scheduler / orchestrator へ移す。

## 16. acceptance criteria

新方式を canonical trainer にする最低条件は以下で十分である。

1. 複数 worker が同時に episode を進められる。
2. topology は共有され、worker-local dynamic state は混線しない。
3. worker の final weight で global を上書きしない。
4. weight averaging を行わない。
5. plasticity transaction が現行 rule の更新を正しく表現する。
6. commit は serialized される。
7. commit 後、その worker は最新 global weight から再開する。
8. CNS→MN→muscle→FlyBody の正規経路を変えない。
9. PAM/PPL1 stimulation semantics を変えない。
10. curriculum は synapse / motor command を直接操作しない。
11. checkpoint / resume で global learned state を保持できる。
12. 既存 serial trainer より wall-clock あたりの experience throughput が明確に増える。

最後の 12 はベンチマークで確認すればよく、並列化手法そのものを研究する必要はない。

## 17. 最終評価

元の再設計案は、方向としてはかなり良い。

特に

```text
asynchronous shared weight
+ episode-local worker state
+ no averaging
+ plasticity transaction commit
+ GPU batching
+ global curriculum distribution
```

という中核は維持するべきである。

変更した方がよいのは次の点である。

```text
1. serial vs parallel の詳細比較を研究課題にしない
2. 最初から Rust scheduler を作らない
3. まず 2-worker prototype を作る
4. transaction の changed-edge density を測ってから sparse/dense を決める
5. checkpoint は global state 中心に単純化する
6. control experiments を parallel trainer 完成条件から外す
7. profiling 後に CPU/GPU の次の最適化先を決める
```

この形なら、`virtual-fly` の本筋を変えずに、現在の直列 trainer よりかなり多くの Flyppy experience を同じ時間で流せる可能性が高い。

実装上の最優先は、理論比較ではなく **2 worker で shared-weight transaction training を実際に通すこと**である。
