# Flyppy並列学習アーキテクチャ再設計案レビュー

Date: 2026-09-15  
対象: `docs/20260915_flyppy学習アーキテクチャ再設計案.md`  
Status: **全面改稿 / 最速学習優先**

## 1. 結論

元案の **episode 終了時に worker-local plasticity transaction を global weight へ commit する方式は、実装可能ではあるが、最速学習を狙う構成としては採用しない方がよい。**

`virtual-fly` で今必要なのは、並列学習方式そのものを研究することではない。

目的は一つである。

> 現在の感覚 → MaleCNS → 個別運動ニューロン → 筋肉 → FlyBody/MuJoCo → 環境 → DAN刺激 → 局所可塑性という経路を維持したまま、利用可能なCPU/GPU資源を使って、学習状態をできるだけ短いwall-clock timeで前進させる。

この目的に対して、現時点で第一候補にすべき構成は次である。

```text
複数 Fly slot を常時並列実行
        ↓
全 slot の sensory current を一括作成
        ↓
GPU で whole MaleCNS を slot 次元つきで batched step
        ↓
各 slot の局所 eligibility / modulation から plasticity increment を計算
        ↓
同一 neural step 内で全 slot の更新を shared global weight に集約
        ↓
次 neural step では全 slot が更新済み shared weight を使用
        ↓
MN spike だけ compact readback
        ↓
CPU で各 FlyBody / MuJoCo を並列更新
        ↓
終了した slot は即座に reset して次 episode を開始
```

つまり本命は、

**batched multi-fly + step-synchronous shared-weight plasticity + CPU/GPU pipeline**

である。

episode単位のtransaction commitではなく、**neural step単位でshared weightへ可塑性を反映する**。

これにより、episode-end方式に存在する

- 長いepisodeの終了待ち
- stale weightでの長時間経験生成
- workerごとのfull local weight
- episode transactionの巨大な蓄積
- commit coordinatorの複雑性

を大幅に減らせる。

元案は「安全に非同期化する案」としてはよいが、最速化の中心設計としては一段遠回りである。

## 2. 変更しない生物学的・物理的経路

高速化のために学習内容そのものを別物へ置き換えてはいけない。

維持する正規経路は以下である。

```text
Flyppy physical world
→ FlyBody compound eye
→ released MaleCNS R1-R6 body-ID current
→ whole MaleCNS neural dynamics
→ individual released wing motor-neuron spikes
→ WingMusclePeriphery
→ anatomical / identified muscle activation
→ FlyBodyMuscleAdapter
→ FlyBody / MuJoCo
→ physical consequences
→ gate / collision event
→ PAM / PPL1 stimulation
→ local neuromodulated plasticity
```

禁止事項も変えない。

```text
外部 action decoder
Q-learning
policy gradient
backpropagation
外部NN controller
Flappy攻略ロジック
scalar rewardを直接weightへ渡す処理
```

今回変えるのは、上記の計算を「1匹ずつ直列に行うか」「複数slotを同じGPU dispatchで進めるか」という計算配置である。

## 3. なぜepisode-end transaction方式よりstep共有方式を優先するのか

元案では各workerがepisode開始時にglobal weightをコピーし、その後はepisode終了まで独立したlocal weightで走る。

```text
W0
├─ worker A: 長い episode → TA
├─ worker B: episode → TB
└─ worker C: episode → TC

終了順に TB, TC, TA を global へ commit
```

この方式ではworker Aが長時間走っている間にglobal weightが更新されても、Aは古いweightを使い続ける。

さらにworkerごとに、少なくとも

```text
local weight
eligibility
transaction state
```

を大量に持つ必要がある。

MaleCNSが約25.6M edgeなら、`f32` 1配列だけで約102 MBである。

したがってfull-sizeで

```text
local_weight
eligibility
transaction_shift
transaction_lo
transaction_hi
```

を持てば約500 MB / workerになる。

これはM1 16 GBでworker数を増やす際に明確な制約になる。

一方、step-synchronous shared-weight方式ではweightは1 copyでよい。

```text
shared global weight              1 copy
eligibility[slot][edge]           slotごと
membrane[slot][neuron]            slotごと
spikes[slot][neuron]              slotごと
trace[slot][neuron]               slotごと
modulation[slot][neuron]          slotごと
refractory[slot][neuron]          slotごと
body / retina / peripheral state  slotごと
```

25.6M edgeで最も大きいslot-local配列はまずeligibilityになる。

8 slotでもeligibilityは概算約820 MBであり、episode-end方式でfull local weightとtransactionを複製するよりかなり軽い。

## 4. GPU上の正規1 step

現行plasticityは概ね次である。

```text
eligibility <- eligibility_decay * eligibility + local_activity_term
weight <- clamp(
    weight + learning_rate * modulation * eligibility,
    0,
    weight_max
)
```

並列版では、1 neural step を次の順序にする。

```text
1. 全slotが同じ W(t) を使ってsynaptic propagation
2. slotごとにmembrane / spike / refractoryを更新
3. slotごとにmodulationを更新
4. slotごと・edgeごとにeligibilityを更新
5. slotごと・edgeごとに plasticity increment d(slot, edge) を計算
6. edgeごとに全slotの d を shared W へ反映
7. W(t+1) を確定
8. traceを更新
9. 必要なMN spikeのみreadback
```

重要なのは、**全slotの学習結果を次のneural stepまでにshared weightへ反映する**ことである。

これにより、episode単位のstalenessを持たない。

## 5. plasticity increment の集約

各slot `s`、edge `e` について

```text
d[s,e] = learning_rate * modulation[s,post(e)] * eligibility[s,e]
```

を得る。

最も単純な実装は、edge-major kernelで1 edgeを担当するthread/work itemがactive slotを順に処理する方式である。

```text
w = global_weight[e]

for s in deterministic_active_slot_order:
    w = clamp(w + d[s,e], 0, weight_max)

global_weight[e] = w
```

現行ruleでは `d` 自体はweightへ乗算依存していないため、この構成と相性がよい。

`sum(d)` を一度だけ加算する実装も高速候補だが、正負更新が混在して途中でclampへ当たる場合、逐次clampと結果が異なる。

したがって初期実装では、**同一kernel内でslot順にclamp付き更新を適用する**。

slot数が小さい間はこのloopのコストより、local weight複製・transaction保存・episode commitを消せる利点の方が大きい可能性が高い。

slot orderは固定して再現性を持たせる。特定slotが常にclamp時の後段になることが問題化した場合のみ、control tickごとのdeterministic rotationを入れる。

これは並列化研究のためではなく、実装上の偏りを避けるための処理である。

## 6. transaction system はcanonical pathから外す

元案の

```text
PlasticityTransaction
GlobalWeightStore version
source_weight_version
commit_weight_version
staleness
shift / lo / hi
```

という仕組みは、canonical最速pathには不要になる。

shared weightはneural stepごとに直接更新されるため、episode終了時のweight transaction自体が存在しない。

checkpointに必要なのは基本的に

```text
global weights
curriculum state
sampler state
training counters
code SHA
MaleCNS source hash
plasticity rule/version
```

でよい。

workerのepisode終了時はweight commitではなく、単にそのslotの短期状態をresetし、次のenvironment conditionをsampleして再利用する。

これによりcontrol planeもかなり単純になる。

## 7. episode境界はGPU並列性を止めない

全slotが同時にepisodeを終了する必要はない。

各slotに

```text
active
needs_reset
episode_id
step_in_episode
```

程度の状態を持たせる。

例えばslot 2が衝突したら、他slotを止めず、slot 2だけ次のcontrol boundaryでresetする。

```text
slot 0: episode継続
slot 1: episode継続
slot 2: collision -> reset -> 新episode
slot 3: episode継続
```

GPUから見れば常に同じslot dimensionを処理できる。

episode長の差によるbarrierを作らない。

## 8. curriculumもslot生成器として扱う

curriculumはglobal experience distributionとして持つ。

各slotがresetされるたびに、最新版のdistributionから新しい初期条件をsampleする。

```text
spawn_x
spawn_z
initial_vx
gate stage
environment seed
その他のenvironment condition
```

終了episodeの成績はrolling statisticsへ追加する。

十分な件数がたまった時だけdistributionを更新する。

curriculumは

```text
何を経験させるか
```

だけを決める。

CNSへactionやweight deltaを与えてはならない。

## 9. CPU側はFlyBody/MuJoCoを並列化する

GPUでMaleCNSをbatched化しても、CPU側の身体計算が直列ならそこで詰まる。

各slotは独立した

```text
FlyBody / MuJoCo state
retina adaptation
WingMusclePeriphery state
course state
```

を持つ。

control tickごとに各slotの

```text
retina readout / sensory encoding
peripheral update
MuJoCo stepping
collision / gate event
```

をCPUで並列実行する。

最終的な実行器は、PythonのGILやprocess間IPCが支配的になった時点でRust schedulerへ移す。

ただし最初からscheduler全面書き換えを先に行わない。

先にbatched GPU pathを作り、profile上CPU orchestrationがボトルネックになった時だけRustへ移す。

## 10. CPU/GPU pipelineを二重化する

最終的にはCPUとGPUを交互に待たせない。

概念的にはdouble-bufferする。

```text
時刻 n:
  GPU: batch A の MaleCNS step
  CPU: batch B の body / retina / periphery

時刻 n+1:
  GPU: batch B の MaleCNS step
  CPU: batch A の body / retina / periphery
```

実際には全slotが同じcontrol tickを進むので、sensory buffer / motor readback bufferをping-pongさせる。

WGPU map/readback待ちをcritical pathへ毎回直列に挿入しない。

MN出力は全CNSをCPUへ戻さず、必要な個別wing motor neuronだけGPU側でgatherしてcompact bufferにする。

viewer / telemetry / checkpoint IOもtraining critical pathから外す。

## 11. worker数は研究せず自動調整する

`population=1,2,4,8...` の学習曲線を研究する必要はない。

必要なのは、そのマシンで最も速く回るslot数を決めることだけである。

起動時または明示的なcalibration commandで短時間benchmarkを行う。

測る値は例えば

```text
control steps / second
neural steps / second
simulated biological seconds / wall-clock second
GPU utilization
CPU utilization
peak unified memory
```

でよい。

候補slot数を短時間だけ走らせ、最も高いthroughputを出す値を採用する。

これはparallel learningの研究ではなく、BLASやthread poolのthread数を決めるのと同じ実行時最適化である。

M1 16 GBなら最初の候補は

```text
2, 4, 6, 8
```

程度で十分である。

RTX 4070 12 GB等の別GPUでは別の最適値になってよい。

## 12. さらに速くする次の候補

step-synchronous batched pathを作った後、profileに従って追加最適化する。

優先度が高い順に見るべきなのは次である。

```text
A. propagation / neuron update / plasticity / trace のkernel fusion
B. GPU submit回数削減
C. MN gather以外のreadback削減
D. CPU/GPU double buffering
E. MuJoCo / retina / periphery のparallel execution
F. eligibilityが実際に疎い場合のactive/plastic edge subset化
G. activityが十分疎い場合のevent-driven / active-frontier実行
H. checkpoint / report / viewer IOの完全非同期化
```

特にFとGは、実測で疎性が確認できた場合だけ行う。

科学的意味を変えて高速化するのではなく、同じ計算をしなくてよい場所だけ省く。

## 13. hae.satoru.netから参考にする高速化

`hae.satoru.net` のwhole-brain LIF実装では、次の入力までにthresholdへ到達不能なニューロンを逐次stepせず、event-drivenに飛ばすことで大幅に高速化している。

参考:

- https://github.com/satorunet/hae
- https://github.com/satorunet/hae/tree/main/flybrain
- https://hae.satoru.net/tech/?lang=en

`virtual-fly` のMaleCNSで同じ方式がそのまま有利とは限らない。現在はGPUで大規模疎グラフを並列処理しているため、active-frontier管理のoverheadとの比較になる。

したがってこれはbatched GPU path完成後のprofile-driven optimization候補とする。

## 14. 回帰テストは必要だが、並列化比較研究はしない

必要なのは実装が壊れていないことの確認だけである。

最低限、small deterministic fixtureで

```text
slot dimensionなしのreference step
slot dimensionありでactive slot = 1のstep
```

が一致することを確認する。

また、shared plasticity kernelについて

```text
手計算できる小さなedge fixture
2〜4 slotの既知 d 値
clamp境界を含むケース
```

をテストする。

ここで必要なのは数値実装テストであって、

```text
serial fly と parallel fly の長期学習曲線比較
population数別の研究
staleness研究
```

ではない。

`virtual-fly` の時間を並列化手法の研究に消費しない。

## 15. 実装順

### P0: 現在のsingle-fly bottleneckを計測

既存trainerで1control tickあたりの時間を

```text
retina
GPU neural propagation
GPU plasticity
GPU readback
periphery
MuJoCo
course/event
logging
```

に分ける。

これは方式比較の研究ではなく、どこを並列化すると効くかを決めるためのprofileである。

### P1: GPU runtimeへslot dimensionを追加

immutable topologyは1 copyのまま、

```text
membrane[slot][neuron]
spikes[slot][neuron]
refractory[slot][neuron]
trace[slot][neuron]
modulation[slot][neuron]
eligibility[slot][edge]
```

を導入する。

weightはこの段階からshared 1 copyとする。

### P2: batched propagation / neuron step

全active slotを1 dispatch系で処理する。

CPUからslotごとにsubmitして待つ構成にはしない。

### P3: shared plasticity reduction kernel

各slotのeligibility / modulationから `d[s,e]` を生成し、edge単位でshared weightへ反映する。

最初はdeterministic slot order + sequential clampでよい。

### P4: multi-FlyBody slot化

複数のFlyBody/MuJoCo/retina/peripheryを常駐させる。

episode終了slotだけ即resetする。

### P5: CPU parallel body stepping

profileに応じてthread pool / process / Rust workerを選ぶ。

### P6: CPU/GPU double buffer

sensory / motor bufferをping-pongし、CPUとGPUの待ちを隠す。

### P7: startup autotuner

候補slot数を短時間benchmarkして、その実行環境で最大throughputとなる値を自動選択する。

### P8: profile-driven second-stage optimization

必要ならkernel fusion、active plastic edge、event-driven化などへ進む。

## 16. acceptance criteria

新しいparallel trainerを完成とみなす条件は、研究的なpopulation比較ではなく次で十分である。

```text
1. canonical sensory → CNS → MN → muscle → physics → DAN → plasticity 経路を維持
2. 外部policy / action decoder / scalar reward weight updateを導入していない
3. MaleCNS topologyは1 copyのimmutable sourceとして共有
4. neural/body short-term stateはslotごとに独立
5. learned weightはshared 1 copy
6. 毎neural stepで全slotの局所plasticityがshared weightへ反映
7. episode終了による全slot barrierがない
8. MN以外の大規模readbackを行わない
9. active slot = 1のsmall fixtureがreference runtimeと一致
10. shared plasticity kernelのclamp fixtureが正しい
11. single-fly trainerよりwall-clockあたりの経験生成量が実際に増える
12. checkpoint/resumeでshared learned stateを継続できる
```

11は当然必要だが、長期の学習曲線比較研究を要求しているわけではない。単純に高速化した実装が本当に高速であることを確認するだけである。

## 17. 元案から残すもの / 捨てるもの

元案からそのまま残してよいのは、

```text
複数FlyBodyを同時実行する
immutable topologyを共有する
worker-localな身体・神経短期状態を持つ
curriculumをglobal experience distributionとして扱う
GPU batchingを行う
終了したepisodeを他workerに待たせない
trainingとviewer/telemetryを分離する
```

である。

一方、最速pathでは次をcanonical設計から外す。

```text
episode-local full weight copy
episode終了時PlasticityTransaction
source_weight_version / commit_weight_version中心の制御
stale transaction rebase
episode commit coordinator
full transaction log
population別の長期比較研究
```

これらはepisode-end async方式を採る場合には必要だったが、neural-step shared-weight方式では大半が不要になる。

## 18. 最終提案

`virtual-fly` のFlyppy学習基盤は、次を最終目標として実装する。

```text
                   ┌──────────────────────────┐
                   │ shared MaleCNS topology  │
                   │ shared learned weights W │
                   └────────────┬─────────────┘
                                │
             ┌──────────────────┼──────────────────┐
             │                  │                  │
         Fly slot 0         Fly slot 1         Fly slot N
       local dynamics      local dynamics      local dynamics
       local eligibility   local eligibility   local eligibility
       local body          local body          local body
             │                  │                  │
             └──────── sensory / neural batch ─────┘
                                │
                                v
                      GPU whole-CNS batched step
                                │
                                v
                  per-slot local plasticity increment
                                │
                                v
                     shared weight update every step
                                │
                                v
                        compact MN readback
                                │
             ┌──────────────────┼──────────────────┐
             │                  │                  │
        CPU body step      CPU body step      CPU body step
             │                  │                  │
             └──── finished slotだけ即reset ──────┘
```

この構成なら、複数episodeからの経験生成量を増やしながら、学習結果をepisode終了まで寝かせず、次のneural stepから全slotへ反映できる。

また、weightをworkerごとに複製しないため、M1 16 GBでもslot数を増やしやすい。

したがって、**元文書のepisode-end async transaction方式をそのまま実装するより、最初からこのstep-synchronous shared-weight batched architectureへ寄せることを推奨する。**

最適slot数やkernel構成は短い自動benchmarkで決めればよく、それ自体を研究テーマにする必要はない。
