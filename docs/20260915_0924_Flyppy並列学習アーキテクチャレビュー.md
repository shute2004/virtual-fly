## 1. この文書の目的

この文書では、Flyppy の並列化方式そのものを研究対象にはしない。

目的は一つだけである。

> **`virtual-fly` の生物学的な感覚→CNS→運動→身体→環境→神経修飾→局所可塑性という因果経路を維持したまま、良い学習状態へ到達する wall-clock time を可能な限り短くする。**

したがって、評価軸は「並列方式として美しいか」「serial と parallel の差が研究上興味深いか」ではない。

主評価軸は次である。

```text
wall-clock time to useful learned checkpoint
```

補助指標としてのみ、

```text
simulated biological seconds / wall-clock second
control steps / second
neural steps / second
episodes / hour
GPU utilization
CPU utilization
memory bandwidth
unified-memory usage
```

を見る。

この文書は、以前のレビューで推した

```text
batched multi-fly
+ step-synchronous shared-weight plasticity
+ CPU/GPU pipeline
```

だけでは不十分だと再評価した結果である。

**複数 Fly を載せる前に、現在 1 Fly あたり毎 neural step で行っている巨大な全 edge 走査と、CPU↔Rust↔GPU の同期コストを減らす方が先に効く可能性が高い。**

現在の最有力候補は、以下を統合した構成である。

```text
Hybrid sparse/dense neural engine
+ event-driven edge traversal
+ sparse plasticity working set
+ shared learned weights
+ vectorized multi-fly slots
+ compact persistent I/O
+ CPU/GPU microbatch pipeline
+ runtime autotuning
```

以下、この案をレビュー可能な形で具体化する。

## 2. 現在の実装で最も重い可能性が高い箇所

対象コード:

- `crates/vf-neural/src/gpu30.rs`
- `crates/vf-neural/src/neural.wgsl`
- `scripts/embodiment/neural_bridge_client.py`
- `scripts/embodiment/train_flyppy_curriculum.py`

### 2.1 neural step ごとに全 edge を読む

現在の `neuron_step` は post neuron ごとに incoming edge を走査する。

概念的には:

```text
for post in all_neurons:
    for edge in incoming(post):
        if pre fired:
            accumulate current
```

である。

つまり、実際に発火している neuron が少数でも、全 post の全 incoming edge を読む。

MaleCNS が約 25.6M edge なら、1 neural step ごとにほぼ全 edge を調べることになる。

### 2.2 plasticity も毎 step 全 edge dispatch

現在の `plasticity_step` も全 edge を dispatch する。

```text
eligibility <- decay * eligibility + local
weight <- clamp(weight + learning_rate * modulation * eligibility,
                0,
                weight_max)
```

`local == 0`、`modulation == 0` の edge も、dispatch と edge state access の対象になる。

多くの時間帯で neural activity / DAN modulation / eligibility が疎なら、ここは大きな無駄になる。

### 2.3 external current は dense buffer を毎 step upload

`GpuRuntime::step()` は毎回 CPU 側の `external_cpu` 全体を 0 で埋め、刺激 neuron を書き、その neuron-count 全体の buffer を GPU へ upload する。

現在の retinal input は body-ID と current の疎な組で得られるため、入力まで dense upload する必要はない。

### 2.4 motor spike readback が control step ごとに allocation + blocking map

現在の `read_spikes_at()` は呼び出しごとに概ね:

```text
index buffer create
output buffer create
staging buffer create
bind group create
compute gather submit
copy to staging
map_async
device.poll(wait)
CPU read
```

を行う。

Flyppy は毎 control step で wing/body motor neuron を読むため、この固定 overhead は小さくない可能性がある。

固定 motor body-ID 群に対して毎回 buffer / bind group を作り直す必要はない。

### 2.5 Python↔Rust subprocess JSON round-trip が毎 control step にある

`NeuralBridgeClient.step_with_body_readout()` は JSON を stdin に書き、Rust subprocess の返答を同期的に待つ。

現在の control loop は:

```text
Python retina
 -> JSON serialize
 -> pipe
 -> Rust
 -> GPU
 -> blocking selected-spike readback
 -> JSON response
 -> pipe
 -> Python
 -> periphery
 -> MuJoCo
```

である。

GPU kernel だけを高速化しても、この同期経路が残れば ceiling になる可能性が高い。

## 3. 結論: まず multi-fly ではなく「1 Fly あたりの edge work」を減らす

単純な multi-fly batching だけなら、全 edge 走査をそのまま slot 数だけ増やす。

概念的には:

```text
現在:
O(E) / neural step

単純 N-fly batching:
O(N * E) / neural step
```

GPU occupancy は改善しても、Apple M1 のような unified-memory GPU では早い段階で memory bandwidth が律速になる可能性がある。

したがって推奨順序は:

```text
1. 1 Fly の不要 edge access を減らす
2. per-step CPU↔GPU / Python↔Rust 同期を減らす
3. その軽量 runtime を multi-fly 化する
4. CPU physics と GPU CNS を pipeline 化する
```

である。

## 4. 最有力 neural engine: candidate-post sparse propagation + dense fallback

完全な event queue simulatorへ一気に作り直す必要はない。

現在の synchronous discrete-step semantics を保ったまま、**edge traversal だけを activity-driven にする**方が実装リスクと速度のバランスがよい。

### 4.1 outgoing CSR を追加する

現在の主要表現は post 側から incoming edge を引くための CSR である。

これに加えて、同じ edge ID を使った outgoing CSR を生成する。

```text
incoming:
post -> edge IDs / pre

outgoing:
pre -> edge IDs / post
```

source snapshot 自体は変更しない。

これは runtime index を追加するだけである。

### 4.2 active presynaptic neuron から candidate post を mark

前 step の spike/event が 0 でない presynaptic neuron だけ outgoing edge をたどる。

```text
for pre in neurons:
    if spikes_prev[pre] != 0:
        for edge in outgoing(pre):
            candidate_post[post(edge)] = 1
```

candidate は bitset でよい。

同時に、external retinal current が入る post も candidate にする。

Dopamine neuron が発火した場合も、その outgoing target を candidate にする。

### 4.3 candidate post だけ incoming edge を本走査する

candidate post に対してのみ、現在と同じ incoming CSR の順番で edge を走査する。

```text
for post in all_neurons:
    if !candidate_post[post]:
        edge scan をしない
    else:
        現在と同じ incoming edge 順で current を積算
```

ここで重要なのは、**active pre から直接 float scatter-add しない**ことである。

WebGPU/WGSL では portable な native `atomic<f32>` を前提にしにくく、float atomic scatter は競合・実装差・数値順序の問題を持つ。

candidate-post 方式なら:

- candidate の mark は integer bitset atomic OR でよい
- 実際の電流和は従来と同じ incoming edge order で計算できる
- dense reference と数値的一致を維持しやすい

という利点がある。

### 4.4 neuron state 自体は全 neuron 更新でもよい

166k neuron の軽い state update は 25.6M edge scan より遥かに小さい。

したがって最初から membrane / trace / modulation まで完全 event-driven 化する必要はない。

まずは:

```text
all neurons:
  membrane decay
  modulation decay
  refractory update

candidate posts only:
  expensive incoming edge scan
```

でよい。

trace は plasticity が old trace を使った後に現在どおり separate pass で更新してもよい。

これにより、複雑な timestamp / lazy-neuron semantics を導入せず edge bandwidth だけ先に削減できる。

## 5. plasticity は「全 edge」ではなく active eligibility working set を更新する

propagation より plasticity の方がさらに最適化余地が大きい。

現行 local term は:

```text
local = trace[pre] * post_event
      - trace[post] * pre_event
```

である。

したがって `local != 0` になり得る edge は、少なくとも:

```text
pre_event != 0 の neuron から出る edge
または
post_event != 0 の neuron に入る edge
```

だけである。

### 5.1 local term を2パスで加える

float atomic を避けるため、1 edge に対する local を一度に scatter-add しない。

次の順番なら各 pass 内で同じ edge を一度しか触らない。

```text
Pass A:
active pre の outgoing edge
eligibility[edge] += -trace[post] * pre_event

Pass B:
active post の incoming edge
eligibility[edge] += +trace[pre] * post_event
```

A と B は別 dispatch とし、順に実行する。

同一 edge が pre/post 両方の event を持つ場合も、A→B で両項が入る。

### 5.2 active eligibility edge list を持つ

eligibility が一度でも非zeroになった edge を active set に入れる。

必要 state:

```text
eligibility[edge]          # dense value arrayでもよい
eligibility_active_bitset
eligibility_active_list
eligibility_active_count
```

新しい local event が edge に入るとき:

```text
if atomic test-and-set(bitset, edge) says previously inactive:
    append edge ID to active_list
```

その後の各 neural step では、全 25.6M edge ではなく active list だけに対して:

```text
eligibility *= eligibility_decay
weight += learning_rate * modulation[post] * eligibility
clamp
```

を行う。

### 5.3 episode reset も active list だけ消す

現在は episode reset 時に全 edge eligibility を GPU で 0 にする。

active list があるなら:

```text
for edge in active_list:
    eligibility[edge] = 0
clear active bits/list/count
```

だけでよい。

短い episode を多数並列実行する場合、この差は大きくなる。

### 5.4 active set が大きくなったら dense kernel に切り替える

eligibility は指数減衰するため、厳密には小さくなってもすぐ 0 にはならない。

1 episode 中に active list が大きく育つ可能性がある。

そのため sparse だけに固定しない。

```text
if active_eligibility_fraction < threshold:
    sparse plasticity kernel
else:
    dense plasticity kernel
```

とする。

threshold は理論で固定せず、起動時または初回 bootstrap 時の短い microbenchmark で決める。

## 6. runtime graph を current neural model 専用に分割する

現在の `neural.wgsl` では neurotransmitter を edge traversal 中に調べ、

```text
ACh -> +
GABA / glutamate / histamine -> -
dopamine -> modulation
その他 -> fast current 0
```

としている。

現在のモデル意味を変えず、runtime graph を事前に次へ分けられる。

```text
FastGraph
  ACh
  GABA
  glutamate
  histamine

DopamineGraph
  dopamine

IgnoredByCurrentRuntime
  current fast_sign == 0 かつ dopamine でもない edge
```

source MaleCNS snapshot は当然すべて保持する。

GPU runtime だけ、現在の方程式上 no-op の edge を毎step読む必要はない。

また FastGraph edge に:

```text
pre
post
count
fast_sign
```

を事前符号化すれば、hot loop 中の transmitter metadata random lookup と branch を減らせる。

DopamineGraph は weight / eligibility を持つ必要がない。

これは current model に対して意味保存型の compile step として実装できる。

## 7. external current は compact upload にする

現在の retina は最終的に:

```text
(body_id, current)
```

の組を返す。

これを neuron-count 長の dense CPU array に展開して毎step uploadする必要はない。

推奨:

```text
StimulusEntry {
    neuron_index
    current
}
```

の compact buffer を upload する。

GPU 側では:

1. 前 step で touched だった external-current entry だけ clear
2. current stimulus entries を書く
3. 同時に candidate_post bit を立てる

とする。

重複 neuron ID があり得る場合は CPU 側で small-map merge するか、GPU 側で決定論的 reduction を行う。

## 8. motor readback は persistent preallocated ring にする

Flyppy training では motor neuron body-ID 群はほぼ固定である。

したがって control step ごとに:

```text
index buffer
output buffer
staging buffer
bind group
```

を新規作成してはいけない。

初期化時に:

```text
motor_index_buffer
motor_output_buffer[ring]
mapped/staging buffers[ring]
fixed bind groups
```

を作る。

### 8.1 可能なら blocking map を control critical path から外す

理想は 2～3 個の readback slot を ring にし、GPU が slot A を書いている間に CPU が slot B を読む。

ただし body physics は現在 step t の motor output を必要とするため、完全に1step遅らせてよいかは運動意味を変える。

したがって最初は:

- allocationをなくす
- copy sizeを motor ID 数まで最小化
- map buffer を再利用する

だけでもよい。

もし direct Metal backend を作るなら、Apple unified memory の shared buffer を使って compact motor output の staging copy 自体を減らせる可能性がある。

## 9. Python↔Rust JSON bridge は canonical fast path から外す

per-control-step JSON subprocess round-trip は、高速化後の neural kernel に対して固定 overhead になる。

最終的な fast path は次のどちらかにする。

### 案A: PyO3 / native extension

Python の FlyBody / MuJoCo orchestration は残し、Rust neural runtime を同一 process にロードする。

```text
Python
  retina result
    -> direct native call
Rust neural runtime
  -> compact motor result
Python
  MuJoCo
```

JSON serialize / pipe / subprocess context switch を消せる。

### 案B: Rust orchestrator

FlyBody / MuJoCo の hot control loop まで Rust/C API 側へ持っていく。

これは最終到達性能は高い可能性があるが、実装コストが大きい。

**最初は案Aを優先する。**

PyO3 が ceiling になったことが profile で確認された場合だけ案Bへ進む。

## 10. ここまで軽量化した後で multi-fly shared-weight 化する

1 Fly runtime が軽くなった後、複数 Fly slot を載せる。

### 10.1 shared state

```text
immutable MaleCNS topology/indexes
FastGraph / DopamineGraph
learned weight[fast_edge]
neural model constants
motor/sensory maps
curriculum distribution
```

### 10.2 slot-local state

```text
membrane[slot][neuron]
trace[slot][neuron]
modulation[slot][neuron]
refractory[slot][neuron]
spikes_prev/next[slot]
external stimulus working set[slot]
eligibility[slot][fast_edge]
eligibility active bitset/list[slot]
FlyBody / MuJoCo state[slot]
retina adaptation[slot]
peripheral muscle state[slot]
episode/environment state[slot]
```

weight は slot ごとに複製しない。

これが episode-local weight copy 方式より memory と同期の両面で有利である。

## 11. shared weight 更新 semantics

各 slot はそれぞれ独立した neural / eligibility state を持つが、weight は共有する。

1 neural step の順序を明示的に固定する。

```text
1. 全 active slot が同じ step-start weight を読む
2. 各 slot の neuron dynamics を計算
3. 各 slot の eligibility/local plasticity state を更新
4. slot 0, 1, 2, ... の順に shared weight へ local plasticity を適用
5. 次 neural step へ進む
```

これなら current step の途中で、早く実行された slot の weight update が別 slot の同 step propagation に混ざらない。

shared update は GPU 上で slot 順に dispatch すれば race がない。

active eligibility list を使えば、各 slot の weight update work は:

```text
O(active plastic edges in that slot)
```

で済む。

### 11.1 「sumして一度clamp」ではなく slot-order apply を初期仕様とする

複数 slot の delta を単純に加算して最後に1回だけ clamp すると、正負deltaが混ざる場合に逐次clampと結果が変わる。

したがって初期仕様は deterministic slot order で:

```text
W <- clamp(W + d_slot0)
W <- clamp(W + d_slot1)
...
```

とする。

後に reduction 方式の方が速く、かつ結果差を許容する設計変更を行うなら別途明示する。

## 12. reinforcement の追加 neural steps を scheduler が扱う

現在、gate pass / collision 後の DAN stimulation は複数 neural steps を追加で進める。

multi-fly ではある slot だけ reinforcement substeps を必要とする場合がある。

単純 lockstep で全 slot を待たせると throughput を落とす。

推奨は:

```text
ready-normal slots
reinforcement-substep slots
reset slots
```

を scheduler が active mask で管理し、同種の処理を microbatch する。

ただし reinforcement event が十分稀なら、最初は全slot同期でもよい。

profile でここが目立った時だけ scheduler を複雑化する。

## 13. CPU / GPU microbatch pipeline

multi-fly 化後は、slot を2つ以上の microbatch に分ける。

概念:

```text
時刻 t
GPU: batch A CNS
CPU: batch B retina/periphery/MuJoCo

時刻 t+1
GPU: batch B CNS
CPU: batch A retina/periphery/MuJoCo
```

これにより CPU physics と GPU neural compute の待ち時間を重ねる。

ただし FlyBody vision が同じ GPU resource を強く使っている場合、実際には GPU-GPU contention になり得る。

そのため pipeline は必ず timestamp/profile を見て有効化する。

## 14. MuJoCo worker は model 共有 + data 分離を優先する

同じ body/course topology を使う slot なら、可能な範囲で:

```text
1 compiled mjModel
N mjData
```

を使い、workerごとに model 全体を複製しない。

各 `mjData` は別 thread に割り当てる。

Python layer が GIL / wrapper overhead で律速する場合は、MuJoCo C API を Rust/C scheduler から直接回す構成へ移す。

ただし vision / FlyBody helper との統合コストがあるため、これは profile 後の段階とする。

## 15. sparse/dense hybrid は neural activity に応じて自動切替する

sparse kernel は活動が疎いほど有利だが、CNS が広範囲に活性化すると:

- outgoing traversal
- bitset marking
- active-list management

の overhead が dense scan より高くなる。

したがって runtime は最低限:

```text
DensePropagation
SparseCandidatePropagation

DensePlasticity
SparseActiveEligibilityPlasticity
```

を持つ。

切替候補指標:

```text
active presynaptic neuron fraction
candidate post fraction
active eligibility edge fraction
```

threshold は固定値を手で決めず、実機 microbenchmark で求める。

これは並列化手法の研究ではなく、BLAS が matrix size に応じて kernel を選ぶのと同じ runtime tuning と扱う。

## 16. runtime autotuner

初回 bootstrap または hardware/backend が変わった時だけ、数秒～数十秒の短い benchmark を行う。

自動選択対象:

```text
worker/slot count
microbatch size
sparse/dense propagation threshold
sparse/dense plasticity threshold
GPU workgroup size（backendが許す範囲）
readback ring depth
shared-weight update microbatch interval（必要なら）
```

保存先例:

```text
artifacts/embodiment/training-throughput-calibration-v1.json
```

通常学習のたびに探索し直さない。

## 17. direct Metal backend は最終候補として残す

現在は wgpu / WGSL で実装されている。

portable backend としては維持する。

ただし対象機が M1 16GB であり、絶対性能をさらに詰める場合は direct Metal backend を比較対象にする価値がある。

Metal で期待できる候補:

- unified-memory shared buffer のより直接的な利用
- compact motor output の copy/map overhead 削減
- GPU-driven indirect dispatch
- simdgroup primitive
- Apple GPU 向け threadgroup tuning
- wgpu abstractionで使いにくい最適化

ただし direct Metal 化そのものを先にやるべきではない。

**アルゴリズムが全-edge scan のままなら、backendを変えるより edge work 削減の方が先である。**

## 18. sample efficiency も wall-clock 最短化の一部

計算 throughput だけ上げても、無意味な経験を大量に生成すれば checkpoint 到達は速くならない。

そのため curriculum は shared experience distribution として、現在の能力境界付近へ経験を集中させる。

ただし外部コードが:

```text
正しい motor action
正しい synaptic delta
```

を教えてはいけない。

許されるのは現在と同じく:

```text
spawn condition
initial velocity
which gate/stage is practised
environment geometry distribution
```

など、経験条件の選択だけである。

worker 数が増えたら全員を全く同じ spawn にせず、現在の boundary band / difficulty distribution から並列sampleする方が経験効率はよい。

## 19. 「最速」の測定方法

最終的な primary metric は raw steps/s ではない。

例えば Flyppy v3 で固定した frozen evaluation condition を用意し、

```text
Target:
  N gate sustained flight success >= X%
```

のような実用 threshold を設定できるなら:

```text
wall-clock seconds until first checkpoint satisfying target
```

を最重要指標にする。

まだ最終 threshold が決められない段階では:

```text
simulated biological seconds / wall-clock second
DAN-bearing useful episodes / hour
control steps / second
```

を代理指標にする。

ここで population=1 vs 2 vs 4 を長時間研究比較する必要はない。

短い system benchmark で throughput ceiling を探し、その設定を通常学習に使う。

## 20. 推奨実装順

速度改善までの時間も考慮し、次の順を推奨する。

### P0: profiling counters を追加する

まず現在の1 Flyについて:

```text
Python retina time
JSON bridge round-trip time
GPU neuron pass time
GPU plasticity pass time
trace pass time
motor gather + map time
periphery time
MuJoCo time
telemetry/logging time
active spike count
candidate post estimate
eligibility nonzero edge count
```

を低overheadで測る。

これは研究ではなく、間違った hotspot を最適化しないための工学的測定である。

### P1: immediate low-risk overhead removal

1. fixed motor readback buffer / bind group を preallocate
2. staging/readback ring を再利用
3. compact stimulus upload
4. telemetry / trajectory logging を training critical path からさらに外す
5. reinforcement `steps>1` を1 command sequenceにまとめ、CPU round-tripを減らす

### P2: runtime graph compile

1. FastGraph / DopamineGraph 分離
2. current-runtime no-op edges を hot graph から除外
3. outgoing CSR 追加
4. fast sign を edge metadataへ事前符号化

### P3: sparse candidate propagation

1. active pre outgoing traversal
2. candidate-post bitset
3. candidate post のみ incoming scan
4. dense fallback
5. population=1 fixture で dense reference と一致確認

### P4: sparse plasticity working set

1. active eligibility bitset/list
2. pre-event outgoing local pass
3. post-event incoming local pass
4. active-list decay + weight update
5. sparse/dense fallback
6. reset は active list のみ

### P5: JSON subprocess fast path を除去

PyO3等で neural runtime を Python process 内へ入れる。

この段階までで1 Fly throughputを再計測する。

### P6: vectorized multi-fly shared weights

1. shared weight 1 copy
2. slot-local CNS/plasticity/body states
3. step-start weight snapshot semantics
4. deterministic slot-order weight apply
5. finished slot の即reset/reuse

### P7: CPU/GPU microbatch pipeline

physics / retina と CNS compute を可能な範囲でoverlapする。

### P8: runtime autotuner

worker数、microbatch、sparse/dense threshold等を自動選択する。

### P9: 必要なら direct Metal / Rust MuJoCo hot loop

profile 上まだ backend / Python control が ceiling の場合だけ進む。

## 21. acceptance criteria

最速化のための最小 acceptance は以下とする。

1. `population=1` optimized neural step が既存 dense reference と一致する。
2. sensory mapping、DAN刺激規則、motor mapping、plasticity方程式を高速化のために変更していない。
3. sparse propagation が active path を取りこぼさない。
4. sparse plasticity が dense plasticity と同じ eligibility / weight を生成する fixture がある。
5. episode reset 後の eligibility が dense reset と一致する。
6. compact stimulus path が dense external-current buffer と同じ入力を作る。
7. persistent motor readback が現在の `read_spikes_at` と同じ body-ID event を返す。
8. shared-weight multi-fly では全slot propagationが当該stepのweight更新前snapshotを見る。
9. slot-order weight apply が決定論的である。
10. CPUへ full weight / full spike array を通常control loopでreadbackしない。
11. workerを増やした結果 unified-memory pressure でswapを発生させない。
12. 最終的に wall-clock throughput が現行trainerより明確に改善する。

ここで必要な `population=1` 比較はアルゴリズム研究ではなく、**高速化が方程式を壊していないことを確認する回帰テスト**である。

## 22. 現時点のメモリ構成案

current model の FastGraph edge 数を `Ef` とする。

shared:

```text
weights[Ef]                     4 * Ef bytes
incoming topology
outgoing edge-index topology
DopamineGraph topology
edge fast-sign/count metadata
```

per slot:

```text
neuron state                    O(N)
spike buffers/bitsets           O(N)
eligibility[Ef]                 4 * Ef bytes
eligibility active bitset       Ef / 8 bytes
eligibility active list         up to 4 * Ef bytes worst-case
candidate post bitset           N / 8 bytes
retina/periphery/body state
```

最悪時 active list が full Ef になるため、slot 数を固定で大きくしすぎない。

active list memory が問題なら:

- list capacity を段階拡張
- dense mode 移行後は list maintenance を停止
- episode reset時だけ bitsetから再構築しない

などで抑える。

worker count は M1 16GB の実 memory headroom を見て autotuneする。

## 23. この案でまだ「最速」と断定しない理由

この文書は、現在のコードを読んだ上での**最有力候補**である。

特に次は実測しないと決まらない。

- MaleCNS activity が本当に sparse kernel 有利な範囲にいるか
- eligibility active set が episode 後半でどこまで膨らむか
- outgoing irregular traversal が Apple GPU でどれだけ速いか
- candidate marking + incoming scan が dense CSR よりどのactivity率まで勝つか
- FlyBody vision が neural GPU compute と競合するか
- PyO3化後に Python/MuJoCo が次の ceilingになるか
- direct Metal が wgpu より十分速いか

したがって「この方式だから最速」と先に決めるのではなく、**最速候補を複数kernelとしてruntime内に残し、短いhardware benchmarkで選ぶ**構成そのものを最終案とする。

つまり、最終的な設計上の答えは1個の固定kernelではなく:

```text
Hybrid runtime
  sparse propagation OR dense propagation
  sparse plasticity OR dense plasticity
  autotuned slot count
  autotuned microbatch
  compact persistent I/O
```

である。

## 25. 最終提案

現時点では、元の

```text
episode-end asynchronous transaction commit
```

を最速候補とはしない。

また、単純な

```text
N flies × dense whole-CNS step
```

も最速候補とはしない。

現在の最有力構成は:

```text
        compact sensory input
                 |
                 v
      +---------------------+
      | shared Fast/Dopa    |
      | runtime topology    |
      +---------------------+
                 |
       active-pre outgoing
                 |
                 v
        candidate-post mark
                 |
                 v
   sparse incoming propagation
       OR dense fallback
                 |
                 v
       slot-local CNS state
                 |
                 v
  sparse active-eligibility plasticity
       OR dense fallback
                 |
                 v
       shared learned weights
                 |
                 v
      compact persistent MN readback
                 |
                 v
     parallel FlyBody / MuJoCo slots
                 |
                 +---- feedback to sensory
```

これを複数 slot で vectorize し、CPU/GPU pipeline と autotuner を載せる。

**「何匹並列にするか」より先に、「1匹につき毎step 25.6M edgeを触る必要が本当にあるか」を潰す。**

これが現在のコードと current neural equations を前提にした場合、wall-clock 学習時間を最も大きく削れる可能性が高い設計だと判断する。
