# Flyppy並列学習アーキテクチャ再設計案レビュー

Date: 2026-09-15 09:24 JST  
対象: `docs/20260915_flyppy学習アーキテクチャ再設計案.md`  
結論: **高速化用の実験モードとしては有望だが、現状案をそのまま canonical training にすることには反対する。**

## 1. 結論

提案されている

```text
複数 worker が同じ global weight snapshot から別々の episode を経験
→ episode-local plasticity transaction を生成
→ 終了順に最新 global weight へ rebase / commit
```

という方式は、一般的な非同期学習システムとしては筋が通っている。

また、以下の設計判断も良い。

- worker の最終 weight を global へ上書きしない
- weight averaging をしない
- topology は共有し、episode-local state だけ worker ごとに持つ
- commit order / source version / staleness を記録する
- `population=1` を reference として残す
- curriculum と evaluation を分離する
- GPU batching と MuJoCo 並列化を別問題として扱う

ただし、`virtual-fly` の中心目的は「最終的に成績の良い policy を得る」ことではなく、**1個体の神経系・身体・感覚・可塑性を時間発展させること**である。

この観点では、複数 episode の異なる未来を同時に分岐させ、そこで生じた可塑性を後から1本の nervous-system history に合流させる操作は、1個体の時間発展としては存在しない。

したがって推奨する位置づけは次である。

```text
canonical biological training
  = population=1 の因果的・直列な1個体 history

parallel high-throughput training
  = asynchronous shared-weight approximation
  = 別モードとして明示

parallel biological experiments
  = 複数独立個体を並列実行
  = weight merge なし
```

shared-weight asynchronous方式自体を捨てる必要はない。むしろ「速く有望な状態を探す」「curriculumやパラメータを絞る」「実装のthroughputを上げる」用途では価値が高い。ただし、そこで得たcheckpointをそのまま「1匹のハエがこの経験系列で学習した個体」と扱わない方がよい。

## 2. 最大の問題はtransaction式ではなく、経験履歴の分岐と合流

再設計案では、例えば次のようになる。

```text
W0
├─ Fly 1: episode E1 -> T1
└─ Fly 2: episode E2 -> T2

T2 を先に commit: W0 -> W1
その後 T1 を W1 に rebase: W1 -> W2
```

ここで `T1` は `W0` の神経系が経験した trajectory から生成されている。

しかし、現実に1個体が

```text
W0 --E2--> W1 --E1--> W2
```

という順に経験したなら、2番目の `E1` は `W1` の神経系から開始する。

その場合、同じ初期身体条件を与えても、

```text
sensory input
neural activity
motor output
body trajectory
next sensory input
DAN timing
eligibility
plasticity increment
```

は `W0` で走った E1 と一致する保証がない。

つまり非同期案の `T1` は、

```text
「現在の個体 W1 が経験した結果」
```

ではなく、

```text
「過去の分岐個体 W0 が別の未来で経験した結果」
```

である。

それを現在の `W1` へ移植することになる。

これはアルゴリズムとして成立しないという意味ではない。非同期分散学習では普通に現れるstale updateである。

ただし `virtual-fly` では意味が違う。これは**1個体の生物学的時間発展の並列化ではなく、複数の反実仮想的経験から得た可塑性を1個体へ集約する近似**である。

この点を canonical / approximation の境界として明記した方がよい。

## 3. additive + clamp transaction の要約式自体は現行則なら妥当

文書中の

```text
w <- clamp(w + d1, 0, M)
w <- clamp(w + d2, 0, M)
...
```

を

```text
shift
lo
hi
```

で要約し、

```text
w_global <- clamp(w_global + shift, lo, hi)
```

とする考え方は、現在の「加算 + 固定上下限clamp」の列を別の開始weightへ適用する変換としては妥当である。

したがって現在案で最も危険なのはこの数式ではない。

本質的な非同値性は、各 `d_t` が

```text
activity
trace
eligibility
modulation
```

から生成され、それら自体が episode 開始時weightと閉ループ身体trajectoryに依存する点にある。

つまり

```text
d_t(W0 trajectory)
```

を

```text
W1
```

へ適用しても、

```text
d_t(W1 trajectory)
```

を再現したことにはならない。

そのためtransaction表現をさらに数学的に厳密化しても、shared asynchronous方式がserial individual historyと同一になるわけではない。

## 4. 推奨する3層構成

### 4.1 Mode A: canonical serial individual

これは必ず残す。

```text
one MaleCNS state
one learned-weight history
one FlyBody
one environment trajectory

Episode 1
  -> plasticity
  -> W1
Episode 2 starts from W1
  -> plasticity
  -> W2
Episode 3 starts from W2
  ...
```

短期状態をepisode境界でresetする現在の設計を維持する場合でも、weight historyの因果系列は1本である。

このモードを、

- 科学的基準
- regression reference
- 最終確認
- 学習成立を論じる際の基準個体

とする。

### 4.2 Mode B: asynchronous shared-weight accelerator

現在の再設計案はこちらに置く。

用途:

- 高速に有望checkpointへ到達する
- curriculum設計を探索する
- plasticity parameter候補を絞る
- throughput benchmark
- 大量経験で何が起きるかを見る

名称にも approximation であることを残す方がよい。

例:

```text
training_mode = serial_individual
training_mode = async_shared_experience
```

`async_shared_experience` で良い結果が出たら、そのcheckpoint周辺や同じ条件を `serial_individual` で再確認する。

### 4.3 Mode C: independent population

複数workerをそれぞれ本当の別個体として扱う。

```text
Fly A: WA(t)
Fly B: WB(t)
Fly C: WC(t)
```

weight mergeはしない。

これは生物学的意味を壊さず完全に並列化できる。

用途:

- 個体差
- seed差
- 学習成功率
- robustness
- curriculum比較
- control experiments

に向く。

計算資源があるなら、科学的にはこの方式が最もきれいである。

## 5. 「1個体を速く育てる」場合に優先すべき高速化

1個体の因果historyを守る限り、episodeそのものを複数未来へ分岐して完全並列化することは原理的に難しい。

そのため canonical path の高速化は、時間軸を分岐させるより**1 stepの処理を速くする方向**を優先すべきである。

優先候補:

1. GPU上でのsynapse propagation / neuron update / plasticityの融合・batch最適化
2. CPU-GPU同期回数の削減
3. MN readbackを必要最小限にする
4. retina / periphery / MuJoCoとGPU CNSのpipeline化
5. activityが十分疎い場合のevent-driven / active-frontier方式
6. biologically justified plastic subsetが確立した場合、そのsubsetだけmutable stateを持つ
7. viewer / telemetryを完全非同期化
8. checkpoint書き出しを学習critical pathから外す

特に `hae.satoru.net` のShiuモデル実装で使われているevent-driven最適化は、MaleCNSで活動が疎い条件なら検討価値がある。ただし現在のGPU dense/sparse dispatchより本当に速いかはbenchmarkで決める。

## 6. 現行案を使うなら staleness は version 数だけで測らない

現在文書では

```text
version_staleness = commit_version - source_version
```

を記録する案になっている。

これは必要だが不十分である。

1 commitが非常に小さい場合と、大量のDAN刺激で多数weightが動いた場合を同じ `staleness=1` と数えるためである。

追加で少なくとも次を記録することを推奨する。

```text
weight_distance_from_source
changed_edge_fraction_since_source
L1 / L2 / max weight delta on plastic subset
number of intervening DAN events
number of intervening commits
```

可能ならtransaction commit時に

```text
source_weight_hash/version
current_global_weight_distance_from_source
```

を取る。

async modeでstale transactionを許容する閾値も、version数よりweight距離で決めた方が意味がある。

## 7. staleness制御の推奨

async modeを実装するなら、最初から無制限commitにしない方がよい。

最初のprototypeは

```text
population = 2
max_version_staleness = 1
```

程度で始める。

比較するもの:

```text
population=1 serial
population=2 async, unrestricted
population=2 async, staleness capped
```

staleness超過時の候補は:

```text
A. transactionを破棄して最新版から新episodeを始める
B. approximation modeとしてそのままcommitする
C. 研究用に両方実装して比較する
```

canonical serialと同値にはならないので、「どれが正しいか」ではなく、async acceleratorとして最も安定する方式を実測で決める。

## 8. synchronous batch にしても本質問題は消えない

例えば全workerを `W0` から開始し、全episode終了後に

```text
T1
T2
T3
T4
```

を決定論的順序で適用すれば、再現性は上がる。

しかし、T2以降も `W0` で生成された別未来のtransactionであることは変わらない。

したがってこれはcommit順の非決定性を消す手段ではあるが、1個体serial historyとの意味的差は解消しない。

## 9. memory設計について

MaleCNS約25.6M edgeに対し `f32` を使うと、概算で1配列あたり

```text
25.6M * 4 byte ≈ 102.4 MB
```

である。

workerごとに

```text
local weight       ≈ 102 MB
eligibility        ≈ 102 MB
transaction shift  ≈ 102 MB
transaction lo     ≈ 102 MB
transaction hi     ≈ 102 MB
```

を全部full-sizeで持つと、edge関連だけで約512 MB / workerになる。

8 workerなら約4.1 GBであり、これに

- topology buffers
- neuron state
- retina
- MuJoCo instances
- WGPU temporary/staging buffers
- macOS / Python / Rust process memory

が加わる。

M1 16 GBでは、full transaction representation × 多workerは早めに圧迫する可能性が高い。

したがってP2の2 worker段階で、まず実際のnonzero plasticity edge率を測るべきである。

もしepisode内でtransactionが非zeroになるedgeが十分疎いなら、

```text
sparse transaction
```

が有力である。

ただし `local weight` と `eligibility` はepisode中の神経活動へ影響するため、単純に消せない。copy-on-writeやsparse deltaを使う場合はGPU lookup costとのtrade-offを実測する。

## 10. curriculum並列化の考え方は概ね良い

curriculumをworkerごとに永久分離せず、global experience distributionとして扱う案には賛成する。

ただし、async modeでは同じweight version近辺から多数episodeが発行されるため、rolling windowを単純な「直近N episode」にすると、特定のweight世代に偏る可能性がある。

記録には

```text
source_weight_version
spawn condition
result
```

を必ず含め、curriculum update時に「どのweight世代で得た成績か」が追えるようにする。

必要なら古すぎるsource versionのepisodeをcurriculum統計から除外する。

## 11. control experimentsの扱い

文書では各experimental conditionに別GlobalWeightStoreを持たせるとしており、これは正しい。

ただし `virtual-fly` の開発目的上、control実験を並列学習基盤の成立条件にする必要はない。

parallel architectureの技術的acceptanceは、まず

```text
state isolation
transaction correctness
checkpoint/resume
throughput
reproducibility
```

で十分である。

control群は、それを使って特定の生物学的主張を検証するときに走らせればよい。

## 12. acceptance criteria の修正案

現在のcriteriaに以下を追加することを推奨する。

### serial canonical

1. `population=1` が従来trainerと一致する。
2. episode N+1 のweightは必ずepisode N終了weightから始まる。
3. 1個体historyに別trajectory由来transactionを混ぜない。

### async accelerator

1. stale local final weightによる上書きがない。
2. weight averagingがない。
3. transaction commitが決定された順序でatomicに適用される。
4. source/commit versionとweight-distance stalenessを保存する。
5. population増加でwall-clock throughputが改善する。
6. serial referenceとの差を定量化する。
7. async checkpointはmetadata上でserial checkpointと識別可能にする。

### independent population

1. 個体間でmutable neural state / weightsを共有しない。
2. 同一initial snapshotからの独立個体として追跡できる。

## 13. 実装順の修正案

推奨順序は次である。

```text
P0  serial referenceを固定
P1  1個体内のprofilingを取る
P2  GPU/CPU pipelineの単体高速化
P3  independent 2-individual runnerを作る
P4  async shared transactionをexperimental modeとして2 workerで作る
P5  serial vs asyncの差を測る
P6  asyncが有用ならGPU batched workerへ拡張
P7  population sizing
```

現在案ではtransaction APIを先に中核へ入れる構成だが、実際のbottleneckが

```text
GPU neural step
CPU-GPU synchronization
MuJoCo
retina
Python orchestration
```

のどこかを先にprofileした方がよい。

もし1個体のGPU利用率が既に高いなら複数worker batchingの伸びは小さい可能性があるし、逆にMuJoCo待ちが支配的ならCPU body parallelismだけでもかなり伸びる。

## 14. 最終判断

質問「学習の並列学習していく仕組みとして、この再設計案でよいか」に対する回答は次になる。

**工学的な並列学習方式としてはかなり良い。ただし `virtual-fly` の canonical biological learner として採用するのは避けた方がよい。**

理由は、非同期transactionの実装上の欠陥ではなく、

```text
1個体の1本の経験history
```

を

```text
複数の分岐した経験historyから得た可塑性の合流
```

へ変更してしまうためである。

推奨する最終構成は:

```text
serial_individual
  科学的canonical / 1個体の本来の学習

async_shared_experience
  高throughput探索・高速学習用 approximation

independent_population
  複数個体を生物学的意味を保って並列実行
```

この3モードを明確に分ければ、現在の再設計案の工学的利点をほぼ失わず、`virtual-fly` の核心である「ハエの神経系を個体として時間発展させる」という意味も守れる。

特に、async modeで得た良いcheckpointや条件はserial modeで再走・確認する運用にすると、開発速度とプロジェクトの意味を両立しやすい。
