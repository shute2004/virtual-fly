# Flyppy 最速学習アーキテクチャ再設計レビュー

Date: 2026-09-15

独立レビュー: `docs/20260915_0949_Flyppy並列学習アーキテクチャ独立技術レビュー.md`

## 1. 目的

この文書の目的は、`virtual-fly` の生物学的・物理的意味を変えずに、Flyppy 学習を **wall-clock で可能な限り速く進める計算アーキテクチャ**を定めることである。

並列化手法そのものを研究対象にはしない。

最適化の目的関数は、概ね次である。

```text
maximize:
  exact / meaning-preserving simulated neural+body time per wall-clock second

subject to:
  MaleCNS topology / sensory mapping / motor mapping / plasticity equation /
  reinforcement semantics / physics timestep / closed-loop timing
  を勝手に変更しない
```

したがって、`population=1 vs 2 vs 4...` の学習曲線研究や、staleness 理論の研究を行うこと自体は目的ではない。

必要なのは、**同じ意味論を保ったまま実機上で最速になる kernel / worker 数 / pipeline 幅を自動選択すること**である。

## 2. 結論

独立レビューを反映した最終候補は、単純な episode 並列化でも、単純な batched multi-fly でもない。

推奨するのは以下である。

```text
Hybrid Exact Neural Runtime
  + compiled Fast/Dopamine graph
  + 3-way propagation
  + timestamp/lazy plasticity
  + persistent readback resources
  + native MuJoCo hot loop
  + shared-weight multi-fly
  + edge-union deterministic weight apply
  + CPU/GPU overlap
  + runtime autotuning
```

最重要点は、**multi-fly を最初に実装しない**ことである。

現在の runtime は、1 neural step ごとに大規模 edge work を行う。その状態で worker 数だけ増やすと、GPU occupancy は改善しても総 edge traffic が worker 数に比例して増え、Apple Silicon の unified-memory bandwidth を早く使い切る可能性が高い。

したがって優先順位は:

```text
1. 1 Fly / 1 neural step のコストを下げる
2. CPU/GPU同期停止を減らす
3. Python/MuJoCo hot loop を削る
4. その後で shared-weight multi-fly を載せる
5. 最後に overlap / autotune する
```

とする。

## 3. 現行 runtime の正確な意味論

高速化はこの意味を保存する必要がある。

現在の GPU step は概念的に:

```text
neuron_step
  -> plasticity_step
  -> trace_step
```

の順である。

### 3.1 modulation

step `t` の postsynaptic modulation は:

```text
m_t = alpha * m_(t-1) + dopamine_input_t
```

### 3.2 local plasticity term

`plasticity_step` は trace 更新前に実行されるため、step `t` の local term は概念的に:

```text
L_e(t)
  = trace_pre(t-1) * activity(post, t)
  - trace_post(t-1) * activity(pre, t-1)
```

### 3.3 eligibility

```text
e_t = beta * e_(t-1) + L_e(t)
```

### 3.4 weight

```text
w_t = clamp(
  w_(t-1) + eta * m_post(t) * e_t,
  0,
  weight_max
)
```

### 3.5 trace

最後に:

```text
trace_t = gamma * trace_(t-1) + activity_t
```

となる。

**高速化実装は、この更新順を変えてはいけない。**

以前の案にあった「local を足してから eligibility 全体を decay する」擬似コードは誤りであり、採用しない。

## 4. P0: まず profile を取る

最初の実装作業はアーキテクチャ変更ではなく、現在の 1 Fly hot path の時間分解である。

viewer は無効にし、現行コードの 1 control step を以下へ分解する。

```text
retina encode
Python -> neural request serialize/write
GPU external input upload
neuron_step GPU
plasticity_step GPU
trace_step GPU
motor gather GPU
GPU -> CPU map wait
Rust -> Python response
periphery update
MuJoCo physics substeps
collision/course update
trajectory logging
telemetry producer I/O
checkpoint amortized cost
```

GPU側では timestamp query が利用可能なら kernel 単位で測る。

同時に毎step次を記録する。

```text
exact neuron count
exact edge count
active fast presynaptic neuron count
active dopamine neuron count
sum_out_degree(active_fast_pre)
candidate_post_count
sum_in_degree(candidate_posts)
nonzero eligibility edge count
modulated post count
motor readback count
```

25.6M という概算値を profile の基準値に固定しない。その run が実際にロードした `edge_count` を使う。

## 5. runtime graph を source snapshot から分離して compile する

MaleCNS source snapshot は変更しない。

runtime 起動時に source snapshot から、現在の方程式で意味を持つ graph を compile する。

### 5.1 FastGraph

fast neurotransmission を行う edge のみ。

保持するもの:

```text
incoming CSR
outgoing CSR
edge identity
post index
pre index
sign
count / initial weight metadata
shared mutable weight index
```

### 5.2 DopamineGraph

現在の model では dopamine edge は fast weight として使わず、postsynaptic modulation へ入力する。

したがって fast edge と分離する。

```text
DopamineGraph
  incoming/outgoing compact adjacency
  fixed count / gain metadata
```

現行意味論上 mutable weight / eligibility が不要なら、dopamine edge を `SynapseStateGpu` の fast mutable pool に残さない。

### 5.3 runtime no-op edge

現在の transmitter rule で fast current にも modulation にも使われない edge は、source snapshot には保持したまま runtime graph から外せる。

これは connectome の削除ではなく、**現在の runtime equation に対する compiled execution view**である。

## 6. plasticity を propagation より先に最適化する

現在の最有力ボトルネック候補は、`plasticity_step` の全 fast edge read-modify-write である。

活動が疎くても eligibility と weight のために全edgeを毎step触る構造は避けたい。

### 6.1 sparse eligibility state

slot ごとに最初から full `eligibility[E]` を常時更新するのではなく、まず sparse state を採用候補とする。

概念:

```text
SparseEligibilityEntry {
  edge_id
  eligibility_at_last_materialize
  last_materialize_step
}
```

必要条件:

- `eligibility != 0` のedgeを取りこぼさない
- 勝手な epsilon cut はしない
- local event が来た edge は必ず materialize する
- post modulation が weight update に影響する区間を取りこぼさない
- checkpoint 時は timestamp 込みで保存するか、現在stepへ materialize して保存する
- episode reset は sparse container を破棄すればよい

### 6.2 lazy eligibility

local event のない区間では:

```text
e_(t+k) = beta^k * e_t
```

なので、毎step multiply する必要はない。

次の local event、weight materialize、checkpoint 等のタイミングでまとめて更新する。

### 6.3 lazy modulation

新しい dopamine input がない区間では:

```text
m_(t+k) = alpha^k * m_t
```

である。

modulation も timestamp で lazy materialize できる。

### 6.4 event-free weight integration

ある edge について区間中:

```text
L = 0
dopamine_input = 0
```

であり、区間開始直後の state を `m_0, e_0` とすると、以後の `m*e` は `alpha*beta` の等比減衰になる。

したがって、逐次:

```text
w += eta * m_j * e_j
```

を毎step行わず、区間末尾で等比級数としてまとめて積分できる。

正確な index convention は CPU dense reference と fixture で固定する。

`alpha > 0`, `beta > 0` の現行設定では event-free 区間内で `m*e` の符号は変わらないため、clamp も区間末尾でまとめられる。

ただし floating-point の丸め順は変わり得るため:

- 方程式意味論一致: tolerance compare
- bitwise replay 必須モード: dense/iterative path

を分ける。

### 6.5 dense fallback

active eligibility が大きくなり、sparse map / compaction / lookup の固定費が高くなった場合は dense plasticity へ切り替える。

切替は「active neuron 割合」ではなく:

```text
active eligibility edge count
modulated post に接続する active eligibility edge count
sparse container bytes touched
predicted dense bytes touched
```

を使う。

## 7. propagation は 3-way hybrid にする

candidate-post 方式を最終解に固定しない。

### Mode A: DenseIncoming

現在に近い方式。

```text
for every post neuron:
  scan incoming FastGraph edges
```

活動が密なとき、Apple GPUでは規則的な memory access によりこれが最速になる可能性がある。

### Mode B: CandidateIncoming

```text
active pre
  -> outgoing adjacency で candidate post をmark
  -> candidate postだけ incoming scan
```

中程度の sparse activity で有利な候補。

ただし高 indegree post が少数 candidate になった場合、outgoing を一度触った後に candidate post の incoming を再度広く走査するため無駄が出る。

### Mode C: ActiveEdgeFrontier

```text
active fast pre
  -> outgoing edge を直接展開
  -> (post, contribution) frontier
  -> postごとに deterministic segmented reduction
```

ultra-sparse activity では触る edge 数を最小化できる可能性がある。

WGSL portable path では `atomic<f32>` 前提にしない。

候補:

```text
edge contribution compaction
post key grouping / prefix
segmented reduction
```

を使う。

### 7.1 runtime selector

モード選択指標は単純な `active_pre_fraction` にしない。

少なくとも:

```text
W_out = sum_out_degree(active_fast_pre)
W_in  = sum_in_degree(candidate_posts)
C_post = candidate_post_count
```

を使う。

概念的には:

```text
if W_out is very small:
    ActiveEdgeFrontier
elif W_in is sufficiently below total_fast_edges:
    CandidateIncoming
else:
    DenseIncoming
```

閾値は Apple M1 / backend 上で実 activity trace を replay して autotune する。

## 8. motor readback を即時最適化する

現行 `read_spikes_at()` は毎callで buffer / bind group / encoder / staging を作り、`map_async` 後 `device.poll(Wait)` でCPUを止める。

これは neural algorithm を変えずに削れる。

### 8.1 persistent gather resources

起動時に motor neuron index は固定する。

以下を preallocate する。

```text
fixed motor index buffer
persistent gather output buffer
2-3 staging buffers ring
persistent bind groups
```

毎stepの resource creation を無くす。

### 8.2 multi-slot時の overlap

single flyでは motor output がphysicsの前提なので、依存 fence 自体は完全には消せない。

multi-flyでは:

```text
slot group A: GPU CNS / gather
slot group B: CPU physics
```

を交互に進め、map waitを他slotの仕事で隠す。

## 9. dense external-current upload は低優先度でcompact化する

全neuron `f32` uploadは edge kernel より小さい可能性が高いので、P0/P1の最優先にはしない。

ただし retina mapping は固定なので、body ID を毎step lookupしない。

起動時に:

```text
body_id -> dense neuron index
```

へ変換し、hot pathでは compact `(index, current)` を直接扱う。

必要なら GPU 側 scatter kernel で dense current buffer を作る。

## 10. reinforcement は request batching ではなく GPU submission batching を行う

現在 `reinforcement_steps=4` は既に1回の Python request で送られている。

次に削るべきなのは IPC request 数ではなく、内部 neural step の GPU submission 数である。

可能なら:

```text
4 neural steps
  -> 1 command encoder
  -> 1 queue submit
  -> readbackなし
```

にする。

step間依存は GPU command sequence 内で維持する。

## 11. telemetry / logging を training critical path から外す

viewer process が別でも、producer が同期 filesystem write をしていれば training は止まる。

training default は:

```text
body telemetry = off or low-rate
neural telemetry = off or low-rate
```

とする。

可視化を有効にする場合も:

```text
trainer hot path
  -> lock-free / bounded ring queue
  -> telemetry writer thread/process
  -> JSON/filesystem
```

とする。

trajectory も毎step JSON serialize を避け、hot pathではcompact binary / ring append、episode後にJSONLへ変換する方がよい。

## 12. checkpoint を再設計する

checkpoint は periodic large stall になり得る。

### 12.1 GPU snapshot copy

checkpoint boundaryで:

```text
live buffers
  -> dedicated snapshot buffers
```

を GPU copy し、training は可能な限り次へ進める。

map / serialization / disk write は別threadへ渡す。

### 12.2 bulk write

`f32/u32` を1要素4 byteずつ `write_all` しない。

```text
large contiguous slice
BufWriter
chunked bulk write
```

を使う。

### 12.3 checkpoint種類を分ける

```text
full-resume checkpoint
weight-only evaluation snapshot
```

を分ける。

評価のためだけに eligibility / membrane / trace 全部を保存しない。

## 13. Python / Rust / MuJoCo hot path

JSON subprocess bridge は固定 overhead なので最終的には外す価値が高い。

ただし PyO3 化だけで終わりではない。

現行 control loopには Python で:

```text
retina
periphery
10 physics substeps
course update
```

がある。

特に `physics_steps=10` は 50us timestep を10回積分する意味を保ったまま、native loopへ移せる。

```text
Python:
  command once

Rust/C native hot loop:
  for _ in 0..10:
      apply muscle/periphery force
      mj_step
```

とすれば physics timestep / wing cadence を変えずに Python loop overhead を消せる。

最終 ceiling を狙うなら:

```text
Python
  experiment configuration / analysis only

Rust/C fast runtime
  neural engine
  periphery hot path
  MuJoCo stepping
  event extraction
```

を候補とする。

## 14. shared-weight multi-fly

1 Flyあたりのコストを削った後で multi-fly を載せる。

### 14.1 shared state

全slot共有:

```text
compiled topology
shared learned weight: 1 copy
neural constants
sensory/motor maps
```

slot-local:

```text
membrane
spikes
refractory
trace
modulation
sparse eligibility state
retina adaptation
periphery state
MuJoCo mjData / body state
environment state
RNG
```

workerごとの full weight copy は持たない。

### 14.2 同一 neural step の意味

exact shared-weight mode では:

```text
step start:
  all slots read same shared W_t

all slots:
  neural propagation
  local plasticity delta generation

then:
  shared W_t に全slot deltaを deterministic order で反映

next step:
  all slots read W_(t+1)
```

とする。

episode終了まで weight update を寝かせない。

## 15. shared weight apply は edge-union single dispatch にする

slotごとに weight update dispatch を直列化しない。

### 15.1 active edge union

各slotで今回 weight delta を持つedgeを集め:

```text
union_active_edges[]
slot_mask / per-slot delta reference
```

を作る。

### 15.2 edge-wise apply

1 edge invocationが:

```text
w = shared_weight[edge]

for slot in deterministic_slot_order:
    if slot has delta for edge:
        w = clamp(w + delta(slot, edge), 0, M)

shared_weight[edge] = w
```

とする。

これにより:

- slot順のclamp semanticsを維持
- weight load/storeを原則1回
- slot数分のdispatchを回避

できる。

**全slot deltaを単純sumして最後に1回clampする方式は採用しない。** 正負deltaと境界が混ざると結果が変わる。

## 16. CPU/GPU microbatch pipeline

slotを少なくとも2群へ分ける。

```text
時刻 n:
  GPU: group A CNS
  CPU: group B retina/periphery/physics

時刻 n+1:
  GPU: group B CNS
  CPU: group A retina/periphery/physics
```

single slot内の因果順は維持する。

```text
vision_t
-> CNS_t
-> motor_t
-> physics_t..t+1
-> vision_t+1
```

複数control stepをまとめてfeedbackを飛ばす近似は canonical exact mode には入れない。

## 17. runtime autotuning

このプロジェクトで必要なのは並列化研究ではなく、起動時の短い runtime tuning である。

実 activity replay を数秒使い、以下を選ぶ。

```text
propagation mode A/B/C threshold
sparse/dense plasticity threshold
workgroup size
worker count: 1/2/4/8...
microbatch grouping
staging ring depth
candidate bitset strategy
slot mask representation
```

選択基準は:

```text
exact neural steps / wall-clock second
control steps / wall-clock second
simulated biological seconds / wall-clock second
```

とする。

短い失敗episodeを大量に回すだけで `episodes/hour` が高くなる場合があるため、`episodes/hour` を主指標にしない。

## 18. direct Metal の位置づけ

macOS 上の wgpu は既に Metal backend を使用する。

したがって direct Metal 化は「GPUをMetalへ変える」ことではなく:

- Metal固有 synchronization
- buffer lifecycle
- indirect dispatch
- SIMD/threadgroup最適化
- WGSLで表現しづらいhot path

を直接使うための最終手段である。

先にやるべきではない。

以下が profile で支配的と確認された場合のみ検討する。

```text
active-edge frontier compaction/reduction
slot-mask edge apply
indirect work generation
wgpu command overhead
```

## 19. 実装優先順位

### P0: profile + correctness fixtures

- exact neuron / edge count保存
- CPU/GPU wall-clock分解
- GPU kernel timestamp
- degree-weighted activity metrics
- dense CPU/reference fixture固定
- plasticity update順fixture固定

### P1: 同期停止とI/Oを削る

- persistent motor gather buffers
- telemetry producer非同期化 / training default off
- checkpoint bulk writer
- reinforcement multi-step single GPU submission
- retinal/body ID 起動時dense-index化

### P2: runtime graph compile

- FastGraph / DopamineGraph / ignored 分離
- incoming + outgoing adjacency
- sign/count事前符号化
- exact compiled graph sizesをprofile出力

### P3: plasticity再設計

- decay -> local -> weight の正確な順序fixture
- sparse eligibility + timestamp
- lazy modulation
- event-free closed-form weight integration
- sparse reset
- dense fallback

### P4: propagation 3-way hybrid

- DenseIncoming
- CandidateIncoming
- ActiveEdgeFrontier + deterministic segmented reduction
- degree-weighted selector

### P5: native hot path

profileで必要なら:

- JSON subprocess bridge除去
- PyO3または直接Rust runtime API
- MuJoCo 10 substep native loop
- periphery hot loop native化

### P6: shared-weight multi-fly

- shared weight 1 copy
- slot-local sparse eligibility
- active edge union
- single-dispatch deterministic slot-order apply
- finished slot即再利用

### P7: overlap + autotune

- CPU/GPU microbatch pipeline
- worker数短時間自動選択
- kernel threshold自動選択
- backend/workgroup tuning

### P8: direct Metal は必要な場合のみ

wgpu pathが profile 上明確な ceiling になったhot kernelだけ移す。

## 20. acceptance criteria

canonical fast runtime として採用する最低条件:

1. source MaleCNS snapshotを変更しない。
2. sensory / motor / reinforcement mappingを変更しない。
3. dense reference と neural event / plasticity結果が規定 tolerance 内で一致する。
4. `e_t = beta e_(t-1) + L_t` の更新順を維持する。
5. trace更新がplasticity後である現行順序を維持する。
6. exact modeではcontrol-loop timingを変えない。
7. shared weight applyのslot順clamp semanticsがfixtureで検証される。
8. sparse modeが不利なactivityではdense fallbackできる。
9. telemetry/checkpointがtraining hot pathを不必要に停止しない。
10. 変更前より実測 wall-clock throughput が改善する。
11. worker増加でthroughputが下がる場合はautotunerが小さいworker数を選ぶ。
12. optimizationによって hidden controller / task-specific action logic を追加しない。

## 21. 実装しないもの

canonical pathには以下を入れない。

- episode-end stale transaction を主学習方式にする
- worker weight averaging
- workerごとのfull weight copy
- scalar rewardによる直接weight更新
- Flappy攻略action decoder
- sparseだからという理由だけで approximate edge pruning
- epsilon eligibility deletion
- multi-control-step feedback skipping
- 単純sum delta + final clamp
- direct Metalへの早期全面移行
