# Flyppy 学習アーキテクチャ再設計案

Status: **proposal / review requested**  
Date: 2026-09-15  
Target branch at drafting: `feat/flybody-flyppy-loop`  
Purpose: 現在の Flyppy 学習実装を、科学的意味を維持したまま「実際に十分な経験量を与えられる学習系」へ作り直すための設計案。

## 1. 結論

現在の `train_flyppy_curriculum.py` は、閉ループが成立することを確認するための **single-lineage smoke test / bootstrap trainer** としては意味がある。しかし、これをそのまま長時間回すことを「本格的な学習」と呼ぶのは不適切だと考える。

理由は、1 個体・1 MuJoCo・1 MaleCNS runtime・1 episode 系列をほぼ逐次実行しており、利用可能な CPU/GPU 資源に対して経験生成量が極端に小さいためである。また、`docs/experiments.md` に既に要求されている多個体・対照群・再現性評価が、現在の学習ランナーには統合されていない。

提案する中核は次である。

```text
immutable observed topology / model definition
                  |
          shared read-only data
                  |
      +-----------+-----------+
      |           |           |
 individual 0  individual 1  individual 2 ...
      |           |           |
 independent   independent   independent
 neural state  neural state  neural state
 weights       weights       weights
 eligibility   eligibility   eligibility
 body          body          body
 curriculum    curriculum    curriculum
 RNG           RNG           RNG
      |           |           |
      +-----------+-----------+
                  |
     batched GPU neural execution
     parallel CPU body execution
```

**個体間で weight を平均しない。共有もしない。**

並列化するのは「独立個体の経験生成と神経時間発展」であり、各個体の学習履歴は完全に分離する。

## 2. 現在の実装で維持すべきもの

以下は現行設計の重要な正しい部分なので維持する。

1. `3D scene -> compound eye -> R1-R6 -> MaleCNS -> individual MN -> peripheral muscle -> FlyBody -> environment` の閉ループ。
2. 外部 action decoder、方策ネットワーク、Q-learning、backpropagation を導入しない。
3. ゲート通過や衝突を scalar reward として synapse update API に渡さず、PAM/PPL1 等の神経修飾系への刺激へ変換する。
4. MaleCNS observed graph は immutable source snapshot として保持し、個体ごとの mutable state を分離する。
5. checkpoint で神経・シナプス・可塑性状態を持続させる。
6. FlyBody の運動は実際の MN -> muscle -> physics から発生させ、隠れた stabilizer / scripted flight を入れない。
7. curriculum は環境初期条件を変えるだけで、CNS の action や synaptic delta を指定しない。

この再設計の目的は、これらを捨てて「普通の強化学習」にすることではない。逆に、これらを維持したまま十分な実験量を生成できる計算構造へ変えることである。

## 3. 現在の学習ランナーの問題

### 3.1 episode が直列である

現在は概念的に次である。

```text
episode 0
  -> checkpoint state updated
episode 1
  -> checkpoint state updated
episode 2
  -> ...
```

1 個体の因果系列としては正しい。しかし、PC 全体を使った学習方式としては、同じ時刻に 1 個体しか経験を生成しない。

### 3.2 GPU backend と GPU フル活用を混同できない

現行 GPU backend は neuron update / plasticity / trace を WGPU compute で並列化している。これは有効である。

しかし閉ループ全体は、概ね次の同期列になっている。

```text
retina / sensory encoding
    -> GPU neural step
    -> GPU motor-spike gather
    -> GPU->CPU readback wait
    -> peripheral state
    -> MuJoCo physics
    -> collision / gate event
    -> next step
```

単一個体では時系列依存があるので、この順序自体を消すことはできない。ただし、**個体 A が CPU physics を計算している間に個体 B/C の neural compute を進める**等、個体間では大きな並列化余地がある。

### 3.3 1 本の trajectory だけでは「学習した」と判断できない

`docs/experiments.md` では既に、少なくとも次の対照を要求している。

- plasticity off
- neuromodulation off
- non-contingent stimulation
- yoked control
- 同一初期状態からの複数独立個体

現在の単一 lineage の Flyppy run は、学習候補のデバッグには使えるが、学習成立の証拠にはならない。

### 3.4 curriculum が単発 episode 成否に敏感すぎる

現在の adaptive curriculum は `passed > 0` を episode 成功として即座に初期条件を hard/easy 方向へ動かす。

これは bootstrap としては単純で分かりやすいが、1 episode の偶然や初速依存に強く影響される。特に「第 1 gate は通ったが直後に衝突した」episode でも difficulty が上がる。

curriculum の目的は CNS に正解行動を教えることではなく、**学習可能な経験分布を維持すること**である。したがって単発判定ではなく、各個体の rolling performance と frozen evaluation を使って難易度を調整した方がよい。

### 3.5 training と evaluation が分離されていない

学習中の episode は、その場で plasticity と DAN stimulation を発生させる。この系列だけを見ると、

- curriculum が易しくなったため成績が上がった
- 神経学習で成績が上がった
- 初期速度の偶然で通過した

を分離しづらい。

定期的に training checkpoint を clone し、**plasticity off / reinforcement off の固定条件 evaluation** を別個体として実行する必要がある。evaluation clone は training individual を変更しない。

## 4. 提案する個体モデル

各個体 `i` は最低限次を独立に持つ。

```text
IndividualState[i]
  lineage_id
  parent_checkpoint_id
  neural dynamic state
  synaptic weights
  eligibility state
  neuromodulator state
  body / MuJoCo state
  peripheral state
  sensory adaptation state
  curriculum state
  RNG state
  cumulative neural steps
  cumulative simulated biological time
```

一方、次は個体間で read-only 共有してよい。

```text
SharedModel
  observed MaleCNS topology
  neuron metadata
  neurotransmitter metadata
  body topology / meshes
  circuit maps
  static environment definitions
  neural model constants
```

ここで重要なのは、**topology を共有することと weights を共有することは別である**という点である。

MaleCNS の observed connectivity は全個体で同じ initial source として共有できる。一方、学習で変化する effective weight / eligibility / modulation は個体ごとに別 buffer を持つ。

## 5. GPU: batched independent CNS runtime

### 5.1 基本形

現在の `GpuRuntime` を 1 個体専用として複数 process 起動するのではなく、最終的には `GpuPopulationRuntime` のような形へ拡張する。

概念的には:

```text
neuron_state[individual][neuron]
synapse_state[individual][edge]
spikes[individual][neuron]
external[individual][neuron]
```

を持つ。

GPU dispatch は、例えば neuron kernel なら `population_size * neuron_count`、plasticity kernel なら `population_size * edge_count` を対象にする。

kernel 内で:

```text
individual_index
local_neuron_or_edge_index
```

を復元し、その個体の mutable state だけを更新する。

### 5.2 weight averaging はしない

この runtime は minibatch SGD ではない。

各 individual は別の状態ベクトルを持ち、GPU 上で同時に時間発展しているだけである。

```text
W0(t+1) = local_plasticity(W0(t), experience0)
W1(t+1) = local_plasticity(W1(t), experience1)
W2(t+1) = local_plasticity(W2(t), experience2)
```

であり、

```text
mean(W0, W1, W2)
```

は canonical learning path では一切計算しない。

### 5.3 topology は一度だけ GPU に置く

現行 topology buffer は全個体で同じなので、個体数分複製する必要がない。

これにより、複数 GPU process を立てて topology を毎回複製するよりメモリ効率がよい。

### 5.4 mutable memory の概算

現在の synapse state が `weight: f32 + eligibility: f32` なら、約 25.6M edge に対して最低でも約 205 MB / individual が必要になる。

したがって 16 GB unified memory の M1 では、理論上は複数個体を保持できるが、実際の上限は WGPU の storage-buffer limit、MuJoCo、rendering、Python/Rust、共有 topology、staging buffer を含めて benchmark で決める。

最初から population=16 と固定せず、`1 -> 2 -> 4 -> 8 -> ...` と増やし、throughput / memory / correctness を測って自動選択する。

必要なら synapse state を複数 buffer / chunk に分割する。

## 6. CPU: 複数 FlyBody の並列実行

各 individual は独立した MuJoCo state を持つ。

M1 の CPU core を使うため、1 個体の Python loop にすべてを集約するのではなく、body/periphery/sensory stage を worker 化する。

候補は次の順で比較する。

```text
A. Rust orchestrator + worker threads
B. Python multiprocessing + 1 process / body slot
C. Python thread pool（GIL / MuJoCo binding の挙動を測定して採否）
```

最終形としては Rust 側に population scheduler を置く方が、Python IPC と GIL を避けやすいと考える。

ただし、最初の prototype は最小変更で実測する。

## 7. CPU/GPU のパイプライン

1 biological/control tick を population 単位で次のように処理する。

```text
CPU workers:
  body/sensory state of individuals 0..N
        |
        v
assemble batched sensory current
        |
        v
GPU:
  one batched MaleCNS step for active individuals
        |
        v
GPU:
  gather only required MN spikes for all individuals
        |
        v
ONE compact population readback
        |
        v
CPU workers in parallel:
  MN -> periphery -> MuJoCo -> events
        |
        v
next batched neural step
```

単一個体内の causality は維持される。

並列化は「同じ biological time の別個体」を同時処理することで行う。

episode 長が個体ごとに異なる場合は `active mask` を持ち、終了した slot だけ reset / next episode へ進める。他個体の CNS state を reset しない。

## 8. 個体ごとの curriculum

全 population に 1 個の global curriculum state を強制しない。

学習速度が異なるので、各 individual が独立した curriculum state を持つ。

```text
Individual 0: stage 1 / difficulty d0
Individual 1: stage 2 / difficulty d1
Individual 2: stage 1 / recovery difficulty d2
```

ただし curriculum が変えてよいのは環境条件だけである。

例:

- spawn x/z
- initial forward velocity
- gate count / spacing / opening geometry
- start gate
- environment random seed

CNS action、motor command、synaptic delta は curriculum が指定しない。

## 9. curriculum を single-episode reaction から performance-window へ変える

提案する基本原則は、

```text
1 episode success -> 即 harden
1 episode fail    -> 即 ease
```

ではなく、一定の window で challenge level を調整することである。

たとえば各個体について直近 K episode を見て、成功率が高すぎれば harden、低すぎれば ease、中間なら条件を固定する。

ここでの成功判定は stage ごとに定義する。

### Stage A: assisted first-gate acquisition

- 第 1 gate を通過
- ただし「初速で偶然通った」だけを区別するため、post-gate survival / trajectory も記録する

### Stage B: first-gate + post-gate control

- 第 1 gate 通過後、一定時間 collision せず飛行を維持
- または第 2 gate 方向へ一定距離進行

### Stage C: multi-gate flight

- 2 gate 以上
- 初速依存を徐々に減らす

### Stage D: target initial condition

- `x=0`, target z, target vx 等の設計上の最終初期条件で固定評価

### Stage E: generalization

- 未学習 seed
- gate height / spacing variation
- 既知範囲内の環境 perturbation

この stage 判定は **curriculum scheduling 用**であり、神経系へ scalar reward を渡すものではない。

神経刺激は従来通り、実際の gate pass / collision event に随伴して発生させる。

## 10. training と evaluation を完全分離する

一定 neural steps または episode 数ごとに、training individual の checkpoint を clone して evaluation slot を作る。

evaluation は:

```text
plasticity = OFF
PAM/PPL1 reinforcement = OFF
fixed initial conditions
fixed environment seeds
```

で実行する。

これにより、同じ学習済み CNS が「学習を継続せずに」固定課題でどの程度行動できるか測る。

主な指標:

- gate pass rate
- gates per episode
- survival time
- post-gate survival
- collision reason distribution
- altitude / pitch / velocity distribution
- fixed-scene trajectory similarity

training curriculum の難易度変化と competence の変化を分離する。

## 11. 複数個体を「best weight search」にしない

canonical scientific experiment では、成績の良い個体だけを選んで他を捨てる操作を「学習」と混同しない。

もし engineering experiment として、複数 lineage から高性能 lineage を選んで継続するなら、それは明示的に別カテゴリにする。

```text
biological-learning experiment
    individual local plasticity only

lineage-selection experiment
    local plasticity + external lineage selection
```

後者は evolutionary / selection pressure を追加しているので、結果を前者と混ぜない。

本 proposal の canonical path は **独立 replicate をそのまま保持する**ことである。

## 12. 対照群も同時並列で走らせる

本格的な「学習」run は、最低でも実験個体だけではなく control cohort を同じ scheduler で同時実行する。

推奨 cohort:

```text
A: contingent PAM/PPL1 + plasticity ON
B: plasticity OFF
C: neuromodulatory stimulation OFF
D: non-contingent stimulation
E: yoked stimulation
```

各 cohort に同一 base checkpoint から複数 replicate を作る。

こうすれば CPU/GPU の並列計算を「単にスコアを上げるため」ではなく、学習成立を統計的に判断するためにも使える。

## 13. yoked control の実装

個体 A の reinforcement event stream を記録し、pair となる個体 E へ同じ neural-time offset で再生する。

ただし E の自分自身の gate pass / collision と刺激時刻は結び付けない。

A と E は body/environment/CNS state を共有しない。

共有するのは「A に何 step 目でどの DAN stimulation が入ったか」という replay schedule のみである。

## 14. viewer

viewer は population 全体を常時 render しない。

学習 throughput を優先し、observer は任意の `individual_id` を選んで telemetry を購読する。

```text
view individual 3
view cohort A replicate 2
view currently selected debug slot
```

observer は現在と同様、training process へ情報を返さない。

## 15. checkpoint / lineage format

最低限:

```text
experiment_id
individual_id
cohort
lineage_id
parent_checkpoint_id
base_snapshot_hash
code_commit_sha
neural_model_version
plasticity_model_version
body_model_version
environment_version
RNG state
neural step
simulated biological time
curriculum state
weights / eligibility / dynamics
```

を保存する。

population checkpoint は「巨大な 1 ファイル」だけにせず、shared manifest + per-individual state として保存できる構造が望ましい。

## 16. 性能最適化の優先順位

### P0: profiler と golden tests

最初に wall time の内訳を測る。

```text
retina
GPU neural compute
GPU->CPU readback
periphery
MuJoCo
course event
telemetry
checkpoint
viewer/rendering
```

CPU/GPU utilization も実測する。

同時に、population 化前後で single-individual trajectory / neural state が同じになる golden test を作る。

`population_size=1` は現行 runtime と一致しなければならない。

### P1: batched GPU population runtime

- shared topology
- independent mutable state per individual
- batched neural step
- batched compact MN readback
- independent checkpoint slot

### P2: parallel body workers

複数 MuJoCo body を CPU core に分散する。

### P3: scheduler

- active mask
- independent episode reset
- independent curriculum
- cohort assignment
- deterministic seeds

### P4: fixed evaluation clones

training と evaluation を分離する。

### P5: control cohorts

plasticity off / DAN off / non-contingent / yoked を同一 run で回す。

### P6: pipeline overlap

GPU compute と別個体の CPU physics を可能な範囲で overlap させる。

## 17. 実装受け入れ条件

新 architecture は最低限次を満たす必要がある。

1. `population_size=1` で既存 single-individual runtime と数値的に一致する。
2. population 内の individual 間で mutable weight/state が共有されていない。
3. individual A の episode reset が B の dynamics / weights を変更しない。
4. 同一 seed + 同一初期 checkpoint なら再現できる。
5. viewer を有効/無効にしても training result が変わらない。
6. evaluation clone が training checkpoint を変更しない。
7. control cohort と experimental cohort の設定差が manifest に完全記録される。
8. CPU/GPU utilization と experiences/hour が現行より改善する。
9. throughput 改善のために action decoder / hidden stabilizer / external optimizer を追加していない。
10. 学習成立の判定は単一 trajectory ではなく、独立 replicate + control と比較して行う。

## 18. 直近の実装方針

次にコードへ入れるなら、私は次の順序を採る。

```text
1. 現行 single-run の profiler を追加
2. GpuPopulationRuntime の population_size=1 実装
3. golden equality test
4. population_size=2/4 へ拡張
5. batched MN spike gather
6. multi-body scheduler
7. independent curriculum state
8. fixed evaluation clone
9. control cohorts
10. auto-tune population size / CPU workers
```

最初から大量の個体数を決め打ちしない。

正しさを保ったまま `population=1 -> 2 -> 4 -> 8` と増やし、M1 16 GB で最も高い **biological simulated time / wall-clock time** と **independent experience episodes / hour** を出す構成を測定して選ぶ。

## 19. 現行 24 episode 継続についての判断

現行ランナーで 24 episode を追加していくことは、デバッグ用データを増やす意味はある。しかし、現在の throughput と実験設計のまま何百・何千 episode と積むことを、本格学習の主経路にはしない。

本格的に経験量を増やす前に、上記 population architecture へ移るべきだと考える。

理由は、学習則を変えずに計算資源の利用効率と実験の統計的妥当性を同時に改善できるからである。

## 20. レビュアーへの確認依頼

この proposal をレビューする LLM / 人間には、特に以下を攻撃的に確認してほしい。

1. 個体独立性を保った batched GPU runtime に、隠れた weight sharing が入り込む余地はないか。
2. single-individual semantics を壊す同期・scheduler 設計になっていないか。
3. M1 16 GB での GPU buffer / storage binding / unified-memory 上限の見積もりに重大な見落としがないか。
4. CPU/GPU overlap の設計で、同一個体の因果順序を壊していないか。
5. curriculum が外部 action policy や外部 reward optimizer の代替になっていないか。
6. frozen evaluation が competence を正しく測れるか。
7. control cohort は「経験依存の学習」と単なる刺激効果を区別するのに十分か。
8. yoked control の neural-time alignment に問題がないか。
9. この設計より単純で、同じ科学的意味を維持しつつ大幅に高速な構成がないか。
10. 現行 architecture からの migration 順序に、先に解決すべき correctness 問題がないか。

## 21. 最終判断

現在の single-lineage trainer は捨てる必要はない。

それは今後も:

- deterministic reference runner
- regression test
- 1 個体 debug mode
- viewer/debugging source

として価値がある。

しかし production learning runner の役割は別にする。

```text
reference / debug:
    one individual, sequential, maximally observable

production learning / experiment:
    many independent individuals
    shared immutable topology
    independent mutable CNS state
    batched GPU neural compute
    parallel CPU body simulation
    independent curricula
    simultaneous controls
    frozen evaluation
```

この分離が、virtual-fly の科学的制約を維持しながら、実際に大量の経験を与え、学習の有無を検証するための最も筋の良い次段階だと考える。
