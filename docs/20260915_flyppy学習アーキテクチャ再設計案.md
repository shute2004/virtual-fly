# Flyppy 学習アーキテクチャ再設計案

Status: **proposal / review requested**  
Date: 2026-09-15  
Target branch: `feat/flybody-flyppy-loop`  
Purpose: 現在の Flyppy 学習実装を、科学的制約を維持しつつ、CPU/GPU を実際に使って十分な経験量を与えられる学習系へ再設計する。

> 2026-09-15 revision: 初稿の「各 worker が永続的に独立 weight を持つ」という案は撤回する。canonical training の中核は **非同期・共有 weight・episode-local worker** とする。weight averaging は行わない。

## 1. 結論

現在の `train_flyppy_curriculum.py` は、1 個体・1 MuJoCo・1 MaleCNS runtime・1 episode 系列をほぼ直列に進める。

これは閉ループの正しさを確認する reference / bootstrap trainer としては有用だが、利用可能な CPU/GPU 資源に対して経験生成量が小さすぎるため、本格的な学習基盤としては不十分である。

提案する canonical training は、複数の Fly worker が同時に episode を経験し、**episode 終了時に、その episode で得た可塑性更新を最新の共有 weight へ順次 commit する**方式である。

概念図:

```text
                         shared global learned weights Wg(v)
                                      |
             +------------------------+------------------------+
             |                        |                        |
        start episode            start episode            start episode
             |                        |                        |
          Fly slot 0                Fly slot 1               Fly slot 2
          local W0                  local W1                 local W2
          local CNS                 local CNS                local CNS
          local body                local body               local body
             |                        |                        |
        experience E0            experience E1            experience E2
             |                        |                        |
      episode finishes         episode finishes         episode finishes
             |                        |                        |
      plasticity txn T0        plasticity txn T1        plasticity txn T2
             |                        |                        |
             +---------- serialized/asynchronous commit ------+
                                      |
                           newest shared Wg(v+1...)
                                      |
                     finished slot starts next episode
                         from newest shared weight
```

重要な点:

- Fly worker 間で最終 weight を平均しない。
- episode 終了時に worker の `W_local_end` で global weight を上書きしない。
- 各 worker は episode 開始時の global weight snapshot から始める。
- episode 中は、その worker のローカル CNS / weight / eligibility / body state だけが時間発展する。
- episode 終了時、その worker の経験により生じた **可塑性更新そのもの**を、その時点の最新 global weight に適用する。
- commit 後、その worker は最新 global weight を読み込んで次 episode を始める。
- 他 worker は episode の途中で強制同期しない。終了時まで自分の episode-local state を使う。

これは「複数の別個体を育てて後で混ぜる」方式ではない。複数の Fly worker を、1 個の共有学習状態へ非同期に経験を供給する計算 worker として使う。

## 2. 具体例

Fly 1 と Fly 2 が同時に走っているとする。

```text
Global weight = W0

時刻 A:
  Fly 1 starts episode from W0
  Fly 2 starts episode from W0

時刻 B:
  Fly 2 finishes first
  experience E2 -> transaction T2
  Global: W0 --T2--> W1
  Fly 2 starts next episode from W1

時刻 C:
  Fly 1 finishes
  experience E1 -> transaction T1
  Global: W1 --T1--> W2
  Fly 1 starts next episode from W2

時刻 D:
  Fly 2 finishes its second episode
  experience E2b -> transaction T2b
  Global: W2 --T2b--> W3
  Fly 2 starts next episode from W3
```

このとき Fly 1 は W0 で経験 E1 を生成しているが、commit 時には W1 が global の最新値である。

したがって正しい操作は、

```text
W_global = W1
W_global <- ApplyPlasticityTransaction(W_global, T1)
```

であり、

```text
W_global = Fly1.W_local_end
```

ではない。

また、

```text
W_global = mean(Fly1.W, Fly2.W)
```

でもない。

## 3. 現在の実装で維持するもの

以下は変更しない。

1. `3D scene -> compound eye -> R1-R6 -> MaleCNS -> individual MN -> peripheral muscle -> FlyBody -> environment` の閉ループ。
2. 外部 action decoder、方策ネットワーク、Q-learning、backpropagation を導入しない。
3. ゲート通過・衝突を scalar reward として synapse 更新 API に渡さず、PAM/PPL1 等の神経修飾系への刺激にする。
4. MaleCNS observed topology は immutable source snapshot として保持する。
5. MN -> muscle -> physics の物理経路を維持し、隠れた stabilizer / scripted flight を入れない。
6. curriculum は環境初期条件・経験分布だけを変え、motor command や synaptic delta を直接決めない。
7. CPU reference と GPU runtime の数値的整合性を golden test で維持する。

## 4. 共有する状態と worker-local 状態

### 4.1 canonical training で共有するもの

```text
SharedTrainingState
  global learned synaptic weights
  global weight version / commit sequence
  immutable MaleCNS topology
  neuron / neurotransmitter metadata
  neural model constants
  circuit maps
  global curriculum / experience-distribution state
  training statistics
```

### 4.2 episode 中だけ worker が持つもの

```text
EpisodeWorkerState[i]
  source_weight_version
  local episode weight copy/state
  membrane
  spikes
  refractory
  activity trace
  modulation
  eligibility
  sensory adaptation
  peripheral state
  FlyBody / MuJoCo state
  episode RNG
  episode environment state
  plasticity transaction accumulator
```

現行 `NeuralState::reset_dynamics_preserving_weights()` は membrane / spike / refractory / trace / modulation / eligibility を消し、weight だけを保持する。この分離は shared-weight training と相性がよい。

## 5. weight commit の意味

### 5.1 単純な最終 weight 差の加算は canonical にはしない

worker が episode 開始時に `W_start`、終了時に `W_end` を持っていたとして、単純に

```text
Delta = W_end - W_start
W_global += Delta
```

とするだけでは、weight clamp や将来の非線形 plasticity rule に対して意味が崩れる可能性がある。

canonical に保存・commit する対象は「weight の完成値」ではなく、**episode 中に発生した局所可塑性操作**である。

### 5.2 現行 plasticity では transaction 化できる

現在の GPU plasticity は各 synapse について概ね、

```text
eligibility <- decay * eligibility + local_activity_term
weight <- clamp(weight + learning_rate * modulation * eligibility,
                0,
                weight_max)
```

である。

したがって各 step の可塑性による加算量を

```text
d_t = learning_rate * modulation * eligibility
```

として、worker はその episode で発生した局所更新列を transaction として蓄積できる。

commit は最新 global weight に対して、その transaction の意味を適用する。

### 5.3 clamp を含む更新列の要約

現行 rule のように「加算して上下限 clamp」を繰り返す場合、全 step の `d_t` を巨大なログとして保存する必要はない。

1 synapse に対する更新列

```text
w <- clamp(w + d1, 0, M)
w <- clamp(w + d2, 0, M)
...
```

は、episode 中に per-edge transaction state を更新することで、commit 時に最新 `w_global` へ適用可能な小さな変換として要約できる。

初期:

```text
shift = 0
lo = 0
hi = M
```

各更新 `d` について:

```text
shift <- shift + d
lo <- clamp(lo + d, 0, M)
hi <- clamp(hi + d, 0, M)
```

commit:

```text
w_global <- clamp(w_global + shift, lo, hi)
```

これは「この episode で実際に発生した additive + clamp の更新列」を、別の開始 weight に rebase するための transaction representation として使える。

ただし、将来 plasticity rule が weight-dependent multiplicative rule 等へ変わる場合は、その rule に対応する transaction representation を別途設計する。

### 5.4 transaction は experience の結果である

ここで `T_i` は、その worker が episode 中に経験した sensory / neural / DAN / motor / body history からローカル可塑性則によって生じた更新である。

外部 optimizer が `T_i` を決めるのではない。

```text
experience
 -> local neural dynamics
 -> local neuromodulation / eligibility
 -> biological plasticity rule
 -> transaction
 -> commit to newest shared weight
```

という流れを維持する。

## 6. asynchronous commit coordinator

global weight への commit だけは順序を持たせる。

必要な概念:

```text
GlobalWeightStore
  weights
  version
  commit_seq

PlasticityTransaction
  worker_id
  episode_id
  source_weight_version
  per-edge transaction payload
  episode metadata
```

worker が episode を終えると:

```text
lock/serialize commit
current = GlobalWeightStore.weights
updated = apply(current, transaction)
GlobalWeightStore.weights = updated
version += 1
record commit
unlock
```

その worker は commit 完了後の最新版を next episode の初期 weight として取得する。

commit 自体は GPU 上で行う。25.6M edge の weight を CPU へ全 readback して再 upload する設計にはしない。

## 7. staleness の扱い

非同期方式なので、worker が episode を走っている間に global weight version は進む。

これはバグではなく設計上の性質である。

例:

```text
Fly 1 source version = 100
Fly 2 commits -> 101
Fly 3 commits -> 102
Fly 1 finishes at global version 102
Fly 1 transaction commits -> 103
```

記録するべき値:

```text
source_weight_version
commit_weight_version
version_staleness = commit - source
wall/simulated episode duration
```

staleness が大きすぎると serial learner からの乖離が大きくなる可能性があるため、population size を無制限に増やさない。

`population=1,2,4,8...` で throughput と学習挙動の両方を測定し、許容範囲を決める。

必要なら将来、

- max staleness を超えた transaction の扱い
- worker 数の動的調整
- episode 長の調整

を追加する。

## 8. これは serial learning と完全同一ではない

この非同期方式は、1 匹のハエが episode を厳密に 1 本ずつ順番に経験する serial trajectory と完全同一ではない。

理由は、Fly 1 の episode 中に Fly 2 の経験が global weight へ先に commit されても、Fly 1 の episode 内軌道はその変更を見ないためである。

したがってこれは、**serial learning の意味をなるべく保ちながら経験生成を並列化する asynchronous approximation** として扱う。

自己欺瞞を避けるため、必ず:

```text
population=1 reference
population>1 asynchronous shared-weight
```

を同一 seed / task family で比較する。

比較対象:

- weight distribution
- changed-edge locality
- neural activity statistics
- curriculum progression
- frozen evaluation performance
- retention
- learning speed per simulated biological time
- learning speed per wall-clock time

## 9. GPU 実装

### 9.1 topology は 1 copy

MaleCNS topology / metadata は全 worker で同じなので GPU 上に一度だけ置く。

### 9.2 mutable episode state は worker dimension を持つ

概念的には:

```text
neuron_state[slot][neuron]
spikes[slot][neuron]
eligibility[slot][edge]
local_weight[slot][edge]  # initial prototype
transaction[slot][edge]
```

を持つ。

ただし 25.6M edge × 多数 slot の full local weight / eligibility は M1 16 GB では重い。

そのため prototype ではまず memory profile を取り、次を比較する。

A. full local mutable synapse state / slot  
B. shared base weight + per-slot copy-on-write / delta representation  
C. active/plastic synapse subset のみ slot-local state  

科学的意味を変える圧縮は採用しない。

### 9.3 batched neural dispatch

1 control tick で active slot をまとめて GPU に流す。

```text
batched sensory currents
 -> batched neuron step
 -> batched plasticity step
 -> batched trace step
 -> gather MN spikes for all active slots
 -> one compact readback
```

現在の「1 fly ごとに GPU submit -> readback wait」を N 回行うより、GPU occupancy と同期コストを改善する。

### 9.4 transaction commit も GPU

終了 slot の transaction を global weight buffer へ適用する compute pass を用意する。

commit 完了後、その slot の local neural/plasticity state を reset し、最新 global weight version から next episode を開始する。

## 10. CPU / MuJoCo 実装

各 slot は独立した body / environment state を持つ。

CPU 側は複数 slot の:

- retina / sensory encoding
- peripheral update
- MuJoCo physics
- collision / gate event
- telemetry aggregation

を並列実行する。

候補:

```text
A. Rust orchestrator + worker threads
B. Python multiprocessing
C. MuJoCo の batched / vectorized execution が利用可能ならそれを比較
```

最終形は GIL と IPC overhead を避けるため、Rust scheduler を優先候補とする。

## 11. CPU/GPU pipeline

理想的には、全 slot を完全 lockstep に待たせない。

概念:

```text
CPU slot workers produce sensory batch
              |
              v
GPU batched CNS step
              |
              v
compact motor readback
              |
              v
CPU slot workers: periphery + physics + events
              |
              +--> finished slots: transaction commit + immediate restart
              |
              +--> active slots: next tick
```

episode が短い worker は、長い worker の episode 終了を待たずに次 episode へ進む。

これが asynchronous training の中心である。

## 12. curriculum は global experience distribution として扱う

初稿の「各 worker が独立 curriculum を永久に持つ」案は撤回する。

canonical shared-weight learner では、curriculum も基本的に共有 learning state に属する。

ただし全 worker に同一 spawn condition を強制する必要はない。

`CurriculumState` は現在の能力に応じた **経験分布**を持ち、新しい episode を開始する worker がそこから条件を sample する。

例:

```text
current curriculum distribution
  spawn_x range
  spawn_z range
  initial_vx range
  gate stage mixture
  environment seed distribution
```

終了 episode が rolling statistics を更新し、十分な件数が溜まった時だけ distribution を hard/easy 方向へ動かす。

単発 episode 1 件で即座に難易度を動かす現行方式は bootstrap 用に残し、本格 training では window-based scheduler に置き換える。

## 13. stage success の定義

現在の `passed_gates > 0` だけをいつまでも curriculum success にしない。

例:

### Stage A

- first gate pass
- post-gate survival / minimum forward progress を併記

### Stage B

- second gate への到達または通過
- first gate 後の即衝突を failure とする

### Stage C

- multi-gate sustained flight

### Stage D

- full course / randomized geometry

ただし curriculum success は外部 reward ではない。

PAM / PPL1 刺激規則とは分離し、episode sampling difficulty を決めるだけとする。

## 14. training と evaluation を分離する

shared global weight の一定 version ごとに frozen snapshot を作る。

その snapshot から evaluation worker を起動し、

- plasticity off
- reinforcement off
- 固定 seed / 固定 spawn

で評価する。

training worker の global weight は evaluation によって変更しない。

これにより、

- curriculum が易しくなった
- 初速が偶然よかった
- 実際に learned weight が改善した

を分離する。

## 15. control experiments は別 shared learner として並列化する

学習成立を主張するには `docs/experiments.md` の control が必要である。

少なくとも:

```text
A. normal contingent PAM/PPL1 + plasticity
B. plasticity off
C. DAN / neuromodulation off
D. non-contingent stimulation
E. yoked control
```

を走らせる。

これは 1 つの global weight を共有させるという意味ではない。

**各 experimental condition は別々の shared learner / GlobalWeightStore を持つ。**

同一 initial checkpoint から分岐し、条件内では複数 Fly worker がその条件の global weight へ非同期に経験を commit する。

## 16. checkpoint / provenance

checkpoint には最低限:

```text
global weights
global weight version
commit sequence
curriculum state
training condition
code SHA
source snapshot hash
plasticity rule/version
commit semantics version
RNG / sampler state
```

を保存する。

各 commit record には:

```text
commit_seq
worker_id
episode_id
source_weight_version
commit_weight_version
staleness
transaction summary
reward/PAM event count
aversive/PPL1 event count
behavior summary
seed / environment condition
```

を残す。

非同期実行では wall-clock scheduling により commit 順序が変わり得るため、**実際の commit order を研究データとして記録する**。

完全 replay が必要な場合は commit log を使う。

## 17. 最初の実装順

### P0: serial reference を固定

現在の `population=1` trainer を reference semantics として固定する。

- deterministic small fixture
- CPU/GPU equality
- known plasticity transaction fixture
- checkpoint/resume equality

### P1: plasticity transaction API

現在の GPU plasticity update から、episode-local transaction を同時生成できるようにする。

必要 API の概念:

```text
begin_episode_from_global(version)
step_local(...)
finish_episode() -> PlasticityTransaction
commit_transaction(transaction) -> new_global_version
```

### P2: 2 worker asynchronous prototype

まず 2 Fly worker だけで実装する。

確認:

- weight averaging が一切ない
- stale worker が最新 global weight を上書きしない
- completion order に従って transaction が commit される
- finish した slot が即座に最新版で再開する

### P3: GPU batching

2 worker で意味を固定してから、N worker の neuron/plasticity/MN gather を batched dispatch にする。

### P4: CPU body parallelism

retina / periphery / MuJoCo を並列化する。

### P5: dynamic population sizing

M1 16 GB で:

```text
population = 1, 2, 4, 8, ...
```

を測定し、

- episodes/hour
- control steps/s
- simulated biological seconds/hour
- GPU utilization
- CPU utilization
- unified memory
- staleness distribution

から最適 worker 数を決める。

### P6: controls + frozen evaluation

normal/control learners と定期 frozen evaluation を同時運用する。

## 18. acceptance criteria

新方式を canonical にする最低条件:

1. `population=1` で旧 trainer と一致する。
2. 2 worker test で、各終了 transaction がその時点の最新 global weight に順序通り適用される。
3. worker の stale final weight が global を上書きしない。
4. weight averaging が存在しない。
5. topology / biological mappings / reinforcement semantics が変わらない。
6. CPU/GPU reference test が通る。
7. throughput が `population=1` より実測で改善する。
8. frozen evaluation で学習進行を測定できる。
9. staleness と commit order が記録される。
10. control conditions と比較可能である。

## 19. この方式の限界

この方式は高速だから正しい、という扱いはしない。

特に:

- worker が episode 中に global weight の途中更新を見ない
- transaction は stale trajectory から生成される
- population を増やしすぎると staleness が増える
- wall-clock completion order が学習 history に影響する

という差がある。

したがって population=1 reference を残し、非同期 population と定量比較する。

一方で、これらの問題は「weight を独立にして後で平均する」理由にはならない。

canonical parallel training の目的は、**複数の同時 episode から得られた局所可塑性経験を、1 本の共有 learned weight history へ非同期に積み上げること**である。

## 20. レビュアーへの確認依頼

他の LLM / reviewer には少なくとも以下を攻撃的に検証してほしい。

1. episode-local plasticity transaction を最新 global weight へ rebase する意味は、現行 plasticity rule に対して正しいか。
2. additive + clamp transaction の要約式に反例がないか。
3. eligibility / modulation / trace を worker-local とする境界は妥当か。
4. transaction commit を GPU 上で効率的に実装できるか。
5. full local synapse state × worker 数の memory cost をどう削減できるか。
6. M1 Metal/WGPU で batched dispatch が実際に速くなるか。
7. MuJoCo 複数 instance の並列実行で thread/process のどれが最適か。
8. asynchronous staleness が学習挙動をどの程度変えるか。
9. global curriculum distribution の更新則は経験生成を偏らせすぎないか。
10. population=1 reference と asynchronous population の比較で、何を同値性指標にすべきか。
11. 現行の biological constraints を破っている箇所がないか。
12. より単純で高 throughput な構成があるなら何か。

この文書は実装確定仕様ではない。レビューで反例・欠陥・より良い構成が見つかった場合は、実装前に修正する。
