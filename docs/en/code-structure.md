# Code structure

[English](code-structure.md) · [日本語](../ja/code-structure.md) · [简体中文](../zh-CN/code-structure.md)

This document describes the current developer-facing responsibility boundaries. It is not a claim that historical artifacts were generated by the current code.

## Production training path

```text
scripts/dev/train_flyppy_population.sh
  -> scripts/embodiment/train_flyppy_population_packed.py   (thin CLI)
  -> virtual_fly.training.population_packed                 (packing/runtime selection)
  -> virtual_fly.training.population_process                (episode orchestration)
       -> virtual_fly.training.flyppy_config                (CLI/config validation + provenance)
       -> virtual_fly.training.curriculum*                  (reset-condition scheduling only)
       -> virtual_fly.training.checkpointing                (global-weights-only persistence)
       -> virtual_fly.runtime.neural_bridge                 (Rust population runtime IPC)
       -> virtual_fly.runtime.packed_*                      (MuJoCo process boundary)
            -> virtual_fly.embodiment.factory               (physical stack construction)
                 -> virtual_fly.embodiment.body             (versioned FlyBody seams)
                 -> virtual_fly.embodiment.retina/haltere   (sensory transduction)
                 -> virtual_fly.embodiment.periphery        (individual-MN peripheral state)
```

The shell filename `train_flyppy_v3_population.sh` is retained only as a compatibility wrapper. The generic production entry point is `train_flyppy_population.sh`.

## Scientific contracts

`virtual_fly.semantics` names compatibility-sensitive contracts such as:

- MaleCNS/class-DAN semantics;
- neural/plasticity semantic versions;
- population checkpoint and aggregate neural-step meanings;
- haltere artifact kinds;
- direct-ray production K;
- body versions and their non-linear historical lineage.

`virtual_fly.reproducibility` validates and records those contracts; it does not define a different learning rule.

## Body lineage

Body version numbers are historical labels, not a linear inheritance chain:

```text
v3
└─ v4
   ├─ v5
   ├─ v6
   └─ v7

v8 = v6 + v7 neutral-trim mixin
```

The implementation is under `virtual_fly.embodiment.body`. The compatibility files under `scripts/embodiment/flybody_v*_adapter.py` only re-export the package implementations.

## Runtime versus pure/configuration code

- `virtual_fly.embodiment`: physical model, environment, sensors and peripheral state.
- `virtual_fly.training`: curriculum, shared-weight orchestration, checkpoint/restart contracts.
- `virtual_fly.runtime`: subprocess/GPU/telemetry side-effect boundaries.
- `virtual_fly.playback`: frozen capture/evaluation orchestration.
- `virtual_fly.reporting`: stable machine-readable report/history contracts.
- `virtual_fly.reproducibility`: hashes, provenance and semantic validation.

Pure scheduling/configuration functions are kept outside MuJoCo/GPU/subprocess lifetime where practical so they can be unit-tested without starting the simulator.

## Legacy and diagnostics

`virtual_fly.legacy` contains historical runtime mechanisms that are not in the production path. The DNg02 population decoder is currently the explicit example.

Historical and diagnostic scripts remain under `scripts/analysis` and `scripts/embodiment` because they are useful for reproducing or interrogating earlier experiments. Many still import the old script module names; those names are compatibility shims and should not be used by new production code.

In particular:

- `train_flyppy_curriculum.py`: historical serial trainer;
- `train_flyppy_population.py`: in-process reference/diagnostic population trainer;
- `evaluate_flyppy.py`: historical/diagnostic evaluator;
- `scripts/analysis/*`: probes, audits, benchmarks and report exporters, not behavior controllers.

The DLM/DVM aggregate and other calibrated/handwritten peripheral mechanics that remain in the current body adapters are **not** classified as legacy merely because they are engineering approximations; they remain part of current physical semantics.

## Python / Rust boundary

Python owns experiment orchestration, physical embodiment, sensory transduction, curriculum and provenance. Rust owns the large MaleCNS neural runtime, including neural dynamics, modulation, eligibility and weight updates. Communication is by body-ID currents/events and explicit checkpoint/transaction protocols; the viewer is read-only.

## Derived embodiment artifacts

Current production-generated embodiment artifacts must not overwrite historical artifacts that were used by earlier experiments. In particular:

- historical v7 neutral trim: `artifacts/embodiment/wing-pattern-neutral-trim-v1.*`;
- current provenance-validated production neutral trim: `artifacts/derived/wing-pattern-neutral-trim-v1.*`.

`train_flyppy_population.sh` generates the current artifact only when the current pair is absent and passes its path explicitly through the typed body configuration. Historical replay may still name the historical artifact explicitly, subject to the legacy provenance opt-in. The numeric v7 trim itself is unchanged; the path separation protects provenance rather than changing body mechanics.
