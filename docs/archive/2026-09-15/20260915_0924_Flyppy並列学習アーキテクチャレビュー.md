## 1. 目的

この文書の目的は、`virtual-fly` の現在の生物学的・物理的モデルを維持しながら、Flyppy が有用な学習状態へ到達するまでの **wall-clock time を可能な限り短縮すること**である。

並列化手法そのものを研究することは目的ではない。

また、単純に simulated seconds/s や episodes/hour を最大化することだけを目的としない。最終的な主KPIは、固定した評価条件における所定の学習到達基準までの wall-clock time とする。

```text
primary KPI:
  wall-clock time to predefined frozen-evaluation threshold

secondary KPI:
  control steps / s
  neural steps / s
  simulated biological time / wall-clock second
  GPU busy ratio
  CPU busy ratio
  memory bandwidth
```

episode長は学習状態やcurriculumで変わるため、`episodes/hour` は補助指標に留める。

最適化にあたっては、以下を勝手に変更しない。

```text
MaleCNS topology
sensory mapping
motor mapping
plasticity equation
reinforcement semantics
physics timestep
closed-loop timing
body model
course physics
```

ただし、同じ数式・同じ物理・同じ局所因果をより効率的に計算するための、

- graph compile
- state compression
- lazy evaluation
- kernel specialization
- batching
- native hot loop
- asynchronous I/O

は積極的に行う。

## 2. 結論

現時点で最速候補として採用する構成は、単純な episode 並列化でも、単純な multi-fly batching でもない。

まず **single-fly の1 control step / 1 neural stepを可能な限り安くする**。

推奨する階層は次である。

```text
Tier A: Reference runtime
  現行CPU/GPU順序を保持
  小規模fixtureで逐次f32 semanticsを確認

Tier B: Canonical fast single-fly
  runtime graph compile
  PlasticFastGraph
  fused neural + motor submit
  preallocated motor readback
  degree-aware / blocked / sparse propagation hybrid
  post-factorized lazy plasticity
  vectorized + pre-indexed retina
  native MuJoCo / periphery hot loop
  telemetry off / async
  async bulk checkpoint
  sustained autotuning

Tier C: Optional throughput expansion
  edge-major shared-topology multi-fly
  shared weight 1 copy
  slot-local neural/body/plasticity state
  CPU/GPU overlap
  sustained autotuned slot count
```

最も重要な変更点は、**multi-flyを最初に実装しない**ことである。

multi-flyは有力なthroughput拡張であるが、shared-weightで複数環境のplasticityを同時に適用する時点で、single-flyの1本の学習時間列とは異なる training schedule になる。

したがって canonical fast path はまず single-fly とする。

multi-flyは、single-fly fast runtime完成後に、実際に `wall-clock to useful state` を短縮することが確認できた場合に追加する。

## 3. 現行runtimeで確定している主要コスト

現在のGPU neural stepは概ね、

```text
neuron_step
-> plasticity_step
-> trace_step
-> queue.submit
```

である。

その後 motor readout が必要になると、別の gather encoder / submit / staging copy / map wait が発生する。

またtrainer側は、

```text
retina encode
-> neural bridge request
-> neural GPU step
-> synchronous motor readback
-> periphery
-> MuJoCo physics substep x 10
-> collision/course update
-> telemetry / trajectory
```

という直列鎖を持つ。

現時点で主要hotspot候補は以下である。

1. `plasticity_step` の全edge read-modify-write
2. `neuron_step` の全incoming edge scan
3. motor spike readbackの別submit + synchronous map wait
4. Python側のretina / periphery / MuJoCo hot loop
5. body telemetryの同期filesystem I/O
6. checkpoint時のfull GPU readbackとscalar I/O
7. Python↔Rust JSON subprocess往復
8. dense external current upload

順位はP0 profileで確定する。

未計測なのに「必ず1位」とは扱わない。

## 5. runtime graph compiler

source MaleCNS snapshotは変更しない。

起動時にruntime-only viewをcompileする。

### 5.1 FastGraph / DopamineGraph / IgnoredGraph

現行runtimeで実際に伝播へ寄与するedgeを、機能別に分ける。

```text
FastGraph
  fast neurotransmissionへ寄与するedge

DopamineGraph
  postsynaptic modulationへ寄与するdopamine edge

IgnoredGraph
  現行runtime equationsでは伝播にもplasticityにも寄与しないedge
```

source snapshotの完全性は保持する。

runtimeだけをspecializeする。

### 5.2 PlasticFastGraph

今回の独立レビューで追加された最重要最適化である。

現行modelでは、weight updateはpostsynaptic modulationを必要とする。

そこで、dopamine inputが構造的に到達し得るpostsynaptic neuron集合を、compile時に静的に求める。

```text
S_D = dopamine released edge を少なくとも1本受ける post neuron集合
```

fast edge `i -> j` について、`j` が `S_D` に属さないなら、正規状態ではそのpostのmodulationは常に0であり、そのedgeのweightは将来も変化しない。

したがって、plasticity対象を

```text
PlasticFastGraph
  = FastGraphのうち postがS_Dに属するedge
```

へ静的に縮約できる。

これはactivity sparsityとは無関係に成立する。

よって、generic sparse eligibility containerを最初から作る前に、まず

```text
E_fast
E_plastic
E_plastic / E_fast
```

を実測する。

`E_plastic` が十分小さい場合は、単純なdense `eligibility[E_plastic]` の方がhash/list型sparseより速い可能性が高い。

## 6. plasticity semantics

現行順序をreferenceとする。

edge `i -> j`、step `t`について概略:

```text
m_j(t) = alpha * m_j(t-1) + D_j(t)

L_ij(t)
  = x_i(t-1) * a_j(t)
  - x_j(t-1) * a_i(t-1)

e_ij(t) = beta * e_ij(t-1) + L_ij(t)

w_ij(t) = clamp(
    w_ij(t-1) + eta * m_j(t) * e_ij(t),
    0,
    M
)

x_i(t) = gamma * x_i(t-1) + a_i(t)
```

重要なのは、

```text
modulation update
-> eligibility decay + current local
-> weight update
-> trace update
```

の順序である。

current localを加えた後にeligibility全体へdecayを掛けてはいけない。

## 7. post-factorized lazy plasticity

### 7.1 基本方針

全plastic edgeを毎stepread-modify-writeしない。

まず `PlasticFastGraph` へ縮約し、その上でlazy化する。

### 7.2 local eventがない区間

local eventがないedgeでは、eligibilityは指数減衰するだけである。

```text
e(t+k) = beta^k * e(t)
```

modulationもdopamine eventがない区間では、

```text
m(t+k) = alpha^k * m(t)
```

である。

したがってevent-free区間のweight updateは幾何級数としてまとめられる。

### 7.3 dopamine eventがあってもedgeを即materializeしない

独立レビューの重要な追加点である。

同じpostsynaptic neuron `j` に入るplastic edgeは、modulation `m_j` を共有する。

local eventがないedgeについては、

```text
C_j = eta * Sum_r [m_j(r) * beta^r]
```

のようなpost-local accumulatorへ因数分解できる。

そのため、dopamine eventのたびに `j` へ入る全plastic edgeを触る必要はない。

edge側は、local eventまたはweight materializeが必要になる時点までlazyに保てる。

推奨状態の概念形は、

```text
PostPlasticState
  modulation
  modulation_timestamp
  integrated_factor

EdgePlasticState
  eligibility
  eligibility_timestamp
  integrated_post_factor_at_last_materialize
```

である。

最終的な表現はGPU memory trafficとlookup costで決める。

### 7.4 clamp

local-free区間中はeligibilityの符号が変わらず、normal stateではmodulationが非負なので、区間中のweight deltaの符号は固定される。

その区間については実数数学上、逐次clampを区間末尾1回へ畳み込める。

ただし、local eventによってeligibility符号が変化する可能性がある境界を跨いでまとめてはいけない。

正負deltaを単純sumして最後に1回clampする方式は一般には同値ではない。

### 7.5 f32 semantics

closed-form / `pow` / tree reductionは演算順を変える。

したがって、

```text
Reference mode
  current sequential f32 semantics

Fast semantic mode
  real-number equation preserving
  tight-tolerance regression
```

を分ける。

canonical trainingはfast semantic modeを使ってよいが、small fixtureでreferenceとの差を継続確認する。

bitwise replayを要求するdebug pathでは逐次f32を残す。

## 8. propagationは固定3-wayではなく複数候補を持つ

単一方式を最終解としない。

最低限、以下を候補にする。

### 8.1 DegreeBucketDense

postsynaptic neuronをindegree帯ごとにdispatch listへ分ける。

例:

```text
0-7
8-31
32-127
128-511
512+
```

post内部のincoming edge orderは変更しない。

目的はSIMD lane間のdegree skewを減らすことである。

### 8.2 BlockedIncoming / BitmapBlockedCSR

incoming `pre_indices` がpost内で整列していることを利用し、presynaptic neuron ID空間をblock化する。

active-pre bitmapと交差しないblockを丸ごとskipする。

```text
post row
  block 0: pre 0..127
  block 1: pre 128..255
  ...
```

medium-sparse領域で、CandidateIncomingやglobal compactionより低い固定費で勝つ可能性がある。

### 8.3 CandidateIncoming

active preのoutgoingからcandidate postをmarkし、そのpostだけincoming scanする。

中程度のsparsityでは有力。

ただし、candidate生成時にoutgoing edgeを触った後、高indegree candidateのincomingを再走査するため二重仕事になる場合がある。

### 8.4 ActiveEdgeFrontier

active presynaptic neuronのoutgoing edgeのみ展開し、edge contributionをpostごとにdeterministic reductionする。

ultra-sparse領域では触るedge数を最小化できる可能性がある。

一方で、

- compaction
- dedup
- sort / segmented reduction
- irregular memory
- global atomic / prefix

の固定費がある。

Apple GPUでは自動的に有利とはみなさない。

### 8.5 Optional row-parallel high-degree mode

P0/P2 profileでhigh-degree postが大きなtail latencyを作る場合のみ、high-degree rowを複数lane/workgroupで分割する方式を追加候補にする。

### 8.6 runtime selector

selectorは単純なactive neuron fractionだけを見ない。

最低限、

```text
A = active_pre_count
O = sum_out_degree(active_pre)
C = candidate_post_count
I = sum_in_degree(candidate_post)
P = plastic_active_edge_count
B = active blocked-row count
```

を利用する。

実activity trace replayから各modeの実測時間を集め、hardware/backendごとにthresholdを決める。

## 9. neuron dynamics自体のevent-driven化

edge workを減らした後もN-wide neuron passが支配的なら、neuron stateもtimestamp化できる。

入力がない非refractory neuronでは、

```text
v(t+k) = decay^k * v(t)
```

であり、trace/modulationも同様にlazy materializeできる。

候補active set:

```text
external-current neuron
postsynaptic target of active fast edge
postsynaptic target of active dopamine edge
refractory/event-boundary neuron
```

ただしevent queue / compaction / irregular accessの固定費があるため、最初からcanonical化しない。

P0/P3後にN-wide passが支配的なら追加する。

## 10. neural + motor readbackを1 submitへ融合

これは低リスクかつ優先度が高い。

現在は通常control stepで概ね、

```text
submit #1:
  neuron
  plasticity
  trace

submit #2:
  motor gather
  copy to staging

CPU waits map
```

となる。

これを、

```text
single command encoder:
  neuron
  plasticity
  trace
  motor gather
  copy motor output to persistent staging/ring

single submit
CPU waits once
```

へ変更する。

single-flyではmotorがphysicsの入力なので、completion dependencyそのものは消せない。

ただし、

- submit数
- encoder生成
- buffer生成
- bind group生成

を減らせる。

motor readback resourcesはrun開始時にpreallocateする。

## 11. reinforcement step batching

Python側では既に複数stepを1requestにまとめているが、Rust/GPU側では複数 `runtime.step()` が複数submitになる。

同じreinforcement stimulusをreadbackなしで4step進めるなら、

```text
one encoder:
  step 1 neuron/plasticity/trace
  step 2 neuron/plasticity/trace
  step 3 neuron/plasticity/trace
  step 4 neuron/plasticity/trace

one submit
```

にまとめる。

数式順序は保てる。

## 12. retina hot path

retinotopic mappingはrun中固定である。

したがって毎step、Pythonでbody IDを再解決し、可変長 `(body_id,current)` pair群をJSONで送る必要はない。

起動時に、

```text
ommatidium index
-> MaleCNS dense neuron index
```

をcompileする。

runtime間通信ではbody IDではなくdense indexを使う。

transductionも可能な限りvectorizeする。

測定時は、

```text
get_ommatidia_readouts()
Python/Numpy transduction
stimulus buffer construction
IPC serialization
```

を分ける。

GPUへ渡す刺激はcompact index/value bufferまたはfixed dense retinal bufferをprofileして決める。

## 13. Python / Rust / MuJoCo hot path

JSON subprocess round-tripは最終形として残さない。

ただしPyO3化だけをゴールにしない。

最終的に高いceilingを持つ構成は、

```text
Python
  experiment setup
  curriculum
  reporting
  offline analysis

Native hot loop
  retina transduction
  neural GPU dispatch
  motor gather
  periphery
  MuJoCo 50 us x 10 substeps
  course/collision event extraction
```

である。

MuJoCoのphysics timestepやsubstep間のwing/periphery torque updateは変えない。

単純に `mj_step(nstep=10)` へ置換してsubstep間の外力更新を消すのは同値ではない。

したがって、50 us × 10回の意味は保持しながら、そのloop全体をC/C++/Rust extension側へ移す。

PyO3は移行段階として使ってよい。

## 14. telemetry / trajectory

training defaultではviewer用body/neural telemetryをcritical pathから外す。

推奨:

```text
training default:
  telemetry OFF

visualization enabled:
  training hot loop
    -> bounded lock-free/ring queue
    -> writer thread/process
    -> filesystem
```

viewer processが別でも、producer側で同期filesystem writeしていればcritical pathに残る。

trajectoryもhot loopではcompact binary/ring bufferへappendし、episode後またはbackground writerでJSONLへ変換する。

## 15. checkpoint

full checkpointはtrainingを大きく止め得る。

改善する。

### 15.1 GPU側

checkpoint boundaryで、必要stateをdedicated snapshot bufferへGPU copyする。

その後のmap/disk I/Oはtraining critical pathから外す。

### 15.2 CPU側

4-byte scalarごとの `write_all` は廃止し、bulk/chunked writeへする。

```text
Vec<f32/u32>
-> byte slice
-> BufWriter / large chunk write
```

### 15.3 checkpoint種類

```text
full resume checkpoint
  full dynamic/plastic state

weight-only evaluation snapshot
  evaluation用weight中心
```

を分離する。

PlasticFastGraph導入後はcheckpoint schemaも、canonical fast modeとreference bitwise modeで必要状態を明確に分ける。

## 16. multi-flyの位置づけ

multi-flyは **optional throughput expansion** とする。

single-fly fast path完成前には実装しない。

### 16.1 shared weight

multi-flyを行う場合、weightは1 copyを共有する。

workerごとのfull weight copyはM1 16GB unified memoryとbandwidthの両方で不利である。

### 16.2 slot-local state

slot-localに必要なのは概ね、

```text
membrane
refractory
activity event / spikes
trace
modulation
eligibility / lazy plastic state
body state
retina adaptation
periphery state
course state
```

である。

eligibilityはまず `E_total` ではなく `E_plastic` に縮約する。

その上で、

```text
sparse
hybrid sparse/dense
dense
```

をactivityに応じて選ぶ。

### 16.3 sparse eligibilityの最悪ケース

sparse entryは、

```text
edge_id
value
timestamp
metadata
```

を持つため、active率が高くなるとdense f32 arrayよりメモリもbandwidthも悪くなり得る。

epsilon thresholdで勝手に消すのは意味変更になる。

したがってdense fallbackを持つ。

### 16.4 edge-major across environments

multi-flyではslot-major graph再走査ではなく、edge-major layoutを優先候補にする。

```text
for edge e:
  topology / shared weight を1回読む
  active slot maskを得る
  slot-local contribution / plastic stateを処理
```

shared topology/weight bandwidthを複数環境で本当に共有するためである。

### 16.5 weight apply

同一edgeに複数slotのplasticity updateがある場合、clampを含む更新順序を定義する必要がある。

canonical multi-fly scheduleでは、固定slot順など再現可能な順序を採用する。

```text
w = shared_weight[e]
for slot in deterministic order:
  w = clamp(w + delta[e,slot], 0, M)
shared_weight[e] = w
```

これをslotごとの別dispatchで行わず、edge invocation内で処理する。

ただし、このmulti-fly schedule自体はsingle-fly learnerの時間列と同一ではない。

したがって「exact single-fly」とは呼ばない。

## 17. CPU/GPU overlap

multi-flyを導入した場合、slot群をmicrobatch化してCPU/GPUを重ねる。

```text
GPU: CNS batch A
CPU: physics / retina batch B

swap

GPU: CNS batch B
CPU: physics / retina batch A
```

single slot内では、

```text
sensory
-> CNS
-> motor
-> physics
-> next sensory
```

の因果順序を維持する。

## 18. Apple M1 / 16GB前提

M1ではcapacityだけでなく、

- unified memory bandwidth
- GPU/CPU competition
- irregular sparse access
- global atomics
- buffer map latency
- sustained thermal behavior

を重視する。

特にper-slot edge stateは高価である。

E≈25.6Mを説明用概算に使うと、

```text
4 byte * E ≈ 97.7 MiB
8 byte * E ≈ 195.3 MiB
```

である。

neuron stateよりedge stateが圧倒的に大きい。

worker数は固定で決めない。

```text
1, 2, 4, 8, ...
```

を短時間だけでなくwarm-up後の持続性能でも測る。

## 19. direct Metal

wgpu on macOSはすでにMetal backendを利用する。

したがってdirect Metal化は「Metalを使い始める」ことではなく、wgpu/WGSL abstractionを外すことである。

以下が実測で制約になった場合のみ検討する。

```text
WGSL atomic制限
persistent execution不足
buffer synchronization ceiling
workgroup specialization不足
frontier / blocked kernel表現力不足
```

全edge scanのままdirect Metalへ移植しても根本解決にはならない。

## 20. autotuning

固定thresholdをハードコードしない。

実activity replayを用いて、hardware/backendごとに以下を選ぶ。

```text
propagation mode
workgroup size
blocked row size
degree bucket boundaries
sparse/dense plasticity threshold
slot count
microbatch size
readback strategy
```

ただしstartupの数秒だけでなく、sustained loadで性能が変わる項目については長めの再評価を行う。

M1ではthermal / unified-memory contentionがあるためである。

## 21. 実装優先順位

### P0: profile + 即時低リスク改善

同じphaseで行う。

1. control-step wall-clock breakdown
2. GPU timestamp / Metal trace
3. motor gather buffer preallocation
4. neural + motor gatherを1 submitへ融合
5. reinforcement複数stepを1 submitへ融合
6. training telemetry default OFF
7. checkpoint scalar writeをbulk writeへ変更
8. retinal body IDを起動時dense index化
9. exact neuron / edge countをrun metadataへ保存
10. request / response byte数を測定

### P1: runtime graph compile

1. FastGraph
2. DopamineGraph
3. IgnoredGraph
4. `S_D`
5. PlasticFastGraph
6. outgoing adjacency
7. degree buckets
8. blocked CSR descriptors

この時点で `E_plastic / E_fast` を確認する。

### P2: propagation低リスクmode

1. DegreeBucketDense
2. BlockedIncoming
3. current DenseIncomingとのtrace replay benchmark

まず irregular global compactionを必要としない方式から試す。

### P3: plasticity最適化

1. `PlasticFastGraph`上のdense eligibility baseline
2.正しい decay -> local -> weight fixture
3. lazy eligibility
4. post-factorized modulation/integrated factor
5. event-free closed-form integration
6. sparse/dense hybrid
7. sparse reset
8. tolerance-based reference validation

`E_plastic` が十分小さければ、generic sparse containerを無理に導入しない。

### P4: advanced propagation

1. CandidateIncoming
2. ActiveEdgeFrontier
3. deterministic segmented reduction
4. optional high-degree row-parallel mode
5. degree-weighted runtime selector

### P5: retina / IPC / native hot loop

P0 profileで支配的なものから実施する。

1. vectorized retina transduction
2. compact/fixed binary stimulus protocol
3. JSON subprocess除去
4. PyO3等によるin-process bridge
5. native periphery
6. native MuJoCo 10-substep loop
7. course/collision eventのnative抽出

### P6: neuron-level event-driven mode

N-wide neuron passが残存bottleneckの場合のみ。

1. timestamp membrane
2. active neuron set
3. refractory/event-boundary handling
4. dense/event mode selector

### P7: canonical fast single-fly完成

ここで、

```text
frozen evaluation thresholdまでのwall-clock
```

を現行baselineと比較する。

parallelization研究ではなく、単に最適化の効果確認として行う。

### P8: optional shared-weight multi-fly

single-fly fast path後もthroughput余地がある場合のみ。

1. shared weight 1 copy
2. slot-local neural/body state
3. `E_plastic` based plasticity state
4. edge-major slot processing
5. active slot mask
6. deterministic edge-local slot-order apply
7. shared `mjModel` + per-slot `mjData` が可能か確認
8. CPU/GPU microbatch overlap

## 25. 最終判断

現在の最優先事項は、worker数を増やすことではない。

最初に、

```text
1匹の1 control stepで本当に必要な計算だけをする
```

runtimeへ変える。

そのための中心は、

```text
PlasticFastGraph
post-factorized lazy plasticity
DegreeBucket / Blocked / Candidate / Frontier hybrid propagation
one-submit neural+motor path
vectorized retina
native physics hot loop
async I/O
```

である。

特に `PlasticFastGraph` は、activity sparsityに依存せずplasticity対象edgeを静的に縮約できる可能性があるため、最初に確認すべきである。

multi-flyはその後でよい。

single-fly runtimeが十分高速になったあと、複数環境を同時に回すことが本当に `wall-clock to useful state` を短縮するなら、edge-major shared-topology方式として追加する。

最終的な設計判断は、見た目の高度さではなく、

```text
同じvirtual-flyの意味を維持したまま
有用な学習状態へ何分・何秒で到達するか
```

で決める。
