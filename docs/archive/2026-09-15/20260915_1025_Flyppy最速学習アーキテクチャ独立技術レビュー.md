## 1. 総合判定

**判定: 現在案は「方向性は良いが、そのまま実装してはいけない」。再設計してから実装するべきである。**

`20260915_0924_...` は前案より大幅に改善されている。特に、multi-fly を最初に実装しない、同期点・I/O・Python/MuJoCo hot loop を見る、Fast/Dopamine graph を分離する、sparse/dense を固定観念で決めない、direct Metal を最後に回す、という判断は妥当である。

しかし「wall-clock 最短」を目的にすると、まだ重要な取りこぼしがある。

1. **全 fast edge を一般的な sparse/lazy plasticity の対象にする前に、構造上 weight が絶対に変化し得ない fast edge を静的に除外できる。** 現行方程式から数学的に証明できる。これは現在案にない。
2. **lazy plasticity は dopamine event でも必ず materialize する必要がない。** 現行 modulation が正規状態で常に非負であることを使うと、postsynaptic neuron ごとの共通積分へさらに因数分解できる。
3. **3-way propagation は十分ではない。** Apple GPU では global compaction/sort/reduction を伴う ActiveEdgeFrontier より、`BlockedIncoming` と degree-bucketed pull が速い領域が十分あり得る。しかも incoming edge order を維持しやすい。
4. **shared-weight multi-fly を「exact」と呼ぶのは不適切である。** それは選んだ multi-fly 更新則に対して deterministic にはできるが、現在の single-fly learner の学習軌道と同値ではない。time-to-useful-state を短縮する可能性はあるが、意味論上は別の training schedule である。
5. **最も確実な低リスク改善がまだ先にある。** 現在は通常 control step だけで neural submit と motor gather submit の2回があり、その後 synchronous map wait がある。さらに telemetry は body state を毎 control step 同期 filesystem write している。ここは複雑な sparse kernel より先に削るべきである。
6. **retina hot path が過小評価されている。** static mapping なのに Python で column / body ID を毎step走査し、その多数の body ID/current pair を JSON IPC している。数式・生物学的意味を変えずに vectorize / pre-index できる。

したがって最速候補は、現在案のままの

```text
3-way propagation
+ generic sparse eligibility
+ shared-weight multi-fly
```

ではなく、まず

```text
single-fly equation-preserving runtime
  + structural graph specialization
  + plastic-capable edge pruning
  + fused submission/readback resources
  + blocked/degree-aware propagation
  + post-factorized lazy plasticity
  + vectorized/native body hot path
```

を完成させ、その後に必要なら **edge-major shared-topology multi-environment** を追加する構成である。

## 4. 現行 runtime の正確な1 step意味論

### 4.1 GPU command ordering

**[確定]** `GpuRuntime::step()` は1 command encoder / 1 compute pass内で:

```text
neuron_step
-> plasticity_step  (plasticity enabled時)
-> trace_step
-> queue.submit
```

の順である。

その後 trainer が motor output を要求すると、`read_spikes_at()` が別の encoder / submit で gather + staging copy を行い、`map_async` 後 `device.poll(Wait)` でCPUを待たせる。

### 4.2 数式

edge `i -> j`、step `t` について、`a` を signed activity event、`x` を activity trace、`m` を postsynaptic modulation、`e` を eligibility とする。

現行実装は:

```text
m_j(t) = alpha * m_j(t-1) + D_j(t)

L_ij(t)
  = x_i(t-1) * a_j(t)
  - x_j(t-1) * a_i(t-1)

e_ij(t) = beta * e_ij(t-1) + L_ij(t)

w_ij(t) = clamp(
    w_ij(t-1) + eta * m_j(t) * e_ij(t),
    0,
    M
)

x_i(t) = gamma * x_i(t-1) + a_i(t)
```

である。

default:

```text
alpha = 0.98
beta  = 0.995
gamma = 0.95
eta   = 0.00001
M     = 1000
```

**[確定]** dopamine input は positive depolarizing event のときだけ加算され、負の dopamine current は現在の model には存在しない。episode reset は modulation / trace / eligibility を0へ戻し、weightだけを保持する。

## 5. plasticity 数式検証

### 5.1 local eventなし・dopamine eventなし

**[証明]** 完了済みstep `t0` の直後を `m0,e0,w0` とし、以後K stepで `L=0`, `D=0` とする。

```text
m_r = alpha^r m0
e_r = beta^r e0
q = alpha * beta
```

したがって clamp 前の総更新は:

```text
Delta_w
  = eta * m0 * e0 * Sum[r=1..K] q^r
  = eta * m0 * e0 * q * (1 - q^K) / (1 - q)
```

defaultでは `q = 0.9751`。

正規状態では `m >= 0`, `alpha>0`, `beta>0` なので、この区間内で更新の符号は変わらない。したがって **実数数学上** は逐次 clamp と区間末尾1回の clamp の最終値は同じである。

### 5.2 dopamine eventなし・localのみ発生

**[証明]** local event直前までを lazy materialize し、そのstepでは順序を必ず:

```text
m_t = alpha*m_(t-1)
e_t = beta*e_(t-1) + L_t
w_t = clamp(w_(t-1) + eta*m_t*e_t)
```

とする。localを足してから全体へbetaを掛ける方式は誤りである。

### 5.3 dopamineのみ発生

**[証明]** `L_t=0`, `D_t>0` なら:

```text
m_t = alpha*m_(t-1) + D_t
e_t = beta*e_(t-1)
w_t = clamp(w_(t-1) + eta*m_t*e_t)
```

となる。

重要なのは、**dopamine eventだから全incoming edgeを即 materializeする必要はない**ことである。

正規状態では `m_t >= 0` が常に成り立つ。あるedgeにlocal eventがない区間では `e` の符号は変わらないため、dopamine eventを含んでいてもweight更新の符号は変わらない。

local-free区間 `r=1..K` では:

```text
e_r = beta^r e0
C_j = eta * Sum[r=1..K] (m_j(r) * beta^r)

w_K = clamp(w_0 + e0 * C_j, 0, M)
```

と書ける。

`C_j` は **同じpostsynaptic neuron jへ入る全edgeで共通**である。よって dopamine dynamics は post-local accumulator / transform として更新し、edge stateはlocal eventまたはweight read時までmaterializeしない構成が可能である。

これは現在文書の「localもdopamineもない区間だけ closed-form」という案より広い。

### 5.4 localとdopamineが同step

**[証明]** current stepの dopamine input を先に modulationへ入れ、その後 eligibility decay + local、最後にweight updateである。

```text
m_t = alpha*m_(t-1)+D_t
e_t = beta*e_(t-1)+L_t
w_t = clamp(w_(t-1)+eta*m_t*e_t)
```

trace updateはその後なので、`L_t` には `x(t-1)` を使う。

### 5.5 clampへ到達する場合

local-free区間では更新符号が固定なので、実数数学上は区間末尾の1 clampへ畳み込める。

しかしlocal eventで `e` の符号が変わる可能性がある境界を跨いでまとめてはいけない。

### 5.6 正負更新が混ざる場合

単純にdeltaをsumして最後に1回clampする方式は同値でない。

具体例:

```text
M = 1
w = 0.9
d1 = +0.3
d2 = -0.2

逐次:
  clamp(0.9 + 0.3) = 1.0
  clamp(1.0 - 0.2) = 0.8

sumして最後にclamp:
  clamp(0.9 + 0.3 - 0.2) = 1.0
```

したがって mixed-sign / clamp boundary を跨ぐ transaction は時系列順を保存する必要がある。

### 5.7 実数数学同値と f32 bitwise同値

**[証明]** closed form / `pow` / tree reduction は演算順を変えるので、一般に f32 bitwise一致しない。

実例として default `alpha=0.98`, `beta=0.995`, `eta=1e-5` で、

```text
m0 = 63.6961687
e0 = -46.0426572
w0 = 40.9735239
K  = 77
```

をf32逐次更新すると `39.989820`、closed-formをf32評価すると `39.989822` となり、1 ULP級の差が出る。

したがって runtime は少なくとも:

```text
reference/replay path:
  現行edge順・逐次f32

fast semantic path:
  実数方程式同値、toleranceでreference比較
```

を分けるべきである。

## 6. 現在案にない最重要最適化: PlasticFastGraph

これは今回のレビューで最も重要な追加提案である。

### 6.1 構造上、絶対にweightが変わらないpostを静的に判定できる

postsynaptic neuron `j` に対し:

```text
S_D = { j | dopamine neuronからjへのreleased edgeが1本以上ある }
```

とする。

**[証明]** episode reset後 `m_j(0)=0`。`j not in S_D` なら全stepで `D_j(t)=0` なので帰納法により:

```text
m_j(t)=0
```

が常に成立する。

したがって `j not in S_D` へ入る任意のfast edgeについて:

```text
Delta_w = eta * m_j(t) * e_ij(t) = 0
```

であり、**weightはepisode中も将来episodeでも一度も変化しない。**

これは activity sparsity に依存しない、静的かつ厳密な性質である。

### 6.2 compile時に分けるべきgraph

```text
FastGraph
  propagationに使う全fast edge

PlasticFastGraph
  FastGraphのうち post in S_D のedgeだけ

DopamineGraph
  modulation input用

IgnoredGraph
  current equation上fastにもdopamineにも使わないedge
```

とする。

profileでまず記録すべきなのは:

```text
E_total
E_fast
E_dopamine
N_potential_modulated_post = |S_D|
E_plastic = sum fast_in_degree(j), j in S_D
E_plastic / E_fast
```

である。

もし `E_plastic << E_fast` なら、一般的な sparse hash/list を実装する前に dense `eligibility[E_plastic]` へ縮めるだけで大きく勝てる可能性がある。

### 6.3 checkpointとの注意

現行コードは modulation=0 のpostへ入るfast edgeでも eligibility 自体は更新して保存する。したがって、その semantically dead eligibility を完全に捨てると **現行checkpointの内部配列までbitwise同じ**ではなくなる。

ただしそのeligibilityは現在の正規状態ではweightにもneural dynamicsにも将来影響できない。

よって:

- full internal-state bitwise replay modeでは保持する
- canonical fast modeでは「将来挙動に影響する状態」だけを保持する新checkpoint schemaへする

のどちらかを明示するべきである。

## 7. propagation方式の再評価

現在案の3方式は方向としては正しいが、最速候補集合として不足する。

### 7.1 DenseIncoming

現在は1 post = 1 GPU invocationで、そのpostのincoming CSRを直列走査する。

長所:

- edge順がsource CSR順のまま
- coalescingしやすい部分がある
- compaction / sort不要
- dense activityでは強い可能性

短所:

- indegree skewが大きいと同一SIMD内でlaneの実行時間が大きくずれる
- inactive preでも`pre_indices`は全edge読む

### 7.2 CandidateIncoming

active preからoutgoingでcandidate postをmarkし、candidateだけincoming scanする。

中程度のsparsityでは有力。ただし:

```text
outgoingを一度読む
+ candidate dedup/mark
+ candidate postのincomingを再走査
```

となるので、高indegree candidateが少数あると二重仕事が大きい。

### 7.3 ActiveEdgeFrontier + segmented reduction

ultra-sparseでは触るedgeを最小化できる可能性がある。

しかし Apple GPU 上では:

- compaction
- key generation
- sort/group
- segmented reduction
- global atomic / counter contention
- irregular access

が固定費になる。

さらに **deterministic reduction = 現行f32順序と同じ**ではない。reduction treeが変われば丸め順が変わる。実数数学上は同値でも、bitwise modeでは現行のpost内edge順を再現しなければならない。

### 7.4 追加すべきMode D: DegreeBucketedIncoming

postをindegree帯ごとに並べたdispatch listをcompileする。

```text
0-7
8-31
32-127
128-511
512+
```

等へ分け、同一wave/workgroupで近いrow lengthを処理する。

edge自体の順序は変えないため、post内部の加算順を維持できる。

**[有力推定]** M1のようなSIMD GPUでは、単純DenseIncomingよりdivergenceを減らし、frontier方式より低い固定費で勝つ領域があり得る。

### 7.5 追加すべきMode E: BlockedIncoming / BitmapBlockedCSR

`prepare_malecns.py` はedgeを `(post, pre)` でsortするので、各postの `pre_indices` は昇順である。

これを利用し、pre neuron ID空間を例えば64/128/256単位のblockへ分ける。

```text
post row
  block 0: pre 0..255 のedge range
  block 1: pre 256..511 のedge range
  ...
```

active-pre block bitsetを作り、inactive blockを丸ごとskipする。

長所:

- global edge sort不要
- candidate dedupを小さくできる
- active edge frontierほどirregularにならない
- post内edge順を保ちやすい
- degreeが大きいpostでもinactive領域を粗粒度skipできる

**[有力推定]** Apple GPUでは、medium-sparse領域でCandidateIncoming/Frontierより有力な可能性がある。

### 7.6 selectorに必要な指標

単純なactive neuron率では不足する。

最低限:

```text
A_pre = active presynaptic neuron count
W_out = Sum out_degree(active_pre)
C_post = candidate postsynaptic count
W_in = Sum in_degree(candidate_post)
C_edge = actual nonzero edge contribution count

post indegree p50/p90/p99/max
candidate post indegree distribution
active pre degree distribution
active block count / scanned block count
frontier compaction bytes
sort/group bytes
segmented-reduction time
dedup time
atomic contention proxy
cache / memory bandwidth counters
```

を使う。

modeは3固定ではなく、少なくとも:

```text
DegreeBucketDense
BlockedIncoming
CandidateIncoming
ActiveEdgeFrontier
```

を実trace replayで比較し、必要ならhigh-degree postだけrow-parallel化する第5方式を追加する。

## 8. event-driven simulation の可能性

現在案はedge workをevent-driven寄りにするが、neuron stateはまだもっとlazy化できる。

### 8.1 neuron dynamicsもtimestamp化可能

入力がない非refractory neuronは:

```text
v(t+k) = membrane_decay^k * v(t)
```

であり、純粋なdecayだけではthresholdを新規にcrossしない。

refractoryも「残りstep数」をtimestampから計算できる。trace/modulationも同様にlazy化できる。

したがって理論上は:

```text
external-current neuron
+ incoming contributionを受けるcandidate neuron
+ refractory/event boundary neuron
```

だけをmaterializeする event-driven CNS が構成できる。

### 8.2 採用判断

**[要profile]** event densityが低いなら、N-wide neuron passまで削れるため大幅高速化候補である。

一方で activity が広がる場合、event queue / bitset / compaction / irregular memory の固定費でdenseに負ける。

よってevent-drivenを「最善」と決めず、dense/block/event modeの1つとしてtrace replayで評価する。

## 9. shared-weight multi-fly 評価

### 9.1 「exact」の意味を修正すべき

現在のsingle-fly learnerでは、step/episodeが1本の時間列でweightへ作用する。

multi-flyで同じstepに複数環境のdeltaをslot順適用すると、選んだmulti-fly規則自体はdeterministicにできるが、**現在のsingle-fly learnerと同じ学習過程ではない。**

したがって分類は:

```text
single-fly fast runtime:
  現行learnerの意味保存高速化

shared-weight multi-fly:
  biological equationsは各slotで保持するが、
  experience/weight update scheduleは変更するtraining architecture
```

とするべきである。

wall-clock to useful state が本当に短くなるなら採用価値はあるが、「exactだから当然採用」ではない。

### 9.2 weight 1 copy

multi-flyを行う場合、shared weight 1 copy自体は妥当である。workerごとのfull weight copyはM1のbandwidthとmemory双方に不利である。

### 9.3 slot-localで必要なもの

原則:

```text
membrane / refractory / activity event
trace
modulation
eligibilityまたはそのlazy representation
retina adaptation
periphery
mjData/body/environment
RNG
```

である。

ただし eligibility を `E_total` denseでslotごとに持つ必要はない。まず `E_plastic` へ静的縮約し、その上でdense vs sparseを選ぶべきである。

### 9.4 sparse eligibilityの最悪ケース

sparse entryが例えば:

```text
edge_id u32
eligibility f32
last_step u32
padding
```

なら12〜16 byte/active edgeになり得る。

一方dense f32 eligibilityは4 byte/edge、timestampを足しても8 byte/edge程度である。

したがってepisode後半にactive setが膨らむと、sparseはdenseより**メモリも帯域も悪くなり得る**。epsilonで勝手に捨てられないため、active率が上がったらdense fallbackが必須である。

### 9.5 より良いmulti-fly: edge-major SIMD across environments

現在案はslot側からactive edge unionを作るが、shared topology/weightの最大の利点は **edgeを1回読んで複数slotへ使うこと**にある。

推奨候補:

```text
state layout: neuron-major x slot
activity: per-neuron positive/negative slot mask

for edge/pre-block:
    topology / shared weightを1回読む
    active slot maskを取得
    複数slotのcontributionを処理
```

sparse側も:

```text
active_slot_mask[pre]
-> outgoing edgeをslot unionとして1回だけ展開
```

にする。

これならslotごとに同じgraphを再走査する方式より、shared topology/weight bandwidthを本当に共有できる。

### 9.6 weight apply

同一edgeに複数slot更新がある場合、clamp semanticsを保つにはslot順が必要である。

```text
w = shared_weight[e]
for slot in deterministic_order:
    w = clamp(w + delta[slot,e], 0, M)
shared_weight[e] = w
```

は正しい。

ただしslot順はclampが起きると学習結果へ系統的影響を持つ。これはbugではなく選択したmulti-fly semanticsである。

profileするべき:

```text
clamp hit count
edges with both positive and negative slot delta
slot-order-sensitive edge count
```

clampが絶対に起きないことをguardで証明できるedgeだけは、sum/reduction fast pathを使える。ただしf32 bitwise順序は変わる。

### 9.7 slot数の限界

**[要profile]** M1 16GBでは容量より先に unified-memory bandwidth / irregular access / CPU-GPU contention / thermal sustained limit が来る可能性が高い。

固定で4や8を推奨しない。`1,2,4,8...` は短時間だけでなくwarm-up後の持続性能でも測る。

## 10. CPU / GPU / IPC / I/O のwall-clock評価

### 10.1 現行control stepの直列鎖

**[確定]** trainerは概ね:

```text
FlyBody eye readout
-> Python retina encode
-> JSON serialize / stdin flush
-> Rust JSON parse / body ID binary-search
-> GPU neural submit
-> GPU motor gather submit
-> map_async + CPU wait
-> JSON response
-> Python periphery
-> Python loop: 10 x physics step
-> pose/velocity/collision/course
-> trajectory JSON
-> body/neural telemetry JSON + filesystem replace
```

である。

### 10.2 motor readback

**[確定]** `read_spikes_at()` は毎callで:

- index buffer
- output buffer
- staging buffer
- bind group
- encoder

を作り、gather submit後に同期map待ちする。

motor IDsはほぼ固定なので、resourcesはpersistent化できる。

さらに neural stepとgather/copyは **同じcommand encoderへ入れられる**。通常control stepを:

```text
neuron
-> plasticity
-> trace
-> motor gather
-> copy to persistent staging
-> single submit
-> one completion wait
```

にすれば、因果順を変えずにsubmit数を減らせる。

single-flyではmotorがphysicsの入力なのでcompletion fence自体は消せないが、2 submitを1 submitへできる。

### 10.3 latest runから確定できるsubmit数の概算

`reports/flyppy/latest.md` の24 episodeはcontrol step合計1802。

通常stepだけで:

```text
1802 neural submit
+ 1802 motor gather submit
= 3604 submit
```

さらに:

- collision 24回
- gate pass 11回
- reinforcement event 合計35回
- 各eventで `steps=4` -> 140 neural submit
- episode reset 24回 -> 24 eligibility reset submit
- checkpoint 4 episode毎 -> 6回
- `state()` は spikes / neurons / synapses の3 readback submit -> 18 submit

なので、neural runtimeだけで **少なくとも約3786 queue submit** がこのrunに発生する。

通常step融合、reinforcement 4 stepを1 encoder/submit、checkpoint copyを1 submitにすると同じ計数で約1867 submitまで減らせる。約50.7%削減である。

これはGPU kernelを変えなくても実施できる。

### 10.4 reinforcement

**[確定]** Python IPCはすでに `steps=4` を1 requestで送る。しかしRustは内部で4回 `runtime.step()` を呼ぶため4 submitである。

同じstimulusでreadback不要なので:

```text
4 x (neuron -> plasticity -> trace)
```

を1 encoderへ積み、1 submitにするのが exact な低リスク改善である。

### 10.5 retina

**[確定]** optical column -> FlyBody ommatidium mappingはinit時に固定されている一方、`encode()` は毎step Pythonで:

- side loop
- column loop
- per-column NumPy sum / clip / adaptation
- per-body-ID append

を行う。

さらにその body ID/current pair をJSONへ変換し、Rust側で毎request body ID -> dense index binary searchしている。

意味を変えずに:

- ommatidium indicesをNumPy array化
- adaptationをvectorized array演算
- column -> body expansionをprecomputed index arrays化
- body IDではなく起動時解決したdense neuron indexを送る
- 最終的にはbinary/in-process bufferで渡す

ことができる。

retinaのうち `get_ommatidia_readouts()` 自体のrender/readout時間と、その後のPython transduction時間は必ず分けて測る。

### 10.6 Python ↔ Rust JSON IPC

**[確定]** current bridgeは1 control stepごとに `json.dumps -> pipe write/flush -> blocking readline -> json.loads` である。

stimulus側はmotor responseより大きい可能性があるため、単純な「JSON固定費」だけでなく:

```text
request bytes/control-step
stimulate_body pair count
serialize us
pipe write/flush us
Rust parse us
body-id resolve us
response bytes
read/parse us
```

を測る。

PyO3化は有力な中間策だが、PyO3だけではMuJoCo Python loop・telemetry・GPU fenceは消えない。

### 10.7 MuJoCo / physics_steps=10

**[確定]** `FlyBodyMuscleAdapter::step_muscles` 相当のPython実装は `for _ in range(physics_steps)` で毎substep:

- phase
- actuator neutralization
- qfrc reset
- cadenceに応じたwing torque
- wing torque apply
- leg/haltere torque hook
- finite check
- `sim.step()`

を行う。

Flyppy v3は50 us physics timestepと0.2 ms wing-command cadenceを意図的に維持している。

したがって単純にphysics timestepを粗くするべきではない。

MuJoCo Python binding自体はC関数呼び出し中GILを解放し、`mj_step(..., nstep=N)` も提供する。しかし現行Flyppyはsubstep間で外力・wing phase・leg/haltere torqueを更新するため、**何もせず `nstep=10` へ置換するのは同値ではない**。

最終fast pathは、50 usを維持したままtorque計算と10 step loop全体をC/C++/Rust extension側へ移すのがよい。

### 10.8 MuJoCo multi-environment

MuJoCo公式の設計では、read-only `mjModel` を共有し、threadごとに独立 `mjData` を持つ方式がthread-safeである。

multi-flyを行う場合、FlyGym wrapperが追加で持つPython stateを分離できるなら、この形が自然である。

### 10.9 telemetry

**[確定]** `LiveTelemetryPublisher` はviewerとは別processでも producer側で同期I/Oを行う。

trainer defaultは:

```text
body_telemetry_stride = 1
neural_telemetry_stride = 5
```

であり、body telemetryは毎control step:

```text
qpos/qvel -> Python list
-> JSON serialize
-> temp file write
-> os.replace
```

を行う。

**training defaultはOFF**にするべきである。可視化時だけ bounded ring queue -> writer process/threadへ渡す。

これは科学的意味を一切変えない。

### 10.10 trajectory

trajectoryもhot pathでJSON serialize + file writeする。stride=10なのでtelemetryより低頻度だが、compact binary/ring bufferへappendし、episode後にJSONL変換する方がよい。

### 10.11 checkpoint

**[確定]** GPU `state()` は:

```text
spikes readback
neuron-state readback
synapse-state readback
```

を別々に行い、各々 staging allocation + submit + map waitを行う。

さらに `checkpoint.rs` はf32/u32を要素ごとに4 byte `write_all` している。

推奨:

```text
GPU live buffers
 -> one checkpoint encoderでdedicated snapshot/stagingへcopy
 -> training stateの整合点を固定
 -> async map / writerへhandoff
 -> bytemuck/cast_slice相当でbulk/chunked write
```

full resume checkpointとweight-only evaluation snapshotを分ける。

## 11. memory / memory traffic評価

リポジトリにはrun時生成されたMaleCNS manifestが含まれていないため、正確な `E` はこのsource treeだけでは確定しない。以下は **E=25.6Mを仮定した説明用概算**であり、実runではbridge readyのexact countを記録すること。

### 11.1 resident memory概算

```text
SynapseState(weight + eligibility) 8E   ~= 195.3 MiB
f32 edge array                  4E      ~= 97.7 MiB
u32 edge array                  4E      ~= 97.7 MiB
pre+post+count                  12E     ~= 293.0 MiB
edge bitset                     E/8     ~= 3.1 MiB

NeuronState 16B * 166,691               ~= 2.54 MiB
external current f32 * 166,691           ~= 0.64 MiB
```

multi-flyで危険なのはneuron stateではなくper-slot edge stateである。

### 11.2 current neural stepのtraffic下限イメージ

current dense incoming scanは少なくとも `pre_indices` の `4E` を読む。

plasticityは全edgeでpre/postを読むので約 `8E`。fast edgeではさらにsynapse stateをread-modify-writeするため約 `16E_fast` が加わる。

したがって topology/synapseだけでも概念的に:

```text
4E + 8E + 16E_fast
```

程度のtrafficがあり、これにrandomなspike/meta/neuron state accessが加わる。

E=25.6MかつE_fast≈Eなら、この部分だけで約716.8 MB/neural-step相当になる。

これはcache/reuseを無視した上限・下限混在の概算であり実GB/sではないが、**全edge RMWを構造的に減らす価値が非常に大きい**ことは示す。

### 11.3 episode reset

current resetは全edgeへ `reset_eligibility` をdispatchする。

lazy / PlasticFastGraph化後は:

- dense `E_plastic`だけclear
- generation counter方式
- sparse container discard

等で全E scanを避けられる。

## 12. Apple M1 16GB 固有の考察

### 12.1 unified memory

Apple SiliconのUMAではCPU/GPUが同一物理メモリを共有できるが、**同期が無料になるわけではない**。

current wgpu pathではstaging buffer / copy / map APIがあり、motor結果が必要なためCPU-GPU completion依存も残る。

Apple自身もUMAではcopy削減と同時にCPU/GPU access synchronization、multi-buffering、working-set管理を重要視している。

### 12.2 memory bandwidth

このworkloadは大量のedge streamingとirregular readを含むため、compute FLOPSよりmemory trafficが支配する可能性が高い。

しかもM1ではCPUとGPUが同じmemory systemを共有するため、GPU neural runtimeを帯域いっぱいにするとCPU側MuJoCo/retinaも影響を受け得る。

profileでは理論帯域値ではなく Instruments / Metal counterの実効 read/write GB/s を使う。

### 12.3 atomics

AppleのMetal最適化資料でもglobal atomicsはbottleneck候補として明示されている。

したがって ActiveEdgeFrontier を「edge数が少ないから自動的に速い」と扱ってはいけない。global append counterやdedup atomicをthreadgroup集約する、あるいはBlockedIncomingでatomic自体を避ける構成を比較する。

### 12.4 workgroup size

現在はWGSL側もRust側も256固定である。

64/128/256等をkernel別に実測する。propagation、plasticity、gatherで最適値が同じとは限らない。

### 12.5 thermal / sustained performance

短いautotuneだけではM1 sustained workloadの熱・電力制約を取り逃がす可能性がある。

推奨:

```text
startup micro-tune
-> 5〜10分程度のwarm sustained validation
-> throughput低下時のみ再選択
```

worker数は短いburst最高値ではなく、持続 simulated biological seconds / wall second で決める。

### 12.6 direct Metal

workspaceは `wgpu = 30.0.1` で、wgpuはmacOSでMetal backendをfirst-class supportしている。

したがってdirect Metalは「Metal GPUを使うため」の変更ではない。

採用理由になり得るのは:

- shared host/GPU buffer lifecycleの直接制御
- Metal-specific synchronization
- SIMD-group primitive
- indirect work generation
- WGSLでは表現しにくいhot kernel
- wgpu CPU command overheadがprofileで支配的

の場合だけである。

先に移植するとalgorithmic bottleneckをそのままMetalへ持ち込むだけになり得る。

## 14. 最速候補アーキテクチャ

### 14.1 Layer 1: Snapshot Compiler

起動時にsource MaleCNS snapshotからruntime-only viewを作る。

```text
Source snapshot (immutable)
  -> FastGraph incoming CSR
  -> FastGraph outgoing edge-index CSR
  -> DopamineGraph
  -> potential_modulated_post bitset
  -> PlasticFastGraph
  -> degree buckets
  -> blocked incoming descriptors
  -> sensory dense-index map
  -> motor gather index sets
```

source snapshotは変更しない。

### 14.2 Layer 2: single-fly fast semantic runtime

通常control tick:

```text
vectorized retinal current
-> compact/dense-index stimulus buffer
-> one GPU command encoder:
     stimulus scatter/prepare
     propagation selected mode
     neuron update
     plasticity materialization/event update
     trace/update bookkeeping
     motor gather
     staging copy
-> one submit
-> one required completion wait
-> native/in-process periphery + MuJoCo 10 substeps
```

通常tickでGPU submitは原則1回にする。

### 14.3 Layer 3: plasticity

実装順は:

1. `PlasticFastGraph` へ静的縮約
2. `E_plastic` が十分小さければdense eligibilityのまま
3. 必要なら timestamp eligibility
4. post-factorized modulation/weight integral
5. candidate-local-postだけmaterialize
6. active率が高いとdense fallback

とする。

最初からhash/map sparse containerを作らない。

### 14.4 Layer 4: propagation

候補を少なくとも:

```text
DegreeBucketDense
BlockedIncoming
CandidateIncoming
ActiveEdgeFrontierSegmented
```

とし、実activity replayで選ぶ。

reference bitwise modeは現行incoming edge orderを保持する。

### 14.5 Layer 5: body hot loop

Pythonはexperiment setup / curriculum / reportingへ縮退させる。

最終候補:

```text
native trainer core
  retinal transduction vectorized/native
  neural runtime
  periphery state
  MuJoCo C API 50us loop
  collision/event extraction
  async logger/checkpoint producer
```

言語はRustでなければならないわけではない。MuJoCo C APIへ低overheadで到達し、現在のsubstep torque semanticsを保持できる実装が優先である。

### 14.6 Layer 6: optional multi-fly

single-fly fast path後もGPU/CPUに余力があり、time-to-thresholdが短くなる場合のみ追加する。

```text
shared topology
shared weights
neuron-major x slot state
per-neuron active slot mask
edge-major graph traversal
per-slot eligibility/lazy state
shared mjModel + per-slot mjData
```

とする。

## 15. 現在案より大幅に速くなる可能性がある代案

### A. Structural-plasticity specialization

最優先候補。`S_D` と `E_plastic` が小さければ、generic sparse machineryを使わずplasticity workそのものを桁違いに減らせる可能性がある。

**リスク: 低〜中。** 数式根拠が明確。checkpoint内部表現だけ整理が必要。

### B. Full event-driven CNS

neuron / trace / modulation / eligibility / propagationをtimestamp化し、event frontierだけ処理する。

**期待: activityが非常にsparseなら最大級。**

**リスク: 高。** irregular GPU workがdenseより遅い領域が広い可能性がある。最初から全面移行しない。

### C. Blocked pull sparse execution

ActiveEdgeFrontierのsort/reductionを避け、sorted CSRを活かしてinactive pre blockをskipする。

**期待: M1のmedium-sparse領域で高い。**

**リスク: 中。** block size autotuneが必要。

### D. Edge-major multi-environment

slotごとにgraphを読むのでなく、edge/topologyを1回読みslot maskで複数環境を処理する。

**期待: multi-flyを採用するなら現在案よりbandwidth効率が良い可能性。**

**リスク: 中〜高。** 学習schedule自体がsingle-flyと同値ではない。

### E. Direct Metal shared-buffer control path

wgpu profile後、submit/map/staging抽象が明確なceilingなら、motor tiny readbackやindirect dispatchだけMetal-native化する。

**リスク: 高。優先度低。**

### F. GPU-resident physics / MJX等

現在のMuJoCo/FlyBody物理と数値意味論を維持する要件に対しては、現時点の第一候補ではない。

physicsがnative CPU化後も支配的と実測された場合にだけ別backendとして検討する。

## 20. 現在案の重大な修正点

優先度順:

1. **PlasticFastGraphを追加する。**
2. **multi-flyを「exact canonical」から optional training-schedule accelerationへ格下げする。**

## 21. 最終推奨構成

最終的に推奨するcanonical hierarchyは次である。

```text
Tier A: Reference
  current-order CPU/GPU small fixture
  sequential f32 semantics
  bitwise/tight-tolerance verification

Tier B: Canonical fast single-fly
  compiled Fast/Dopa/PlasticFast graph
  degree-bucket + blocked + candidate/frontier hybrid
  post-factorized lazy plasticity
  one-submit neural+motor path
  vectorized/pre-indexed retina
  native MuJoCo/periphery hot loop
  telemetry off/async
  async bulk checkpoint

Tier C: Optional throughput expansion
  edge-major shared-topology multi-fly
  shared weight 1 copy
  slot-local dynamics/plasticity/body
  sustained autotuned slot count
  CPU/GPU overlap

Tier D: Backend-specific ceiling removal
  selected direct-Metal kernels / shared buffers
  only after profiling proves wgpu ceiling
```

**最重要なのは、Tier Cを先に作らないことである。**

現在の約139.55 ms/control-stepのどこを使っているかをP0で分解し、意味を変えないTier Bを先に詰める。その上でまだM1のCPU/GPUに余力があり、shared-weight multi-flyが frozen-evaluation threshold までのwall-clockを実測で短縮する場合だけTier Cを採用する。

この順序が、実装コスト・失敗時損失・生物学的/物理的意味保存・Apple M1の帯域特性を同時に考えたとき、現在案より「有用な学習状態までのwall-clock」を短縮する可能性が高い。

## 23. 最終短答

### 現在案は本当に最速候補か

**まだ違う。** 改善方向は正しいが、static PlasticFastGraph、post-factorized lazy plasticity、blocked/degree-bucket propagation、single-submit control pathが抜けている。

### 現在案をそのまま実装してよいか

**いいえ。** 上記のP0/P1再編とmulti-flyの位置づけ修正を先に行うべきである。

### 最大の確定問題は何か

現時点で確定できるのは「最大ボトルネック」ではなく、**不要な同期・resource creation・submit・同期telemetry・full checkpoint readback/scalar I/Oがcritical pathに存在すること**である。

### 最大ボトルネック候補は何か

**[要profile]** dense all-edge plasticity / propagation、motor map fence、vision/retina、10-substep physicsのいずれか、または複合である。現状のデータだけでは順位を確定できない。

### 最終推奨

**まずsingle-flyの意味保存runtimeを極限まで高速化し、その後にだけmulti-flyを足す。** そのsingle-fly runtimeは、現在案よりさらに静的graph specializationとpost-factorized lazy stateを強く使うべきである。
