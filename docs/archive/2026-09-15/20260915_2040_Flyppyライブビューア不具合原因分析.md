# Flyppy ライブビューア不具合 原因分析・引き継ぎ

作成日時: 2026-09-15 20:40 JST  
対象リポジトリ: `shute2004/virtual-fly`  
対象ブランチ: `feat/flybody-flyppy-loop`  
監査基準 HEAD: `b0011b5e5ac1207c7849abe9c3079f39a57279e5`

## 1. この文書の目的

Flyppy v3 の detached live viewer について、以下の症状をゼロベースで調査した結果を、次の実装担当 LLM に引き継ぐための文書である。

症状:

- `bash scripts/dev/view_flyppy_v3.sh` でブラウザページ自体は開く。
- `bash scripts/dev/train_flyppy_v3_population.sh` で学習自体は正常に進む。
- しかしブラウザには FlyBody の映像が表示されない。
- MaleCNS の neuron firing 表示も動かない。
- production viewer E2E は PASS している。
- 通常学習では `VF_POPULATION_TELEMETRY=1` を有効化していない。

要求される設計は次の通り。

- 学習はデフォルトで headless のまま。
- viewer が接続された間だけ body/neural snapshot を生成する。
- viewer は学習途中から attach 可能。
- viewer を閉じれば viewer 用負荷は消える。
- `VF_POPULATION_TELEMETRY=1` を常時必須にしてはいけない。

この監査では、原因分析を先に行うため、既存コードの変更は行っていない。

---

## 2. 結論

現在確認できた最も強い根本原因は、**viewer と trainer の接続に使う Unix domain socket 名を「experiment directory の絶対パス文字列の SHA-256」で決めていること**である。

macOS の通常の case-insensitive filesystem では、例えば次の2つは同じ物理ディレクトリを指す。

```text
/Users/<local-user>/Desktop/virtual-fly
/Users/<local-user>/desktop/virtual-fly
```

しかし現在の `viewer_control_socket_path()` は path string をそのまま hash するため、同じ物理ディレクトリでも別の socket path になる。

実測例:

```text
/Users/.../Desktop/.../flyppy-v3
  -> /tmp/virtual-fly-viewer-3e11ea9591c8eeef58fe.sock

/Users/.../desktop/.../flyppy-v3
  -> /tmp/virtual-fly-viewer-30fbf9ee9580db33ce71.sock
```

この状態では:

```text
browser
  -> viewer HTTP server: 正常
  -> viewer-side ViewerTelemetryLease: socket A を探す

trainer
  -> LiveTelemetryPublisher: socket B を listen

A != B
```

となる。

結果として trainer 側は viewer demand を一度も認識せず、on-demand telemetry が生成されない。

```text
publisher.requested() == false
```

そのため:

- `live/body.json` が生成されない
- `live/neural.json` が生成されない
- detached `live_body_viewer.py` は body snapshot を受け取れない
- `live/fly.png` が生成されない
- ブラウザには FlyBody 映像が出ない
- MaleCNS firing 表示も更新されない

という観測症状がすべて同時に説明できる。

重要なのは、これは「browser rendering の問題」と「trainer telemetry の問題」が別々に壊れているのではなく、**viewer demand の rendezvous が成立していないため、その下流が全部空になる**という1本の故障で説明できる点である。

## 3. 現在の実行経路

### 3.1 v3 viewer launcher

`scripts/dev/view_flyppy_v3.sh`

概略:

```text
ROOT=repo root
EXPERIMENT=artifacts/experiments/flyppy-v3
VF_VIEWER_ENVIRONMENT_VERSION=v3
exec scripts/dev/view_flyppy.sh "$EXPERIMENT"
```

### 3.2 generic viewer launcher

`scripts/dev/view_flyppy.sh`

主な処理:

1. neural viewer graph の準備・schema 検証
2. `live_viewer_server.py` 起動
3. macOS では `uv run mjpython scripts/embodiment/live_body_viewer.py` 起動
4. browser を次の URL で開く

```text
http://127.0.0.1:8765/visualization/live-neural-viewer.html?experiment=artifacts/experiments/flyppy-v3
```

5. HTTP server と body renderer の両プロセスを監視

ログ:

```text
/tmp/virtual-fly-live-viewer-8765.log
/tmp/virtual-fly-live-body-8765.log
```

### 3.3 HTTP server / viewer demand lease

`scripts/embodiment/live_viewer_server.py`

`ViewerTelemetryLease` が background thread で trainer の Unix socket へ接続し、接続中は約 0.4 秒ごとに:

```text
watch\n
```

を送る。

HTTP server は missing telemetry に対して browser の `Promise.all()` が全体停止しないよう、status/body/neural に waiting payload を返す。

`/api/viewer-health` では:

- `telemetry_stream_connected`
- socket path
- status/body/neural/fly.png/camera の存在・mtime・size

を確認できる。

### 3.4 Browser frontend

`visualization/live-neural-viewer.html`

importmap:

```text
three -> jsDelivr three@0.180.0
three/addons/ -> jsDelivr examples/jsm/
```

browser は `experiment` query parameter を読み、`connect()` から graph fetch、camera POST、`tick()` に進む。

`tick()` は:

```javascript
Promise.all([
  fetch status.json,
  fetch neural.json,
  fetch body.json,
])
```

の後に FlyBody image を更新する。

`fly.png` は:

```text
/live/fly.png?v=<timestamp>-<counter>
```

で読み直しており、cache busting は既に入っている。

### 3.5 Trainer

`scripts/embodiment/train_flyppy_population_process.py`

重要部分:

```python
telemetry_active = bool(args.telemetry) or publisher.requested()
```

つまり通常時は `--telemetry` が false でも、viewer が接続されれば `publisher.requested()` が true になり telemetry を生成する設計である。

viewer が必要な MaleCNS body IDs は viewer graph から読み込まれる。

telemetry が active の slot 0 では:

- viewer IDs を `read_body` に追加
- body spikes を neural snapshot に出力
- body handle の `snapshot()` から qpos/qvel を取得
- body.json / neural.json を publish

する。

### 3.6 Packed body worker

`scripts/embodiment/train_flyppy_population_packed.py` では body factory を packed slot handle に差し替える。

`scripts/embodiment/flyppy_packed_slot_adapter.py` の snapshot は worker の `snapshot` command へ渡る。

`scripts/embodiment/flyppy_packed_body_worker.py` は snapshot で:

```text
sim_time_s
qpos
qvel
```

を返す。

この経路自体は実測で動作した。

### 3.7 Detached body renderer

`scripts/embodiment/live_body_viewer.py`

これは trainer 内で映像を render するのではなく、`live/body.json` を読む detached observer である。

body snapshot が存在すると:

1. qpos/qvel を MuJoCo sim へ適用
2. `mj_forward`
3. camera 適用
4. `renderer.update_scene`
5. `renderer.render()`
6. atomic に `fly.png` 書き込み

を行う。

body telemetry が無ければ待機する。

したがって body renderer 自体を起動しても、trainer が body.json を publish しなければ fly.png は出ない。

## 4. 実際に観測したこと

### 4.1 Browser module は実行されている

実ブラウザ Chrome 152 で current HTML を実行し、Three.js の WebGL canvas が生成されることを確認した。

DOM には Three.js r180 の canvas が作られていた。

また実際の viewer server log には:

```text
GET /artifacts/embodiment/neural-viewer-graph-v1.json 200
POST /api/camera 200
```

が記録され、その後 `fly.png` の取得も試行されていた。

したがって、少なくとも今回の障害では以下は root cause ではない。

- importmap が完全に壊れて module が始まらない
- Three.js CDN が取得できない
- OrbitControls import が失敗している
- JS syntax error で `connect()` 前に停止している
- `connect()` 自体が呼ばれていない
- `experiment` query が flyppy-v3 に反映されていない

### 4.2 fly.png cache ではない

frontend は毎回 query string を変えている。

```text
fly.png?v=${Date.now()}-${frameCounter}
```

よって、古い fly.png が browser cache に固定されていることが主因ではない。

### 4.3 Promise.all は今回の root cause ではない

以前なら body/neural の 404 により Promise.all 全体が reject し、fly.png 更新まで進まない可能性があった。

現在の server は missing body/neural/status に waiting payload を返すようになっている。

さらに実ブラウザが fly.png を要求していることも確認した。

したがって Promise.all は今回の直接原因ではない。

設計上さらに独立化する余地はあるが、この障害を直すための最優先箇所ではない。

### 4.4 viewer と training は時間的に overlap していた

対象 run では training summary が約 12.2 秒の run を示しており、その時間帯に viewer log で camera POST と fly.png request が継続していた。

したがって「viewer を開いた時にはもう training が終わっていた」だけでは説明できない。

### 4.5 実際の failed viewer session は lowercase path を使用していた

HTTP server の static file error には次のような path が出ていた。

```text
/Users/<local-user>/desktop/virtual-fly/...
```

通常の checkout path は:

```text
/Users/<local-user>/Desktop/virtual-fly/...
```

である。

macOS 上ではこの2つは same file / same directory だった。

### 4.6 shell / Python の path spelling 挙動

macOS の case-insensitive filesystem 上で lowercase alias から `cd` すると、shell builtin `pwd` が logical spelling を維持する場合がある。

確認例:

```text
cd /Users/.../desktop/virtual-fly
bash builtin pwd      -> /Users/.../desktop/virtual-fly
bash builtin pwd -P   -> /Users/.../desktop/virtual-fly
/bin/pwd -P           -> /Users/.../Desktop/virtual-fly
```

また Python の `Path.resolve()` も、既に absolute な lowercase spelling を与えた場合に、必ずしも filesystem 上の表示 casing に正規化しない。

したがって現在の launcher と Python path hashing の組み合わせでは、同じ physical directory を異なる string として扱うことが実際に起こり得る。

## 5. 根本原因の直接再現

現在の `viewer_control_socket_path()` は概ね次の形式である。

```python
resolved = str(Path(experiment_dir).resolve()).encode("utf-8")
token = hashlib.sha256(resolved).hexdigest()[:20]
return Path("/tmp") / f"virtual-fly-viewer-{token}.sock"
```

同じ物理 experiment directory を、片方は `Desktop`、片方は `desktop` spelling で `LiveTelemetryPublisher` と `ViewerTelemetryLease` に渡して直接再現した。

結果:

```text
same_fs=True
publisher_socket != viewer_socket
viewer_connected=False
publisher_requested=False
```

つまり、**同じ experiment なのに viewer と trainer が互いを発見できない状態を current code だけで再現できた。**

この再現は本番症状と一致する。

```text
HTTP/browser は生きている
camera POST も来る
training は進む
しかし trainer telemetry は一切 materialize しない
body renderer は待機
fly.png は無い
neural 表示も更新されない
```

## 6. socket identity が一致する場合は data path が動く

逆に、publisher と viewer で同じ path identity を使う条件では、現在の production packed trainer を viewer-demand で動作させることに成功した。

確認条件:

- population=4
- packed-process
- direct-ray K=13
- `VF_POPULATION_TELEMETRY=1` なし
- viewer demand あり

確認結果:

```text
viewer lease connected
trainer rc=0
live/body.json generated
live/neural.json generated
live/status.json generated
```

body snapshot には qpos/qvel が存在し、neural snapshot にも viewer body ID に対応する firing data が入った。

また viewer server を trainer より先に起動するケースでも:

```text
viewer health: stream disconnected
  -> trainer starts
  -> viewer lease connects
  -> body/neural/status materialize
```

という late rendezvous が成立した。

このため以下は root cause ではない。

- population=4 自体
- packed-process 自体
- packed body worker の snapshot path
- MaleCNS viewer body IDs の read path
- `VF_POPULATION_TELEMETRY=1` がないこと
- viewer-first 起動順序そのもの

## 7. production viewer E2E が PASS する理由

`scripts/analysis/probe_viewer_production_e2e.py` は browser E2E ではない。

実際には:

- viewer server subprocess を起動
- body renderer を起動
- packed trainer を起動
- Python の `urllib.request.urlopen()` で endpoint を確認
- body/neural/fly.png の存在・mtime・HTTP response を確認

している。

Chromium/Chrome は起動しない。

したがって frontend module exception などがあっても原理的には検出できない。

さらに重要なのは、この probe が viewer server と trainer に**同じ canonical ROOT 由来の experiment path を渡している**ことである。

そのため今回のような:

```text
Desktop vs desktop
```

という path spelling mismatch が発生しない。

つまり E2E が PASS していることと、実際の launcher 経路で今回の不具合が出ることは矛盾しない。

E2E は「backend data path が正しい条件では動く」ことは検証しているが、「実 launcher から browser を開いた現実の path/rendezvous」までは検証していない。

## 8. 現時点で除外できる候補

今回の root cause として優先度を下げてよいもの:

1. Three.js CDN URL 自体
2. OrbitControls CDN/importmap
3. frontend module syntax error
4. `connect()` 未実行
5. `tick()` が一度も走らない問題
6. `experiment` query の flyppy-v3 反映ミス
7. fly.png browser cache
8. current server における missing JSON + Promise.all 問題
9. population=4
10. packed worker snapshot
11. MaleCNS viewer IDs 読み出し
12. macOS で `mjpython` launcher 自体が即死している問題
13. viewer と training が overlap していないだけ、という説明

これらを再度主原因として掘る前に、まず control socket identity を修正すべきである。

## 9. 次の実装担当への修正方針

### P0: control socket identity を path string の表記揺れから独立させる

最優先。

現在の問題は「同一 physical experiment directory でも path string が違えば別 ID」という設計である。

必要条件:

- `/Desktop/...` と `/desktop/...` が同一 directory を指す環境では同じ viewer endpoint に到達すること。
- symlink 等、同一 physical directory への別 spelling でも可能なら同一視できること。
- `/tmp` Unix socket の path length 制約は維持すること。
- viewer と trainer の双方で全く同じ identity 規則を使用すること。
- `VF_POPULATION_TELEMETRY=1` 強制という回避策にしないこと。
- viewer telemetry を常時生成する回避策にしないこと。

実装候補としては、存在する experiment directory について filesystem identity、例えば `stat()` の device/inode 等を使って short token を導出する方法が考えられる。

少なくとも単純な `Path.resolve()` の文字列 hash のままでは macOS case alias を吸収できない。

実装時には repository の cross-platform 要件を確認し、最小で明確な identity helper にまとめること。

### P0 test: path alias regression test を追加

macOS または case-insensitive filesystem で:

```text
same physical experiment dir
uppercase/lowercase spelling differs
publisher and lease created independently
```

としても:

```text
lease connected == true
publisher.requested() == true
```

になることを検証する。

プラットフォーム依存 test にする必要がある場合は、その前提を明示する。

### P1: launcher-level production test を追加

現在の production E2E は backend probe であり、実 launcher/browser 経路を覆わない。

少なくとも次の2層に分けるとよい。

#### backend E2E

現在の probe 相当。

- trainer
- viewer HTTP server
- detached body renderer
- artifact generation

を検証。

#### real frontend E2E

実 Chromium/Chrome で:

- `live-neural-viewer.html?experiment=...` を開く
- Three.js canvas が作成される
- JS exception がない
- graph load 成功
- camera POST 発生
- viewer-health が trainer attached を示す
- body/neural の frame/step が進む
- fly.png が更新される
- DOM 上の viewer status が connected/active へ移行する

まで確認する。

### P1: viewer health の意味を強化

現在の `telemetry_stream_connected` は有用だが、ブラウザ UI はそれを主状態として表示していない。

少なくとも debug/diagnostic 表示として:

- expected control socket path
- trainer stream connected/disconnected
- body.json last update
- neural.json last update
- fly.png last update

が見えると、今回のような問題を frontend issue と誤認しにくい。

### P2: logging を必要時だけ見えるようにする

現状 artifact polling の GET log は抑制されているため、通常 log だけでは browser tick が継続しているか判断しづらい。

常時 noisy にする必要はないが、debug flag で:

- viewer lease state transition
- socket path
- connect/disconnect
- trainer accepts viewer
- telemetry on/off transition

を記録できるとよい。

## 10. 修正後に必ず確認する状態遷移

### A. trainer first

```text
trainer starts
viewer demand = false
no body/neural viewer telemetry generated
viewer opens
lease connects
trainer demand = true
body/neural generated
fly.png generated
browser updates
viewer closes
lease disconnects
trainer demand = false
viewer-only telemetry cost disappears
```

### B. viewer first

```text
viewer starts
HTTP page works
lease retries because trainer absent
trainer starts
publisher socket appears
lease connects automatically
telemetry begins
browser updates
```

### C. viewer attaches late during long training

viewer 起動前に trainer が何 step 進んでいても attach 後に telemetry が開始されること。

### D. viewer closes and reopens

```text
close -> demand false
reopen -> demand true
```

が同一 training process 中に成立すること。

### E. path alias

trainer と viewer を同一 physical repo の異なる case spelling から起動しても接続すること。

今回の regression の最重要ケース。

### F. telemetry environment override

`VF_POPULATION_TELEMETRY=1` は従来通り explicit always-on telemetry として動いてよいが、通常 viewer 利用の必須条件にはしないこと。

## 12. 過去 run についての証拠強度

一点だけ区別しておく。

failed viewer session の viewer/server 側が lowercase:

```text
/Users/<local-user>/desktop/virtual-fly/...
```

を使っていたことはログから確認できた。

一方、その**同じ過去 trainer process が実際に生成した socket path string** はログに残っていないため、その過去プロセスが uppercase `Desktop` を使ったことを事後的に直接比較することはできない。

したがって厳密には:

- historical trainer の casing mismatch そのもの: ログ不足で直接証明不能
- current implementation に同一 physical path の spelling mismatch で socket が分裂する bug がある: 直接再現済み
- その bug が実際の症状を完全に再現する: 確認済み
- socket identity を一致させると production data path が動く: 確認済み

という証拠関係である。

現時点で、今回の症状を current code 上で同じ形に再現できた原因はこの socket identity bug であり、最優先で修正するのが妥当である。

その後:

1. path alias regression test
2. stream lease attach/detach test
3. production packed trainer + viewer-demand test
4. detached body renderer + fly.png test
5. 実ブラウザ E2E

の順で確認する。

既存の design requirement を崩す回避策、特に:

```text
常時 telemetry を有効化する
VF_POPULATION_TELEMETRY=1 を必須化する
trainer 本体で常時 render する
```

は採用しないこと。

根本原因は viewer-demand rendezvous の identity であり、そこを直接修正する。
