# Flyppy ライブビューア不具合 修正結果

作成日時: 2026-09-15 20:55 JST  
対象リポジトリ: `shute2004/virtual-fly`  
対象ブランチ: `feat/flybody-flyppy-loop`

## 1. 結果

Flyppy v3 detached live viewer の実ブラウザ不具合は、実環境で修正確認できた。

確認した実行構成:

- ターミナル1: training
- ターミナル2: viewer
- training: `bash scripts/dev/train_flyppy_v3_population.sh` 系 production packed trainer
- viewer: `bash scripts/dev/view_flyppy_v3.sh`
- 通常利用時に `VF_POPULATION_TELEMETRY=1` は不要

修正後、実ブラウザで FlyBody の映像が正常に接続・更新された。

## 2. 確認された root cause

独立監査 `docs/archive/2026-09-15/20260915_2040_Flyppyライブビューア不具合原因分析.md` が指摘した control socket identity bug が実際の不具合原因だった。

旧実装では、viewer/trainer rendezvous 用 Unix domain socket 名を experiment directory の絶対パス文字列の SHA-256 から生成していた。

macOS の case-insensitive filesystem では、例えば:

```text
/Users/.../Desktop/virtual-fly
/Users/.../desktop/virtual-fly
```

は同じ物理ディレクトリを指すが、文字列としては異なる。

そのため旧実装では:

```text
viewer  -> socket A
trainer -> socket B
```

となり、HTTP viewer 自体は正常に起動していても trainer が viewer demand を認識できなかった。

結果として:

```text
publisher.requested() == false
```

のままとなり、viewer 接続中にも:

- `body.json`
- `neural.json`
- detached body renderer 用 snapshot
- `fly.png`

が live data として生成されず、FlyBody と MaleCNS の表示が停止していた。

## 3. 修正

`scripts/embodiment/live_telemetry.py` の viewer control socket identity を、path string の表記そのものではなく、存在する experiment directory の filesystem identity を基準に生成する方式へ変更した。

主な性質:

- case alias が同一物理ディレクトリなら同一 socket identity
- symlink alias でも同一物理ディレクトリなら同一 socket identity
- Unix socket path は `/tmp` の短い名前を維持
- viewer/trainer が同一 helper を使用
- viewer telemetry の常時生成は不要
- `VF_POPULATION_TELEMETRY=1` を通常viewer利用の必須条件にしない

また viewer 側は接続失敗時に control socket path を再計算するため、viewer-first 起動後に experiment directory が作成・再作成された場合にも新しい filesystem identity へ追従できる。

## 4. 回帰検査

`scripts/analysis/probe_viewer_stream_lease.py` に以下の回帰ケースを追加した。

- trainer first
- viewer first
- symlink alias
- macOS case alias
- experiment directory 再作成後の reconnect

今回の不具合の中心である `Desktop` / `desktop` のような path spelling 差を、再発防止対象として明示的に検査する。

## 5. 実ブラウザ検証

修正後、実際の production 利用形態で確認した。

```text
terminal 1: training
terminal 2: viewer
```

viewer は学習とは独立して起動し、実ブラウザ上で FlyBody 映像が正常に接続された。

これにより少なくとも以下の経路が実環境で成立したことを確認した。

```text
production training
  -> on-demand viewer request
  -> trainer detects viewer
  -> body/neural telemetry
  -> detached MuJoCo renderer
  -> fly.png
  -> browser viewer
```

## 6. 結論

今回の不具合は frontend rendering 自体ではなく、viewer と trainer が同一 physical experiment directory を異なる path spelling で参照した際に、control socket identity が分裂する rendezvous bug だった。

filesystem identity ベースへ変更したことでこの分裂を解消し、実ブラウザで FlyBody 映像が動作することまで確認した。

この不具合は修正済みとして扱う。
