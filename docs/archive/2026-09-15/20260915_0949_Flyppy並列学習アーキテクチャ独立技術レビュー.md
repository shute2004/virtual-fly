## 1. 総合判定

**判定: 再設計推奨**

対象文書の根本認識、すなわち「複数個体化の前に1個体あたりの dense edge work、GPU readback、IPC、physics loop を削る」「shared weight を1 copyにする」「sparse/dense を実機で切り替える」は妥当である。

しかし、そのまま実装するべきではない。主な理由は4つある。

1. **sparse plasticity の擬似コードが現行方程式と一致しない。** 文書記載順では current-step local term まで `eligibility_decay` が掛かる。
2. **candidate-post sparse propagation を主方式として固定する根拠が足りない。** ultra-sparse 領域では active outgoing edge frontier + segmented reduction の方が少ない edge を触れる可能性があり、逆に Apple GPU では irregular traversal / global atomic / dedup のコストで dense が勝つ領域も広い。
3. **shared-weight の deterministic slot-order apply を「slotごとの逐次dispatch」で実装すると不要な直列化になる。** 同じ clamp semantics を保ったまま、edge単位1 dispatch 内で slot順に適用できる。
4. **現行コードの別の大きな停止要因が対象文書で過小評価されている。** 特に、毎 control step の同期 motor readback、10回の Python→MuJoCo physics substep、同期 telemetry ファイル書き込み、checkpoint の full-state readback と4-byte単位ファイル書き込みである。

したがって、対象文書の「hybrid runtime」という結論は残しつつ、**propagation は2択ではなく3択、plasticity は active-list 毎step更新ではなく timestamp/lazy closed-form を主方式、multi-fly weight apply は edge-union方式**へ置き換えるのがよい。

また `reports/flyppy/latest.md` の現行 run は 24 episode / 251.466 s、表中 control step 合計は 1802 なので、run全体では約 **7.17 control step/s、約139.5 ms/control step** である。checkpoint・reinforcement・telemetry等を含む値なので neural kernel単体値ではないが、最適化余地が大きいことは明確である。

MaleCNS の正確な現在 edge 数については、生成物 `artifacts/malecns-v1.0/manifest.json` がリポジトリに含まれていないため、この branch のみから 25.6M を厳密確認できない。`prepare_malecns.py` は MaleCNS v1.0 の annotated neuronal entries を採用し、exact count を manifest に記録する設計であり、`neural_bridge` の ready response も実際の `neurons` / `edges` を返す。以後の profile では概算値ではなく、その run の exact count を必ず記録すべきである。

## 2. 現行設計の最大ボトルネック順位

順位は実測前の推定であり、P0 profile で入れ替える前提である。ただしコード上の確定事実と推定を分ける。

| 順位 | 候補 | 推定コスト | 根拠 | 最初に実測すべき指標 |
|---:|---|---|---|---|
| 1 | `plasticity_step` の全 edge dispatch | 非常に大 | plasticity有効時は毎 neural step `edge_count` 全体をdispatchし、fast edgeでは trace/spike/synapse state を読み、eligibility/weight を更新する。propagationより read-modify-write が重い可能性が高い | GPU timestamp、edge kernel時間、実効GB/s、fast-edge数 |
| 2 | `neuron_step` の全 incoming edge scan | 非常に大 | 全 neuron が incoming CSR を走査する。E≈25.6Mなら `pre_indices` だけで約97.7 MiB/step。spike/meta/weight参照が加わる | neuron kernel時間、active pre数、candidate post数、degree-weighted edge数 |
| 3 | selected motor readback の同期 fence | 大 | `read_spikes_at()` が毎回 index/output/staging buffer、bind group、encoderを生成し、`map_async` 後 `device.poll(Wait)` でCPUを止める | gather dispatch、copy、map待ち、resource creation時間 |
| 4 | Python側 FlyBody / MuJoCo / retina hot loop | 大になり得る | 1 control stepで `vision.encode()` 後、`step_muscles(... physics_steps=10)` が Python loop で10回 `sim.step()`。whole-body torque計算も各physics stepで走る | retina時間、10 substep合計、1 `sim.step()`平均、Python overhead |
| 5 | telemetry / trajectory の同期I/O | 中〜大 | `body_telemetry_stride` 既定値は1。`LiveTelemetryPublisher._write()` は毎回 JSON serialize→temp file write→`os.replace` を同期実行する | telemetry ON/OFF A/B、write時間、fsyncではなくてもfilesystem latency |
| 6 | checkpoint | 短時間runでは中、長期では周期的大停止 | GPU `state()` が spikes/neuron/synapse を全readback。その後 `checkpoint.rs` は各f32/u32を4 byteずつ `File::write_all` する | readback時間、weights/eligibility書込み時間、checkpoint amortized比率 |
| 7 | Python↔Rust subprocess + JSON | 中 | control stepごとに `json.dumps`、pipe flush、blocking `readline`、JSON parse。さらに body ID→indexをRust側で毎回binary search | request serialize/write/read/parse、Rust request setup時間 |
| 8 | dense `external_current` upload | 小〜中 | N≈166,691なら f32 全neuronでも約0.64 MiB/step。25M級edge workより桁違いに小さい。ただし `queue.write_buffer` staging overheadは残る | write_buffer時間、compact化A/B |

### 2.1 最重要修正

対象文書は「全 edge scan」を主要コストとする方向では正しいが、**propagation と plasticity を一括りにしない方がよい**。現行 `plasticity_step` は fast edge に対して synapse state を毎step read-modify-write するため、活動が疎でも bandwidth を使う。一方 `neuron_step` は全edgeの `pre_indices` は見るが、weightは presynaptic event が非zeroのときだけ必要になる。

したがって最初に疑うべきは「dense propagation」単独ではなく、**dense plasticity + dense propagation のedge系2本**であり、特に plasticity を先に timestamp/lazy 化した方が wall-clock に効く可能性が高い。

### 3.2 重点29項目への短答

1. **現在の最大ボトルネック推定**: edge workが最大候補という判断は妥当。ただし最有力は propagation単独ではなく plasticity全edge RMW。readback/physicsが実測で上回る可能性もある。
2. **全edge scanが主要コストか**: 主要候補である。ただし `plasticity_step` と `neuron_step` を別々に測る必要がある。
3. **candidate-postは現行dynamicsを再現できるか**: 条件付きで可能。external-current、active fast pre、active dopamine preを取りこぼさず、全neuronのdecay/refractoryを維持する必要がある。
4. **outgoing adjacency / active frontierの方が速いか**: ultra-sparseでは十分あり得る。candidate-postは「active outgoingを一度触った後、candidate postの全incomingを再走査」するため、高indegree postでは無駄が大きい。
5. **lazy eligibility / trace / modulationの反例**: 数学的にはevent境界でmaterializeすれば成立する。対象文書のactive-list更新順には反例がある。
6. **inactive区間のweight updateを閉形式化できるか**: できる。後述する。
7. **sparse/dense切替条件**: neuron fractionではなく、`Σ out_degree(active_pre)`、`Σ in_degree(candidate_post)`、active eligibility edge数、modulated-postに接続するactive eligibility数を使うべき。
8. **frontier/dedup/prefixがdenseより高くなる条件**: sparse側のedge expansion + atomic bitset + compaction/sort/reductionの実仕事量とcache missがdense scan相当へ近づいた時。固定fractionではなく実機計測で決める。
9. **Apple Silicon / Metalでsparse有利か**: 自動的には有利ではない。Apple GPUはSIMD divergence、irregular memory、global atomicsに弱くなり得る。sparseは低activity域の候補である。
10. **direct Metalへ移るべきか**: 先ではない。wgpu 30.0.1はmacOSでMetal backendを使う。WGSLではatomic型がi32/u32に限定されるため表現力差はあるが、まずalgorithmと同期を直すべき。
11. **multi-fly何匹まで有効か**: 固定値はまだ出せない。現行のfull eligibility/slotならまず1,2,4を試し、sparse eligibility後に8を候補にする。16GB unified memoryでは容量より帯域・cache pressureが先に悪化する可能性が高い。
12. **shared weight競合をどう処理するか**: active edge unionを作り、edgeごとにslot maskを持ち、1 invocationがslot 0→N-1順にdeltaを適用する方式を第一候補にする。
13. **deterministic slot-order applyは遅いか**: 「slotごとにdispatch」なら遅い。edge単位1 kernel内のslot loopならclamp semanticsを維持しつつweight read/writeを1回にまとめられる。
14. **per-step / microbatch / chunk updateのどれが最速か**: 意味保存なら「同一neural stepの複数slotをmicrobatchし、step末に1回edge-wise apply」。時間方向chunkでweight反映を遅らせる方が速い可能性はあるが、次stepが古いweightを見るため意味変更になる。
15. **eligibilityをworker-localに全edge必要か**: 必要ない。active edgeのみ `{edge_id, value, last_step}` を保持する方式は成立する。
16. **active eligibility setのみで成立するか**: 成立する。ただしepsilon pruningは意味変更。GPU上のlookup/dedupコストがdenseを超えたらdense fallbackする。
17. **local weightを持たずshared 1 copyにできるか**: できるし、wall-clockとmemoryの両面で推奨。
18. **bandwidth/cache/atomic contention**: 現行はedge bandwidthが大きい。新案でもcandidate bitset、active-list append、slot-mask ORを無制限にglobal atomic化すると逆に遅くなる。threadgroup/local reductionを優先する。
19. **external_current全neuron upload**: 約0.64 MiB/step規模なので、25M edge scanより本質的に小さい。最適化価値はあるが最優先ではない。
20. **motor readbackで毎step buffer/map待ちがあるか**: ある。`read_spikes_at()` が毎call resourceを生成し、blocking mapを行う。
21. **Python↔Rust JSON IPC支配度**: 同期固定overheadとして存在するが、現状はGPU map/edge kernel/physicsより下の可能性が高い。高速化後には支配的になり得る。
22. **trainerをRust orchestrationへ移す価値**: ある。特にMuJoCo10 substepとneural runtimeを同一native hot loopにすると、PyO3でJSONだけ消すより ceiling が高い。
23. **MuJoCo/retina/peripheryとGPU CNSのpipeline**: 複数slotで `GPU CNS(A)` と `CPU physics/retina(B)` をoverlapする。single flyの因果依存は崩さない。
24. **physics/neural timestep batching**: 現在すでに1 CNS controlに `physics_steps=10` を使う。複数control stepをまとめるとclosed-loopを変える。代わりに10 physics substepをnative loop内でまとめてPython往復を消す。
25. **reward/aversive DANの連続stepをGPU内でまとめられるか**: まとめられる。重要なのは、Python→Rustは既に `steps=4` を1 JSON requestで送っている点である。改善対象はRust loop内の4回 `queue.write_buffer` / encoder / submitを1 command sequenceへ畳むこと。
26. **viewer/telemetry/loggingがcritical pathか**: viewer自体は分離されているがproducerは分離されていない。body telemetry既定stride=1で毎control step同期ファイル書込みがあるためcritical pathに残っている。
27. **checkpoint/resetの不要readback**: checkpointはfull readbackする。resetはfull readbackしないが全edge eligibility reset dispatchを行う。sparse eligibilityならactive state clearだけにできる。
28. **runtime autotuning**: 妥当。ただしworker数・thresholdだけでなくworkgroup、kernel mode、slot mask方式、readback strategyを実 activity trace で選ぶ。
29. **さらに大きな高速化余地**: lazy closed-form plasticity、checkpoint I/O再設計、edge-wise single-dispatch shared update、native MuJoCo hot loop、同期telemetry除去、dopamine/fast分離によるrefractory時fast scan省略が対象文書の主要な見落としである。

## 4. 数式・意味論上の問題

### 4.1 sparse propagation

現行 `neural.wgsl` の `neuron_step(post)` は、概略次である。

```text
fast_current = external_current[post]
dopa_input = 0
for incoming edge pre -> post:
    if spikes_prev[pre] != 0:
        if pre transmitter == dopamine and event > 0:
            dopa_input += synapse_count * modulator_scale
        else:
            fast_current += fast_sign(pre) * weight[edge] * event_sign

modulation_new = modulation_old * alpha + dopa_input

if refractory > 0:
    membrane = reset
    refractory -= 1
    spike_next = silent
else:
    membrane = membrane_old * decay + fast_current
    threshold判定
```

重要なのは、**refractory中でも dopamine input は modulation に入る**ことである。一方、fast currentは refractory branchで捨てられる。

したがって最速の意味保存実装は、FastGraphとDopamineGraphを本当に別kernel/別candidateとして扱うべきである。

- refractory post: fast incoming scanは省略可能
- refractory postでもdopamine scanは必要
- non-refractory post: external currentまたはactive fast preがなければfast incoming scan不要
- modulation decay自体は全neuron更新でもN≈166kなので小さい

candidate-post方式そのものに反例はないが、「候補を立ててからcandidate postの全incoming fast edgeを読む」ため、active preが少なくてもcandidate postのindegreeが大きいと無駄が大きい。

このため propagation backend は次の3種類を持つ方がよい。

```text
A. DenseIncoming
   全FastGraph incomingを順次scan

B. CandidateIncoming
   active-pre outgoingでcandidate postをmark
   candidate postだけincoming scan

C. ActiveEdgeFrontier
   active-pre outgoing edgeだけfrontier化
   postでdeterministic segmented reduction
```

CはWGSLのportable `atomic<f32>`に頼らず、edge contributionのcompaction + post順reductionで構成できる。ただしsort/prefix/compactionの固定費があるため、ultra-sparse領域専用候補とする。

### 4.2 plasticity の現行正確式

`trace_step` は `plasticity_step` の後に実行される。したがって、step `t` のlocal termは概念的に:

```text
L_e(t)
 = trace_pre(t-1) * spike_post(t)
 - trace_post(t-1) * spike_pre(t-1)
```

である。

eligibility は:

```text
e_e(t) = beta * e_e(t-1) + L_e(t)
```

weight は、同じstepで更新済みの post modulation を使い:

```text
w_e(t) = clamp(
    w_e(t-1) + eta * m_post(t) * e_e(t),
    0,
    w_max
)
```

となる。

### 4.3 対象文書の active-list 擬似コードはそのままでは誤り

対象文書は、Pass A/B で先に:

```text
eligibility += local
```

した後、active listに対して:

```text
eligibility *= beta
weight += ...
```

と記述している。

これを文字通り実装すると:

```text
e(t) = beta * (e(t-1) + L(t))
```

となり、正しい:

```text
e(t) = beta * e(t-1) + L(t)
```

と一致しない。新規localまで `beta` 倍される。

修正するなら、既存eligibilityのdecay/materializeを先に行い、その後A/B localを加え、最後にweight updateする必要がある。

### 4.4 lazy eligibility / lazy modulation は成立する

現行値は:

```text
alpha = modulator_decay = 0.98
beta  = eligibility_decay = 0.995
eta   = learning_rate
r     = alpha * beta = 0.9751
```

edgeにlocal impulseがなく、post neuronに新しいdopamine inputもない区間がK step続くとする。区間開始時を `m0`, `e0`, `w0` とすると:

```text
m(j) = alpha^j * m0
e(j) = beta^j  * e0
```

なので、その区間のweight deltaは:

```text
Δw
 = eta * m0 * e0 * Σ[j=1..K] r^j
 = eta * m0 * e0 * r * (1 - r^K) / (1 - r)
```

で閉形式化できる。

この区間中は `m*e` の符号が変わらないため、実数演算上は逐次clampを最終1回のclampにまとめても最終値は同じになる。local eventまたはdopamine eventが来た時点で区間を切り、そこまでmaterializeすればよい。

注意点は **bitwise f32一致とは限らない** ことである。逐次乗算と `pow` / 閉形式では丸め順が変わる。方程式の意味保存を要求するなら許容誤差でreference比較し、bitwise replayが要件なら反復更新を残す必要がある。

### 4.5 lazy trace も成立する

traceは:

```text
x(t) = gamma * x(t-1) + spike(t)
gamma = 0.95
```

なのでeventのないK stepは:

```text
x(t+K) = gamma^K * x(t)
```

でmaterializeできる。

ただしN≈166kのtrace passはedge系より軽いため、最初からlazy traceまで入れる必要はない。plasticityをlazy化した後に profile 上必要なら実施すればよい。

### 4.6 active eligibility set の正しい使い方

active setだけを保持する方式は成立する。条件は:

1. `eligibility != 0` のedgeを取りこぼさない。
2. epsilon thresholdで勝手に消さない。これは意味変更である。
3. edge event時に `last_update_step` からdecayをmaterializeする。
4. checkpoint時には全active entryを現在stepへmaterializeするか、timestamp込み形式で保存する。
5. episode resetではactive containerを破棄すればよい。

dense `eligibility[edge]` をslotごとに常時持つ必要はない。25.6M edgeと仮定するとf32 eligibilityだけで約97.7 MiB/slot、full edge-ID listも最悪約97.7 MiB/slotである。最初から両方を各workerに持つのは帯域・cache面で不利である。

### 4.7 shared weight と synchronization

shared weight 1 copyは妥当である。

ただし文書案の:

```text
slot0 apply dispatch
slot1 apply dispatch
slot2 apply dispatch
...
```

はclamp semanticsは明確だが、wall-clockでは不要な直列化を生む。

より速い意味保存案は:

```text
active shared-edge union
edge -> slot bitmask
```

を構築し、1 edgeを1 GPU invocationに担当させる方式である。

```text
w = weight[edge]
for slot in 0..N:
    if slot_mask has slot:
        w = clamp(w + delta(slot, edge))
weight[edge] = w
```

これならslot順clampを完全に保持しつつ、shared weightのload/storeは原則1回で済み、slot数分のdispatchも不要になる。

複数slot deltaを単純sumして最後に1回clampする方式は、正負deltaと境界が混ざると結果が変わるため、別の近似仕様としてのみ採用すべきである。

## 5. GPU / CPU / memory / IPC の実装評価

### 5.1 GPU memory layout

E≈25.6Mを仮定した概算は以下である。

```text
current SynapseStateGpu(weight + eligibility) 8B * E  ≈ 195.3 MiB
1 x f32 edge array                          4B * E  ≈  97.7 MiB
pre + post + synapse_count                 12B * E ≈ 293.0 MiB
full edge-id list                           4B * E  ≈  97.7 MiB
edge bitset                                      E/8 ≈   3.1 MiB
external_current f32 * 166,691                     ≈   0.64 MiB
NeuronStateGpu 16B * 166,691                       ≈   2.54 MiB
```

したがって、multi-flyで危険なのはneuron stateではなく **per-slot edge state** である。

### 5.2 Apple Silicon / WGPU

現行 `reports/flyppy/latest.md` は `gpu:Apple M1 (Metal)` である。`Cargo.toml` の `wgpu = 30.0.1` はmacOSでMetal backendを持つので、direct Metal化は「GPU backendを初めてMetalへ変える」のではなく、**wgpu/WGSLの抽象を外してMetal固有機能とbuffer/synchronizationを直接制御する変更**である。

WGSLの標準atomic型は `i32/u32` なので、portable WGSL fast pathはfloat scatter-addを前提にしない方がよい。一方、direct MetalはMetal language/version次第でより広い機能を使えるが、Apple自身もglobal atomicsを主要bottleneck候補として挙げているため、float atomicが使えることと速いことは別問題である。

Apple GPUでは、固定 `@workgroup_size(256)` を最適と仮定しない。direct Metalではpipelineごとの `threadExecutionWidth` を見てmultipleを選ぶのが基本であり、wgpu側でも64/128/256等を短いbenchmarkで選ぶ価値がある。

### 5.3 motor readback

ここはコード上、即修正対象である。

`GpuRuntime::read_spikes_at()` は毎call:

- index buffer作成
- output buffer作成
- staging buffer作成
- bind group作成
- encoder作成
- gather dispatch
- copy
- submit
- `map_async`
- `device.poll(Wait)`

を行う。

persistent resourcesへ変えるだけでも改善する。ただしsingle flyは「motor resultがないと次のphysicsを進められない」ため、ringだけで依存fenceは消えない。ringの本当の価値はallocation削減とmulti-fly時のoverlapである。

### 5.4 external current

compact化は正しいが、優先度を上げすぎない。dense uploadは約0.64 MiB/step程度であり、25M edge規模のkernel trafficより小さい。

さらに現在 `neural_bridge` は `stimulate_body` のbody IDを毎request `snapshot.index_of_body_id()` でbinary searchしている。retina mappingは固定なので、起動時に body ID→dense neuron indexへ変換し、trainer/runtime間はdense indexを直接渡せばCPU側の変換も消せる。

### 5.5 Python / Rust IPC

JSON subprocess round-tripは明確に不要な固定overheadである。ただし「PyO3化すれば最終形」とは限らない。

現行 hot loopにはさらに:

```text
Python retina
Python periphery
Python 10 x MuJoCo step
sync motor map wait
sync telemetry write
```

がある。

したがって absolute fastest を狙うなら、最終形は:

```text
Python: curriculum / experiment setup / report
Rust/C hot loop:
  neural engine
  motor gather
  periphery state
  MuJoCo stepping
  event return
```

の方が高い ceiling を持つ。FlyBody model構築や視覚seamを同じ意味でnative側へ移せるかが実装境界になる。

### 5.6 physics batching

現在は既に1 neural control stepに対し `physics_steps=10` である。Flyppy v3はphysics timestep 50 µs、wing command cadence 0.2 msを保持する。

したがって「physicsを10stepまとめる」ことで timestepを粗くする必要はない。**50 µsの10回積分をC/Rustの内側loopで連続実行し、Python loopを消す**だけで意味を変えず高速化できる。

複数control stepをまとめてmotor/vision feedbackを飛ばすのはclosed-loop timingを変えるため、別の近似である。

### 5.7 reinforcement batching

対象文書のP1にある「`steps>1` を1 command sequenceにまとめる」は、IPCレベルでは既に実装済みである。

`deliver_reinforcement()` は `steps=args.reinforcement_steps` を1 requestで送り、Rust `neural_bridge` が内部loopで4 neural stepを進める。

残っている最適化はGPU側で:

- stimulus uploadを1回
- 4回分のneuron/plasticity/trace dispatchを1 command encoderへ積む
- 1 submit
- readbackなし

にすることである。

### 5.8 telemetry / trajectory

viewerが別processでもproducer I/Oはcritical pathにある。

`LiveTelemetryPublisher._write()` は同期でファイルを書き換える。trainerの `body_telemetry_stride` 既定値は1なので、通常学習でも毎control step JSON serialize + filesystem write + renameが走る。

training modeでは以下のどちらかにすべきである。

- telemetry OFFをdefaultにする
- lock-free/ring queueへ書き、別thread/processがfilesystemへ吐く

trajectoryも同じく、hot loopではbinary/ring bufferへappendし、episode後にJSON/CSVへ変換する方がよい。

### 5.9 checkpoint / reset

checkpointは対象文書より重大である。

`SaveCheckpoint` は `runtime.state()` により full spikes / full neuron state / full synapse stateをGPUからreadbackする。その後 `checkpoint.rs` の `write_f32` / `write_u32` は `fs::File` に対して**要素ごとに4 byteずつ `write_all`**している。

E≈25.6Mなら weights + eligibility だけで約51.2M scalar write calls相当になる。OSやRust内部の実際の挙動をprofileする必要はあるが、実装として避けるべきである。

推奨は:

1. GPU上でcheckpoint boundaryのstateを専用snapshot bufferへcopy
2. queue順序でsnapshotを固定した後、training用mutable bufferは次stepへ進める
3. readback/mapとdisk writeはI/O threadへ渡す
4. `bytemuck::cast_slice` 等で大きな連続byte sliceとしてchunked/BuffWriter書込み
5. full resume checkpointと、weight-only評価snapshotを分ける

resetはfull CPU readbackをしないが、現在は全edgeに `reset_eligibility` dispatchする。sparse eligibility stateならactive container破棄だけでよい。

## 6. 私が考える最速構成

### 6.1 neural engine

```text
Snapshot compiler
  source MaleCNS immutable snapshot
      -> FastGraph incoming CSR
      -> FastGraph outgoing edge-index CSR
      -> DopamineGraph incoming/outgoing
      -> precomputed sign/count
      -> body_id -> dense_index tables

Runtime per neural step
  1. compact external stimulus apply
  2. Dopa sparse propagation + all-neuron modulation decay
  3. choose Fast propagation kernel:
       DenseIncoming
       CandidateIncoming
       ActiveEdgeFrontierSegmented
  4. neuron state update
  5. event-local plasticity impulse update
  6. lazy weight integration for only relevant active edge/post state
  7. trace update（initially dense N passでよい）
  8. fixed motor gather
```

kernel選択はactive neuron fractionではなく、degree-weighted predicted edge workで決める。

### 6.2 plasticity

主方式は `active-list every-step decay` ではなく:

```text
SparseEligibilityEntry {
    edge_id
    eligibility
    last_eligibility_step
}

LazyModulationState {
    value
    last_modulation_step
}
```

とし、local/dopamine event boundaryだけmaterializeする。

weight updateはpost modulationとeligibilityが同時に意味を持つ区間だけ処理し、event-free区間は閉形式でまとめる。

active setが大きくなった時だけdense plasticityへfallbackする。

### 6.3 multi-fly

shared:

```text
1 x topology
1 x FastGraph/DopaGraph
1 x weights
```

slot-local:

```text
neuron state
spikes
retina/periphery/body state
sparse eligibility state
```

shared weight applyは:

```text
edge union + slot bitmask
1 thread per active edge
slot-order loop inside thread
```

を第一候補とする。

worker数は長時間研究せず、実機で `{1,2,4,8}` を短時間測る。現行のdense per-slot eligibilityを維持するなら2〜4で帯域が頭打ちになる可能性が高く、sparse化後なら4〜8まで候補にできるが、これは予測であって固定値ではない。

### 6.4 CPU/GPU pipeline

複数slotを2群以上に分ける。

```text
GPU: CNS batch A
CPU: MuJoCo/retina batch B

GPU: CNS batch B
CPU: MuJoCo/retina batch A
```

single slot内では因果順序を維持する。

visionがMetal/GPU resourceを強く使う場合はGPU-GPU contentionになるので、CPU/GPU timelineを見てpipeline幅を決める。

### 6.5 orchestration

最終wall-clock最優先なら:

```text
Python
  experiment config / curriculum / reporting
      ↓ low-frequency
Rust native trainer
  neural runtime
  MuJoCo C API hot loop
  periphery
  event scheduler
  async checkpoint/log producer
```

を最終候補とする。

PyO3は移行手段として有用だが、JSON bridgeだけ消してPython physics loopを残す構成を最終形と決めない。

### 6.6 memory layout

- topologyはSoAを維持
- fast/dopa/no-opをruntime compileで分離
- outgoing adjacencyはedge IDを持ち、incomingと同一edge identityを共有
- weightはcontiguous 1 copy
- per-slot eligibilityはsparse first、dense fallback allocationは必要になったslotだけ
- active listは最大capacityを最初からEで確保しない
- candidate bitset / slot maskはinteger atomic ORを使うが、append counterへの競合はworkgroup単位で集約する

### 6.7 synchronization

exact modeでは:

```text
all slots propagation read step-start weights
barrier/pass boundary
all slots local plasticity state update
barrier/pass boundary
edge-wise slot-order shared weight apply
next neural step
```

時間方向のchunk updateは、次stepが古いweightを読むため意味を変える。採用するなら「高速化近似」と明記し、exact modeとは別にする。

### 6.8 autotuning

hardware/backendごとに短い実activity replayで以下を選ぶ。

- propagation mode A/B/C
- sparse/dense plasticity threshold
- slot count 1/2/4/8
- microbatch size
- workgroup size
- readback ring depth
- checkpoint buffer ring depth

thresholdの入力は:

```text
active_pre_count
sum_active_pre_out_degree
candidate_post_count
sum_candidate_post_in_degree
active_eligibility_count
active_modulated_post_count
active_eligibility_edges_into_modulated_posts
```

を使う。

単純な `active_presynaptic_fraction` だけではdegree skewを捉えられない。

## 7. 実装優先順位

### P0: profile + correctness基準

最初に実施する。

- exact neuron/edge countをrun metadataへ保存
- CPU wall-clock区間:
  - retina
  - JSON/IPC
  - GPU submit前処理
  - motor map wait
  - periphery
  - MuJoCo 10 steps
  - telemetry
  - trajectory
  - checkpoint GPU readback
  - checkpoint disk write
- GPU区間:
  - neuron/propagation
  - plasticity
  - trace
  - motor gather/copy
- activity counters:
  - depolarizing/hyperpolarizing pre数
  - fast/dopa outgoing edge work
  - candidate in-edge work
  - active eligibility数
  - modulated post数

同時に small graphのCPU/dense reference fixtureを固定する。

### P1: 同期停止とI/Oを除く

1. motor gather/readback resourcesをpreallocate
2. body telemetryをhot pathから外す
3. checkpoint writerをbulk/chunked I/Oへ変更
4. DAN `steps>1` をsingle GPU command sequence化
5. retinal/body IDを起動時dense index化

### P2: graph compile

1. FastGraph / DopamineGraph / ignored分離
2. sign/count事前符号化
3. outgoing CSR追加
4. current exact graph sizesをprofile metadataへ出す

### P3: plasticityを先に再設計

1. 正しいdecay→local→weight順序fixture
2. sparse eligibility + timestamp
3. lazy modulation
4. event-free closed-form weight integration
5. dense fallback
6. sparse reset

対象文書とはここで順番を変える。propagationより先にplasticityを最適化する価値が高い。

### P4: propagation 3-way hybrid

1. DenseIncoming baseline
2. CandidateIncoming
3. ActiveEdgeFrontier + deterministic segmented reduction
4. degree-weighted runtime selector

### P5: native hot path

P0 profileでJSON/Python/MuJoCo比率が十分大きい場合:

1. PyO3でneural bridge除去
2. さらに必要ならMuJoCo/periphery hot loopをRust/C側へ統合

PyO3を必ず先に長期間維持する必要はない。

### P6: shared-weight multi-fly

1. shared weight 1 copy
2. sparse slot-local eligibility
3. active edge union + slot mask
4. single-dispatch slot-order apply
5. slot再利用

### P7: overlap + autotune

- CPU/GPU microbatch pipeline
- worker 1/2/4/8 benchmark
- sparse/dense/kernel threshold自動選択

### P8: direct Metal hot kernel比較

wgpu版でalgorithmic workを削った後にのみ実施する。

比較対象はbackend全置換ではなく、まず:

- motor readback/shared buffer
- active frontier/segmented reduction
- slot-mask shared update

など制約が効くhot pathに限定する。

## 8. この文書よりさらに速くする具体案

対象文書より速くできる可能性が最も高い差分は以下である。

### 8.1 candidate-postを最終解にしない

対象文書:

```text
active pre outgoing
 -> candidate post mark
 -> candidate postの全incoming scan
```

修正版:

```text
ultra sparse:
  active edge frontier -> segmented reduction

medium sparse:
  candidate post -> incoming scan

dense:
  dense incoming scan
```

これによりdegree skewとApple GPUのirregular-work thresholdの両方に対応できる。

### 8.2 eligibilityを毎step触らない

対象文書:

```text
active eligibility listを毎step decay + weight update
```

修正版:

```text
edge event時だけ eligibility materialize
post dopamine event時だけ modulation materialize
無event区間のweight積分は幾何級数で一括
```

これは active list がepisode後半に膨張した時にも毎step bandwidthが増え続けない。

### 8.3 shared weight applyをslot dispatch列にしない

対象文書:

```text
slot0 dispatch
slot1 dispatch
...
```

修正版:

```text
active edge union
edge -> slot mask
1 edge invocation内でslot順clamp
```

同じ意味でweight load/storeとdispatch数を減らせる。

### 8.4 reinforcementをGPU内で一括進行

IPCは既に1 requestなので、次に削るべきは4回のGPU submissionである。

### 8.5 checkpointをtrainingから非同期化

full stateをcheckpoint boundaryでGPU snapshot bufferへcopyし、その後のmap/disk I/Oをtraining critical path外へ出す。現在の4-byte scalar write loopは廃止する。

### 8.6 Python physics loopを削る

50 µs physics semanticsは維持しつつ、10 `mj_step` をnative loop内で回す。これはneural modelを変えずにCPU wall-clockを削れる。

### 8.7 telemetryをproducer側でも非同期化

viewer process分離だけでなく、training processのfilesystem writeも外す。

## 9. 最後に

### 9.1 今の文書をそのまま実装すべきか

**いいえ。**

特に sparse plasticity の更新順は現行方程式と一致しないため、そのまま実装してはいけない。またcandidate-postとslot-order multi-dispatchを最終形として固定すると、より高速な構成を取り逃がす。

### 9.2 修正版を作ってから実装すべきか

**はい。**

ただし全面破棄ではなく、以下を対象文書へ反映すればよい。

- propagationを3-way hybridへ
- plasticityをlazy/timestamp + closed-formへ
- shared weight applyをedge-union + slot maskへ
- reinforcement最適化を「IPC batching」から「GPU submission batching」へ修正
- telemetry / checkpoint / MuJoCo Python loopを正式な主要hotspot候補へ追加
- sparse/dense thresholdをdegree-weighted workベースへ変更
- P3/P4を入れ替え、plasticityを先に最適化

### 9.3 最初にprofileすべきもの

最初のprofileは **1 Fly、現行コード、viewerなし** で、1 control stepを以下へ分解する。

```text
retina
Python JSON encode/write
Rust request setup
external upload
GPU neuron/propagation
GPU plasticity
GPU trace
motor gather/copy/map wait
JSON response
periphery
MuJoCo 10 substeps
telemetry/logging
```

さらにepisode境界で:

```text
reset
checkpoint GPU readback
checkpoint disk write
```

を別計測する。

GPUについて最初に欲しい数字は、単なるactive neuron率ではなく:

```text
E_exact
E_fast
E_dopamine
Σ out_degree(active fast pre)
Σ in_degree(candidate fast post)
active eligibility edges
active eligibility edges whose post modulation is active
```

である。

このprofile結果を使って、最初に `plasticity all-edge`、`motor readback fence`、`MuJoCo/retina` のどれが最大かを確定し、その最大項から削るのが wall-clock 最短経路である。
